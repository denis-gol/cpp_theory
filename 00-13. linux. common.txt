ТЕСТИРОВАНИЕ ЯДРА (для общего развития)

Некоторые механизмы.

1. Стресс-тестирование («Убийцы» систем)
    - stress-ng: Вирус-вредитель для проверки ядра. Умеет непрерывно, в тысячи потоков, одновременно создавать файлы, 
        тут же делать им unlink, вешать flock, переименовывать папки и обрывать дескрипторы. Если в коде ядра есть 
        хоть малейшая дыра в синхронизации, stress-ng уронит систему в Kernel Panic за несколько минут.
    - xfstests: Официальный и самый жесткий набор тестов для файловых систем Linux (Ext4, XFS, Btrfs). Он не просто 
        нагружает, он имитирует внезапное отключение питания посреди тяжелых операций с inodes, 
        проверяя, не сломается ли структура метаданных.
2. Динамический анализ ядра (Санитайзеры) - встроенные инструменты ядра:
    - KCSAN (Kernel Concurrency Sanitizer): Наблюдает за доступом к памяти. Если два процесса (или прерывания ядра) 
        одновременно пытаются изменить счетчик жестких ссылок в одной иноде без правильной блокировки, KCSAN мгновенно 
        фиксирует это и бьет тревогу, даже если система в этот момент не упала.
    - Lockdep (Runtime Locking Correctness Validator): Внутренний арбитр ядра, который следит за всеми блокировками 
        (включая flock). Он строит карту зависимостей в реальном времени. Если Lockdep видит, 
        что Процесс А ждет Процесс Б, а Процесс Б ждет Процесс А (Deadlock), он тут же выводит детальный отчет в логи.
3. Формальная верификация и статический анализ (проверка роботами-аналитиками)
    - Sparse — статический анализатор (созданный лично Линусом Торвальдсом). 
        Например, проверяет: если был open, то во всех ли ветках вызван close? Итд.

ПРОЦЕСС и ПОТОК

Процесс — это виртуальная операционная среда (абстракция), которую ядро Linux создает для выполнения программы. 
В ядре Linux за это отвечает структура struct task_struct (заголовок: <linux/sched.h>)

ВАЖНО!
В ядре Linux нет разделения на процессы и потоки — для него есть только «задачи» (task_struct).

Внутри хранится:
    - Выделенная изолированная виртуальная память.
    - Таблица файловых дескрипторов (открытые файлы, сокеты).
    - Права доступа (UID/GID — от чьего имени работает код).
    - Таблица диспозиции сигналов (Signal Disposition) - СМ. "СИГНАЛЫ".

Процесс создается сист.вызовом fork() (см: fork())

ЖИЗНЕННЫЙ ЦИКЛ ПРОЦЕССА (АКАДЕМИЧЕСКИЙ - Танненбаум)

[ Рождение: fork() / clone() ]
                        │
                        ▼
                ┌───────────────┐
                │  R (Running)  │ ◄───────┐
                └───────┬───────┘         │
                        │                 │
     Добровольный сон   │ Прилетел        │ Событие произошло
    (read / poll/ sleep)│ сигнал          │ или таймер сработал
                        ▼                 │
     ┌──────────────────────────────────┐ │
     │       S (Interruptible Sleep)    ├─┤
     │       D (Uninterruptible Sleep)  │ │
     └──────────────────┬───────────────┘ │
                        │                 │
                        │ kill -STOP      │ kill -CONT
                        ▼                 │
                ┌───────────────┐         │
                │  T (Stopped)  ├─────────┘
                └───────┬───────┘
                        │
                        │ exit() / убили
                        ▼
                ┌───────────────┐
                │  Z (Zombie)   │ ───► [ Окончательная смерть ]
                └───────────────┘       (Родитель вызвал waitpid)

Состояния:
- R (Running / Runnable) — Выполняется или Готов к выполнению
    Или занимает сейчас ядро или ждет кванта в очереди
- S (Interruptible Sleep) — Прерываемый сон
    Ушел с процессора сам или ждет данные (из сокета, файла итд), или вызвал sleep. Ядро м мгновенно его разбудить
- D (Uninterruptible Sleep) — Непрерываыемый сон
    Заблокирован системным вызовом (ввод-вывод к диску или папке NFS. Ядро запрещает прерывать, чтобы не вызвать краш.
- T (Stopped) — Остановлен (Заморожен)
    Принудительно заморожен по SIGSTOP (19) или SIGTSTP (Ctrl+Z). Используется, например, в отладке.
- Z (Zombie) — Зомби (Умерший процесс)
    Закончил выполнение, память очищена, дескрипторы освобождены. Ждет пока заберут код возврата по waitpid()

Процессы проводят 99% жизни в состояниях R и S

Разница между академическим и реальным:
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| Поток (Учебник)| Поток в Linux (task_struct)  | Описание работы под капотом                             |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| New            | Рождение (clone)             | Ядро выделяет task_struct, но поток еще не в очереди.   |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| Ready          | R (Runnable)                 | Поток сидит в runqueue и ждет свой квант времени.       |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| Running        | R (Running)                  | Поток прямо сейчас выполняется на ядре процессора.      |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| Waiting        | S (Interruptible Sleep)      | Ждет сеть/таймер. Ядро разбудит его при сигнале.        |
|                | D (Uninterruptible Sleep)    | Наглухо заблокирован диском или файловой системой.      |
|                | T (Stopped)                  | Заморожен отладчиком (gdb) или сигналом SIGSTOP.        |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+
| Terminated     | Z (Zombie)                   | Код выполнен, ждет пока родитель вызовет pthread_join.  |
+────────────────+──────────────────────────────+─────────────────────────────────────────────────────────+

Линукс не делает разницы между Ready|Running - если поток МОЖЕТ выполняться или выполняется - это R.
Если не может, то - S, D, T


Ключевые отличия процесса в S и R:
+───────────────────────────+────────────────────────────────────+────────────────────────────────────+
| Характеристика            | Кончился квант времени (Вытеснен)  | Процесс ушел в сон (Заблокирован)  |
+───────────────────────────+────────────────────────────────────+────────────────────────────────────+
| Статус в task_struct      | TASK_RUNNING                       | TASK_INTERRUPTIBLE / D             |
| Где сидит в ядре          | В очереди на выполнение (Runqueue) | В очереди ожидания (Wait queue)  |
| Хочет ли работать?        | Да, готов в любую микросекунду     | Нет, ждет внешнего события         |
| Как виден в htop/ps       | Статус 'R' (Running)               | Статус 'S' (Sleep) или 'D'         |
| Кто инициатор состояния   | Насильно планировщик ОС (Таймер)   | Добровольно сам код программы      |
+───────────────────────────+────────────────────────────────────+────────────────────────────────────+

На уровне ядра поток и процесс представлены одной и той же структурой task_struct.
Это фундаментальная особенность архитектуры Linux.

Концепция LWP (Lightweight Process)
    - С точки зрения планировщика задач (Scheduler) абсолютно всё в системе — это LWP.
    - Каждый поток при создании (std::thread итд), получает в ядре свою собственную независимую структуру task_struct.
    - У каждого потока есть свой уникальный TID (Thread ID), получаем его по gettid().
    - Для планировщика ядра каждый поток — самостоятельная единица, которую можно вешать на разные ядра процессора.

Потоки делят (шерят) общие ресурсы через указатели внутри этой структуры.

Поток создается сис.вызовом clone() со специальными флагами:
    - CLONE_VM — потоки делят одну и ту же виртуальную память.
    - CLONE_FS — потоки делят информацию о файловой системе (корневой каталог, текущая директория).
    - CLONE_FILES — таблицы файловых дескрипторов у всех общие (если один поток открыл сокет, второй его сразу видит).
    - CLONE_SIGHAND — у потоков общая таблица обработчиков сигналов!

Внутри task_struct есть поле pid — на уровне ядра это на самом деле TID (ID потока).
Также есть поле tgid (Thread Group ID) — это ID лидера группы (самого первого потока, с которого началась программа).
Когда в пространстве пользователя (Userspace) вызываете функцию getpid(), ядро Linux возвращает значение поля tgid. 
    Именно его мы привыкли считать «PID процесса».

МАСКА "USER MASK"

У каждого процесса есть свойство, которое называется маской режима создания файлов (User Mask или коротко umask).

Когда любая программа создает новый файл (лог-файл или конфигурацию) с помощью системного вызова open(), она явно 
    указывает желаемые права доступа — например, 0666 (чтение и запись для всех).
Но ядро Linux никогда не создает файл с теми правами, которые запросила программа напрямую. Вместо этого оно применяет 
    к ним фильтр в виде текущего umask процесса по формуле:
        Реальные_права = Запрошенные_права AND NOT umask

Другими словами - оно ЗАПРЕЩАЕТ (вырезает) соответствующее право при создании.
Обычно равен 0002 или 00022 («запретить запись для группы и для остальных»)

При запуске программы из терминала (будущего демона) процесс наследует текущий umask из терминала.
Если позже программа будет запущена другим админом или крон, запись в файл не будет доступна (получим permis. denied)

Безопасность - umask(0) не выставляет права 0777 на все файлы. Он говорит ядру: «Не вмешивайся, доверься кодеру».

Выставить можно двумя путями:
1) НЕ из кода:
    - через субшелл - как только демон уйдет в фон, субшелл закроется, маска останется 0022
        > (umask 0000 && /usr/local/bin/my_classic_daemon)
    - через env:
        > sh -c "umask 0000; exec /usr/local/bin/my_classic_daemon"
    - Если демон запускается через Systemd
        [Service] -> UMask=0000

2) Из кода - это ради гарантии, вдруг у админа лапки и он забыл про маску. Обычно в самом начале:
    #include <sys/types.h>
    #include <sys/stat.h>
    umask(0);

СМЕНА РАБОЧЕЙ ДИРЕКТОРИИ (CWD - Current Working Directory)

Проблема - есть правило: Линукс не позволит размонтировать диск или раздел, если его использует хотя бы один процесс.

Запущенный демон останется привязан к папке запуска. Если ночному админу потребуется обслужить систему и umount диск, то:
    > umount: /mnt/storage: target is busy.
    Можно писать завещание.

Делаем:
    #include <unistd.h>
    // Внутри кода демонизации:
    if (chdir("/") < 0) {
        // Обработка ошибки, если корень вдруг недоступен (что маловероятно)
        exit(EXIT_FAILURE);
    }

Внутри процесса дескриптор cwd сменится на /. Почему именно корень (/)?
    - корень невозможно размонтировать (т.е. корень никогда ничего не заблокирует)
    - можно прокинуть и например в /tmp, если надо писать в файл. Главное, чтобы только туда, где не будет никогда umount.
    - директория принадлежит root, ее права 0755 (rwxr-xr-x) - ошибка при попытке записи, хулиганам не сломать.

Если демону нужно писать в файл, то меняем на /var/run/my_daemon или /tmp

ИЗОЛЯЦИЯ СТАНДАРТНЫХ ФАЙЛОВЫХ ДЕСКРИПТОРОВ:  0 (stdin), 1 (stdout) и 2 (stderr).

Демон не должен иметь возможность писать/читать в потоки, поэтому их необходимо закрыть.
Просто close(0); close(1); close(2); здесь нельзя, т.к. дескрипторы 0,1,2 освободятся и могут случайно быть отданы
    другому процессу (int fd = open("config.txt", O_RDONLY);), затем случайный std::cout начнет туда гадить.
Поэтому - Перенаправление в /dev/null

    #include <unistd.h>
    #include <fcntl.h>
    #include <sys/stat.h>
    #include <sys/types.h>

    void isolate_descriptors() {
        // 1. Открываем "черную дыру" /dev/null на чтение и запись
        int null_fd = open("/dev/null", O_RDWR);
        
        if (null_fd != -1) {
            // 2. Перенаправляем stdin (0) в /dev/null
            dup2(null_fd, STDIN_FILENO);   // STDIN_FILENO == 0
            
            // 3. Перенаправляем stdout (1) в /dev/null
            dup2(null_fd, STDOUT_FILENO);  // STDOUT_FILENO == 1
            
            // 4. Перенаправляем stderr (2) в /dev/null
            dup2(null_fd, STDERR_FILENO);  // STDERR_FILENO == 2
            
            // 5. Сам дескриптор null_fd нам больше не нужен, закрываем его.
            // Номера 0, 1 и 2 теперь надежно удерживают связь с /dev/null.
            close(null_fd);
        }
    }

ГРУППА ПРОЦЕССОВ (Process Group)

Логическое объединение взаимосвязанных процессов, которое позволяет операционной системе управлять ими как единым целым. 
У каждой группы есть свой уникальный числовой идентификатор — PGID (Process Group ID).

ЛИДЕР группы (Process Group Leader) - процесс, который инициировал создание новой группы.
    - У лидера идентификатор процесса PID всегда равен PGID (PGRP)
    - Группа существует, пока жив хотя бы один из участников (даже если Лидер помер).

Группа нужна для:
    - Управление задачами (Job Control) - изменение данных (что именно?) можно отправить сразу на всех.
    - Групповая рассылка сигналов - три команды через пайп - kill по PGID (Ctrl+C) убьет всю группу.

Увидеть группу процессов:
> cat /dev/urandom | grep -a "abc" | less
    Замрет на less, ждет ввод
    Далее > htop, смотрим вывод (включить вывод через F2_Setup ► Screens ► Active Columns ...


Иерархия процессов: Процесс (PID) --> Группа процессов (PGID) --> Сессия (SID)

1. Процесс (PID) - Отдельная единица выполнения (конкретная программа или её поток).
2. Группа (PGID) - Объединяет связанные пайпом процессы для совместного получения сигналов терминала.
3. Сессия (SID) - Объединяет несколько групп процессов, привязанных к одному управляющему терминалу TTY.

СЕССИЯ объединяет все группы процессов, запущенные в рамках одной вкладки терминала (или одного SSH-подключения).
    Например, PID баша становится SID для 4 процессов: 1 bash + команды (cat, grep, less).
    Это связывает процессы с управляющим терминалом (controlling terminal). 
    Если закрыть терминал (крестиком), то закроются все процессы.

Демон - чтобы отвязаться от терминала должен завести свою сессию (SID).
ПРАВИЛО - вызов setsid() вернет ошибку, если текущий процесс является лидером группы процессов (PID == PGID).
    (Если бы лидеру группы разрешили вызвать setsid(), это нарушило бы фундаментальный принцип: 
    все процессы в одной группе обязаны принадлежать одной и той же сессии. Если лидер запилит себе свою сессию,
    то получится что он уходит, а остальные остались - поэтому: если ты лидер группы, тебе запрещено менять сессию.
    Сначала передай лидерство (умерев или сделав форк) либо выходи из группы.)

    Поэтому перед созданием сессии демон делает первый fork() и завершает родительский процесс.
    Дочерний процесс наследует старый PGID, но получает новый PID. Так как теперь PID != PGID, он гарантированно 
    не является лидером группы и имеет полное право создать новую сессию.

Но после этого нужно сделать второй форк - защита от захвата tty.
ПРАВИЛО - только лидер сессии может открыть и захватить управляющий терминал (TTY).
    Если процесс случайно откроет файл терминала, то станет уязвим к сигналам извне (SIGHUP при закрытии терминала).
    Поэтому потомок после создания делает второй форк, и закрывает родителя (его PID != SID, терминал не захватит).

Негласное правило демонов - при запуске с флагом -f (foreground) не создавать Демона, запуститься в обычном режиме.
    - Запрет на fork()
    - Прямой вывод в консоль (stdout / stderr)
    - Прямой контроль через сигналы TTY

УСТРОЙСТВА (папка /dev - "devices")

+---------------+-----------------------+-------------------------+---------------------------------+
| Устройство    | При записи (>)        | При чтении (<)          | Основной юзкейс                 |
+---------------+-----------------------+-------------------------+---------------------------------+
| /dev/null     | Исчезает без следа    | Ничего (Конец файла)    | Спрятать лишний вывод           |
| /dev/zero     | Исчезает без следа    | Бесконечные нули (0x00) | Создать пустой файл-контейнер   |
| /dev/urandom  | Исчезает без следа    | Бесконечный случайный   | Криптография, пароли, тесты     |
| /dev/full     | Ошибка "Диск заполнен"| Бесконечные нули (0x00) | Тестирование обработки ошибок   |
+---------------+-----------------------+-------------------------+---------------------------------+

/dev/null — это специальный виртуальный драйвер (символьное устройство), который работает на уровне ядра Linux.
    Каждое открытие создает независимый поток - это абсолютно новый, изолированный файловый дескриптор.
    Ему не нужно хранить данные (он не имеет состояния).
    Не имеет внутренней памяти, буфера или позиции чтения/записи (offset).

СИГНАЛЫ - подсистема системных сигналов (Signals)

Основной механизм асинхронного межпроцессного взаимодействия (IPC), с помощью которого ядро или другие процессы
    управляют поведением программ.

Являются неотъемлемой частью стандарта POSIX.

Сигнал — это асинхронное программное прерывание.
На системном уровне — это просто целое число от 1 до 64.

У каждого числа есть стандартное имя (макрос). Например:
    1 — это SIGHUP
    2 — это SIGINT (Ctrl+C)
    9 — это SIGKILL (немедленная смерть)
    15 — это SIGTERM (вежливая просьба выйти)
Еще сигналы:
    11 - SIGSEGV (Segmentation Fault - ошибка сегментации)

Когда сигнал отправляется процессу, ядро не передает никаких аргументов. Оно просто делает «пометку» в структуре 
дескриптора процесса (task_struct) внутри памяти ядра — выставляет определенный бит в единицу.

Сигналы генерируются в трех случаях:
1) Аппаратные сбои и исключения процессора (Hardware):
    - Программа попыталась поделить на ноль. Проц генерирует Аппар.ПРВ, ядро превращает в SIGPE, отправляет процессу.
    - Программа полезла в чужую или невыделенную память. MMU ругается, Ядро шлет процессу SIGSEGV.
2) Драйверы ядра и сама ОС (Kernel):
    - Закрылся терминал или оборвался SSH. Драйвер TTY генерирует SIGHUP
    - Процесс попытался писать в закрытый пайп или сокет. Подсистема ввода-вывода ядра генерирует SIGPIPE.
3) Другие процессы (Userspace):
    - Пользователь набрал в консоли kill -9 1234. Утилита kill делает системный вызов kill(). Ядро проверяет 
        права доступа и перенаправляет сигнал целевому процессу.

Адресаты сигналов:
- Конкретному процессу (по PID): Сигнал доставляется строго в один процесс.
- Группе процессов (по PGID): Если отправить сигнал на отрицательный PID (например, kill(-5000, SIGINT)), 
    ядро веерно разошлет его всем процессам, которые входят в эту группу. Именно так работает Ctrl+C в терминале.
- Конкретному потоку (Thread): Внутри многопоточного процесса (POSIX Threads) можно отправить сигнал конкретному 
    pthread_t через вызов pthread_kill().

Жизненный цикл доставки (как реагирует ПРЦ):
    Когда сигнал сгенерирован, он переходит в состояние Pending (ожидающий). Он сидит в очереди ядра до тех пор, 
    пока планировщик Linux не решит дать процессу квант процессорного времени.
    Когда процесс переключается из режима ядра (Kernel Space) обратно в режим пользователя (User Space), ядро проверяет
        есть ли у процесса сигналы (биты сигналов). Выполнение main ставится на паузу, дальше 3 варианта:
1) По умолчанию (Default)
    Процесс выполняет стандартное системное действие. Обычно это либо мгновенная смерть (Terminate), либо смерть с 
        сохранением слепка памяти (Core Dump).
    Пример: SIGTERM (выход), SIGSEGV (вылет с дампом).
2) Игнорирование (Ignore)
    Ядро просто сбрасывает бит ожидания сигнала. Процесс не узнает, что ему что-то прилетало. Код продолжает работать.
    Пример: Можно проигнорировать SIGPIPE или SIGHUP. !!! SIGKILL и SIGSTOP проигнорировать нельзя!
3) Перехват (Catch / Handle):
    Управление передается в специальную функцию — обработчик сигналов (Signal Handler), регается через sigaction().
    Пример: Мы перехватываем SIGTERM для плавного закрытия или SIGHUP для перезапуска конфигурации.

Остальные некоторые:
SIGSTOP (19) - принудительная заморозка (приостановки) выполнения процесса.
    - Процесс полностью останавливается на текущей инструкции.
    - Его состояние в ядре меняется на TASK_STOPPED
    - Кванты не выделяются, ПРЦ висит в памяти, сохраняя дескрипторы, сокеты и переменные.
SIGCONT (Continue) (18) - возобновляет работу процесса.


Незыблемое правило: два сигнала физически невозможно перехватить через sigaction или проигнорировать. 
Это абсолютные команды ядра:
    - SIGKILL (9) — абсолютная смерть (процесс уничтожается).
    - SIGSTOP (19) — абсолютный анабиоз (процесс засыпает).

Оба обрабатываются самим ядром «на подлете» к процессу, код самого приложения об их существовании даже не догадывается.

Сигналы, отправленные процессу хранятся в поле: Таблица диспозиции сигналов (Signal Disposition).
У ядра для каждого процесса есть прописанная таблица реакций по умолчанию.
Если мы не переопределили поведение, то будет выполняться дефолтное.

Диапазон сигналов в Linux строго разделен на две (три) принципиально разные группы:

1) Стандартные сигналы (POSIX) — от 1 до 31
    Классические сигналы (SIGHUP, SIGINT, SIGKILL и т.д.).
    Ключевое свойство — они не ставятся в очередь. Это бит в маске. Прилетело 3 шт, бит только один.

2) Сигналы реального времени (Real-time) — от 34 до 64
    SIGRTMIN ... SIGRTMAX
    Ключевое свойство — они гарантированно доставляются все и строго в порядке очереди. 10 раз дернул, 10 в очереди ждет

3) Сигналы 32, 33 - одна из самых красивых инженерных тайн подсистемы glibc и потоков в Linux.
    Их забирает себе библиотека pthread (NPTL — Native POSIX Thread Library) для управления потоками приложения.
    - Сигнал 32 (обычно SIGCANCEL) — Завершение потока - отправляется потоку
    - Сигнал 33 (обычно SIGSETXID) — Синхронизация прав (UID/GID)
        Если один поток меняет свои права доступа (вызвал setuid/setgid), права обязаны мгновенно измениться у всех 
            остальных потоков этого процесса. Для этого либа pthread отправляет 33 всем потокам этого процесса.
    glibc конспиративно прячет эти сигналы от программиста (вернет ошибку EINVAL - недопустимый сигнал)

Специальная структура для работы с сигналами - менять через & или | нельзя!:

sigset_t set;

sigemptyset(&set);       // Обнулить все 64 бита (маска пустая)
sigfillset(&set);        // Выставить все 64 бита в 1 (выбрать все сигналы)
sigaddset(&set, SIGINT);  // Включить конкретный бит (добавить SIGINT в маску)
sigdelset(&set, SIGTERM); // Выключить конкретный бит (убрать SIGTERM из маски)

fork()
    создает новый процесс как полную копию самого себя.

На самом деле, это clone() с флагами полной изоляции памяти. Рождает полноценный дочерний процесс.

Потомок наследует следующие признаки родителя:
    - сегменты кода, данных и стека программы
    - таблицу файлов, в которой находятся состояния флагов дескрипторов файла
    - рабочий и корневой каталоги;
    - реальный и эффективный номер пользователя и номер группы;
    - приоритеты процесса (администратор может изменить их через nice);
    - контрольный терминал;
    - маску сигналов;
    - ограничения по ресурсам;
    - сведения о среде выполнения;
    - разделяемые сегменты памяти.
Потомок НЕ наследует от родителя следующих признаков:
    - идентификатор процесса (PID, PPID);
    - израсходованного времени ЦП (оно обнуляется);
    - сигналов процесса-родителя, требующих ответа;
    - блокированных файлов (record locking).

Как только fork() завершается, в системе одновременно начинают работать два одинаковых процесса. Они находятся в одной 
и той же точке кода (сразу после вызова fork). 
Единственное отличие, по которому они понимают, кто из них кто:
    - Родителю fork() возвращает PID нового ребенка.
    - Ребенку fork() возвращает 0.

А дальше - МАГИЯ:

    #include <stdio.h>
    #include <sys/types.h>
    #include <unistd.h>

    int main (void)
    {
            pid_t pid = fork (); // для простоты случай -1 отбросим
            if (pid == 0) {
                    printf ("child (pid=%d)\n", getpid());
            } else {
                    printf ("parent (pid=%d, child's pid=%d)\n", getpid(), pid);
            }

            return 0;
    }

// этот вариант - для случая, когда команды соединены через пайп
    for (int i = 0; i < 3; i++) {
        pid_t pid = fork();
        if (pid == 0) {
            // --- КОД ВНУТРИ КОПИИ ---
            // Копия смотрит на свою унаследованную переменную 'i'
            
            // 1. Копия настраивает пайпы, зная свой индекс 'i'
            if (i > 0) dup2(pipes[i-1][0], 0); // если я не первый, беру вход из прошлого пайпа
            if (i < 2) dup2(pipes[i][1], 1);   // если я не последний, отдаю выход в текущий пайп

            // 2. Копия берет аргументы строго по индексу 'i'
            char *cmd = commands[i].name;
            char **args = commands[i].arguments;

            // 3. Копия вызывает execve со своими уникальными аргументами
            execve(cmd, args, environ); 
        }
        // Основной bash идет на следующую итерацию цикла, увеличивая 'i'
    }

//Еще вариант - создаем одного потомка:
    int rv;
    pid_t pid = fork();
    switch (pid) {
        case -1:
            perror("fork"); /* произошла ошибка */
            exit(1); /*выход из родительского процесса*/
        case 0:
            printf(" CHILD: Это процесс-потомок!\n");
            printf(" CHILD: Мой PID -- %d\n", getpid());
            printf(" CHILD: PID моего родителя -- %d\n", getppid());
            printf(" CHILD: Введите мой код возврата (как можно меньше):\n");
            scanf(" %d");
            printf(" CHILD: Выход!\n");
            exit(rv);
        default:
            printf("PARENT: Это процесс-родитель!\n");
            printf("PARENT: Мой PID -- %d\n", getpid());
            printf("PARENT: PID моего потомка %d\n", pid);
            printf("PARENT: Я жду, пока потомок не вызовет exit()...\n");
            wait(&rv); // ждет rv из Потомка
            printf("PARENT: Код возврата потомка:%d\n", WEXITSTATUS(rv));
            printf("PARENT: Выход!\n");
    }

КОД ВОЗВРАТА

Когда программа завершает работу, она обязана сделать системный вызов exit(код_возврата).
В этот момент ядро Linux делает следующее:
    - освобождает всю оперативную память, которую занимал этот процесс.
    - Закрывает все файловые дескрипторы (пайпы, сокеты, файлы).
    - не удаляет структуру task_struct (запись о процессе) и сохраняет там тот самый код_возврата.
    - переводит статус в Zombie, который будет висеть, пока родитель не заберет этот код.

wait(&status) - ждать завершения ЛЮБОГО потомка (первого кто помрет)
    pparent обязан дождаться завершения работы pchild (иначе - zombie).
    pid_t child_pid = wait(&code_return)


waitpid(pid, &status, options) - ждать завершения определенного потомка
    - pid > 0 (Ожидание конкретного потомка)
    - pid == -1 (Аналог обычного wait)
    - pid == 0 (Ожидание по группе процессов) - который находится в той же группе процессов (PGID), что и сам родитель.
    - pid < -1 (Ожидание конкретной группы)

Коды переменной status
Ядро использует одну 32-битную переменную status, чтобы закодировать сразу три важные вещи:
1) Как именно умер процесс (сам через exit или его убил сигнал?).
2) Был ли записан дамп памяти (Core dump).
3) Сам код возврата (если процесс завершился сам).

Карта битов переменной status.
- Старшие 16 бит в классическом wait() не используются (зарезервированы для расширенных флагов трассировки ptrace).
- Старший (второй) байт [биты 15–8]: Хранит код возврата из exit(N) или return N.
- Младший (первый) байт [биты 6–0]: Хранит номер сигнала, если процесс был убит, 
                        [бит 7]: флаг создания дампа памяти (Core Dump).

Список макросов и их назначение:
    Всего существует 4 главных макроса-вопроса (начинаются на WIF..., возвращают true/false) 
        и 3 макроса-значения (начинаются на W..., достают конкретные числа).
Группа А: Мирное завершение (exit или return)
    - WIFEXITED(status) — true, если процесс завершился добровольно (exit(), _exit() или выходом из main).
    - WEXITSTATUS(status) — чистый код возврата (0-255). Его можно вызывать только если WIFEXITED=true.
Группа Б: Принудительное уничтожение (kill)
    - WIFSIGNALED(status) — true, если процесс был аварийно убит системным сигналом (например, SIGKILL, SIGSEGV).
    - WTERMSIG(status) — номер сигнала, который прикончил процесс (от 1 до 64). Вызывать только если WIFSIGNALED=true.
    - WCOREDUMP(status) — true, если ядро успело записать файл дампа памяти (core dump) в момент падения процесса.
Группа В: Остановка и продолжение (Ctrl+Z, kill -STOP)
    - WIFSTOPPED(status) — true, если процесс был поставлен на паузу (например, по Ctrl+Z или сигналу SIGSTOP). 
        Работает только если в waitpid был передан флаг WUNTRACED.
    - WSTOPSIG(status) — номер сигнала, который приостановил процесс (19 для SIGSTOP или 20 для SIGTSTP).
    - WIFCONTINUED(status) — true, если приостановленный процесс был обратно разморожен (сигналом SIGCONT).

Под капотом:
- WIFEXITED - Равны ли нулю нижние 7 бит - (((status) & 0x007F) == 0)
    Если сигналов не было, в конце числа гарантированно стоит 0.
- WEXITSTATUS - Вырезает второй байт и двигает в начало - (((status) & 0xFF00) >> 8)
    Маска 0xFF00 обнуляет всё, кроме бит 8–15. Сдвиг >> 8 превращает, например, 768 обратно в 3.
- WIFSIGNALED - Есть ли сигнал в нижних битах - (((status) & 0x007F) != 0 && ((status) & 0x007F) != 0x007F)
    Проверяет, что в конце числа записан не 0 (не exit) и не 0x7F (не маркер паузы).
- WTERMSIG - Вырезает нижние 7 бит - ((status) & 0x007F)
    Маска 0x007F (в бинарном виде 01111111) оставляет только номер сигнала (от 1 до 127).
- WCOREDUMP - Проверяет 8-й бит (флаг дампа) - (((status) & 0x0080) != 0)
    Маска 0x0080 (в бинарном виде 10000000) проверяет ровно один этот бит. Если он взведен — дамп записан.
- WIFSTOPPED - Ищет маркер паузы 0x7F в конце - (((status) & 0x00FF) == 0x007F)
    Если процесс на паузе, ядро жестко прописывает в младший байт число 127 (0x7F).
- WSTOPSIG - Достает код сигнала паузы - (((status) & 0xFF00) >> 8)
    Номер сигнала остановки ядро прячет во второй байт, точно так же, как и код exit.


МАРКЕР ПАУЗЫ
Когда в дочерний процесс прилетает SIGSTOP (нажали Ctrl + Z), ядро перехватывает событие, останавливает ребенка 
    и тут же выбрасывает родителю статус, содержащий этот маркер паузы.
    0x7f - магический маркер, означает - «Процесс ЖИВ, но остановлен!»
При получении SIGSTOP ядро пакует сигнал так:
    - В младший байт (биты 0-7) оно записывает маркер паузы: 0x7F.
    - Во второй байт (биты 8-15) оно записывает номер сигнала, который вызвал эту паузу: 19.
ВАЖНО!
Родитель увидит Маркер паузы только если вызвал waitpid(child, &status, WUNTRACED).
Обычный wait() не сработает.


СБРОС ДАМПА ЯДРА (Core Dump)
Три условия должны сработать:
1) 1. Ограничение размера (ulimit)
    Включить: > ulimit -c unlimited (разрешить дампы любого размера)
2) 2. Тот самый /proc/sys/kernel/core_pattern
    2.1) Прямая запись (Просто имя файла или путь). Если там core, то в папку программы.
        Можно настроить маску: /tmp/core-%e-%p (e - prog_name, p - PID)
    2.2) Перенаправление через Пайп (|). Перенаправляет дамп демону systemd-coredump или другому.
3) Права доступа и SUID-безопасность (suid_dumpable)
    Запускалась от обычного юзера, но повысила свои права. Либо это системная служба SUID. Дамп запрещен.

execve() - системный вызов «полного стирания памяти».
    Ядро полностью уничтожает весь текущий код процесса и загружает вместо него совершенно новую программу с диска.

    - filename (/bin/cat) — точный путь к исполняемому файлу на диске. Ядро открывает этот файл, проверяет права 
        и загружает его в память процесса.
    - argv[] (массив аргументов, например ["cat", "/dev/urandom"]) — этот массив передается новой программе.
    - envp[] — массив переменных окружения (например, PATH, USER), чтобы новая программа знала контекст системы.

Пример - запуск команд крона:
> execve("/bin/sh", ["/bin/sh", "-c", "ваша_команда"], environ);

clone()

тот же fork(), но со встроенным «пультом управления» в виде флагов (Bitmasks).
Передаем ядру Linux набор флагов, которые хотим.

> clone(..., SIGCHLD, ...); - это и есть fork. Передаем сигнал, который ждем от потомка (здесь SIGCHLD), но м и другой.

> clone(..., CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND, ...); - создание потока
    - CLONE_VM - у нас общая вирт.память
    - CLONE_FS - общая таблица файловых дескрипторов
    - CLONE_FILES - Общая информация о файловой системе (текущая рабочая директория). При cd меняется у обоих.
    - CLONE_SIGHAND - Общие обработчики сигналов.

dup2

Синтаксис: dup2(oldfd, newfd)

Атомарно копирует файловый дескриптор.
Заставляет дескриптор с номером newfd указывать на тот же самый открытый файл (или сокет, или пайп), на который 
    сейчас указывает oldfd.

Это главный инструмент для перенаправления ввода-вывода (стримов) в Linux. 
Именно с его помощью командная оболочка (bash) реализует конструкции вроде ls > file.txt или 2>&1.

Что под капотом:
1) Проверка newfd - 
    Если дескриптор newfd уже был открыт процессом, ядро автоматически и молча закрывает его 
    (вызывается внутренний close(newfd)).
2) Перенаправление - 
    В таблице дескрипторов процесса ячейка newfd начинает указывать на ту же самую запись в системной таблице 
    открытых файлов (File Description), на которую указывает oldfd.
3) Общий указатель - 
    Теперь у oldfd и newfd становится общая позиция чтения/записи (offset) и общие системные флаги. 
    Если сдвинуть указатель (например, через lseek или прочитав данные) в oldfd, он сдвинется и в newfd.

Пример 1:
    int oldfd = open("output.txt",...); // типа получили 3
    dup2(oldfd,1); // stdout = oldfd, т.е. вывод подключился к файлу output.txt
    close(oldfd); // больше не нужен
    exec(); // запустили

Пример 2:
    > ./script.sh > log.txt 2>&1 // в 1 сейчас log.txt
        1) > log.txt — заставляет дескриптор 1 (вывод) указывать на файл log.txt
        2) 2>&1 — под капотом вызывает dup2(1, 2)


//--------------------------------------
JOB CONTROL (управление задачами)

background(bg)-foreground(fg)

Фоновый процесс (background process) — это «полудемон». Работает как демон, но зависит от терминала и есть общий вывод.
    Также есть доступ к stdin (будет STOP), у демона вообще нет доступа к терминалу.



> jobs - список процессов в сессии шелла (номера можно будет подставлять в %N)ы
> jobs -l - список процессов в сессии шелла (выведет PID)
> Ctrl+Z - СТОП текущей команды (status: T)
> (sleep 100) & - запустить команду сразу в bg
> bg %N - продолжить команду прямо в bg (SIGCONT)
> fg %N - вернуть процесс на передний план (шелл сделает tcsetpgrp() - отдаст терминал процессу)
> kill -STOP %N - остановить процесс в bg (status: T)
> kill -STOP <PID> - или так
> kill %1 - убить
> kill -9 %1 - убить надежно (если кобенится и помирать не хочет)
> kill <PID> - убить


Под капотом:
1. Передний план (Foreground)
    - bash делает fork() и execve(), создавая новый процесс.
    - bash делает системный вызов tcsetpgrp(0, child_pgid). Группа процессов становится активной группой терминала.
    - bash делает вызов waitpid() и полностью блокируется (засыпает).
    - процесс на переднем плане монопольно владеет терминалом (/dev/pts/X), нажатие клавиши пересылает в stdin процесса.
    - Нажатие Ctrl+C - ядро отправляет SIGINT активной группе, процесс погибает, bash забирает управление обратно.
2. Фоновый режим (Background) через &
    - bash делает fork() и execve(), создавая новый процесс.
    - bash НЕ вызывает tcsetpgrp(). Активной группой терминала остается сам bash.
    - bash НЕ вызывает блокирующий waitpid(). Сразу выводит на экран номер задачи и PID, и возвращает управление.
    - фоновый процесс сохраняет дескриптор терминала на вывод - может писать в терминал.
    - Фоновому процессу запрещено читать с клавиатуры - при попытке читать из stdin, мгновенный SIGTTIN (Stopped)

kill - программа отправки сигналов процессам

> kill <PID> - отправить SIGTERM (15) - «все сохрани и самовыпились плиз», можно игнорить.
> kill -9 <PID> - отправить SIGKILL - «ядро, убей процесс», никак не проигнорить, до процесса даже не дойдет.

> kill -STOP %N - для jobs

TTY (teletype, teleprinter, teletypewriter)

Устройство (терминальное), которое обеспечивает работу консоли.
Два компонента:
- Драйвер устройства. Отвечает за доставку ввода с клавиатуры в программу и за отображение вывода программы на экран.
- TTY Line Discipline (дисциплина линии). Интерфейс доступа к драйверу, привносит доп. логику в TTY устройство.

Строение TTY устройства:

             [user process]
                    ▲
 ┌ . . . . . . . . . . . . . . . . . . ┐
 :                  ▼                  :
 :        ┌───────────────────┐        :
 :        │  read and write   │        :
 :        │     functions     │        :
 :        └───────────────────┘        :
 :             │         ▲             :
 :             ▼         │             :
 :        ┌───────────────────┐        :
 :        │   terminal line   │        :  kernel
 :        │    discipline     │        :
 :        └───────────────────┘        :
 :             │         ▲             :
 :             ▼         │             :
 :        ┌───────────────────┐        :
 :        │  terminal device  │        :
 :        │      driver       │        :
 :        └───────────────────┘        :
 :                  ▲                  :
 └ . . . . . . . . . . . . . . . . . . ┘
                    ▼
              [actual device]


Типы TTY-устройств:
1) Виртуальные консоли (tty1, tty2 и др.): Текстовые экраны самого компьютера, которые открываются по комбинациям клавиш.
    Это самые трушные консоли - напрямую из ядра/железа.
2) Псевдотерминалы (pts): Вирт. аналоги для графических окон терминала, утилит tmux или удаленных подключений по SSH.
    Основные терминалы, которые используются. Присоединяются к процессу и дают текстовый ввод/вывод.
3) Последовательные порты (ttyS): Разъемы для старых устройств или отладки микроконтроллеров.
    Работа с железными портами

---
PTY состоит из двух частей (вирт.устройств):
- PTY master (PTM / Pseudo-Terminal Master / Управляющий):
    Он создается внутри процесса (например, утилиты socat или графического эмулятора терминала). Юзер его не видит.
- PTY slave (PTS / Pseudo-Terminal Slave / Ведомый): 
    То самое устройство в папке /dev/pts/X, которое мы видим на диске. Оно ведет себя как полноценный терминал, 
    к которому можно подключить программу (cat, microcom, или ваш C++ сервер)


       ПОТОК ДАННЫХ В ЯДРЕ LINUX (Двусторонний мост)
       
 [ Программа-клиент ]                   [ C++ сервер ]
          │                                    │
          ▼                                    ▼
  /dev/pts/7 (Slave)                 /dev/pts/6 (Slave)
          │                                    │
          ▼                                    ▼
  /dev/ptmx (Master 2)  ◄──socat──►  /dev/ptmx (Master 1)


Или так:
    [Второй терминал] ──> ~/client_dev ──> [ PTY 2 ]
                                             │  ▲  (Виртуальный кабель, созданный утилитой socat)
                                             ▼  │   
    [ C++ программа ] ──> ~/modem_dev  ──> [ PTY 1 ]

Утилита socat (SOcket CAT)
    Её задача — взять поток данных из одного места (левый аргумент) и перенаправить его в другое (правый аргумент).
    Работает как двусторонний мост.

Команда состоит строго из двух адресов: Адрес 1 и Адрес 2:
    socat [опции]  [Адрес 1]  [Адрес 2]

Адрес бывает: одиночный (single) и bi-address (двухкомпонентный адрес: single-address!!single-address).
Single-адрес состоит из полей: ТИП_УСТРОЙСТВА,опция1,опция2,опция3
    - PTY — это ключевое слово (тип адреса). Оно говорит: «Создай виртуальный терминал».
    - link=..., raw, echo=0 — это модификаторы (опции) для этого конкретного PTY-устройства. Они настраивают его 
        поведение: имя ссылки, режим передачи байтов и отключение эхо-ответа.
Bi-адрес - нужен когда нужно получать данные из одного места (читать из файла), а отправлять их в другое (в сокет UDP).
    Записывается через: <single-address> или <single-address>!!<single-address>
    > socat - OPEN:/tmp/input.txt!!UDP:127.0.0.1:5000

Установка
> sudo apt update && sudo apt install -y socat

Прокинуть мост меж двумя вирт.портами:
- через файл-симлинк в домашней директории:
    > socat -d -d PTY,link=$HOME/modem_dev,raw,echo=0 PTY,link=$HOME/client_dev,raw,echo=0
- без файлов, только соединение двух pty (флаги пишем строго после raw, который сам ставит кучу флагов):
    > socat -d2 PTY,raw,echo=0 PTY,raw,echo=0
    > socat -d2 PTY,raw,echo=0,icanon=0,onlcr=0 PTY,raw,echo=0,icanon=0,onlcr=0
- или даже так, через стандартные cin/cout (учесть, что все что будет cout, будет попадать в канал):
        EXEC - запускает скомпилированную C++ программу как дочерний процесс.
    > socat -d2 PTY,raw,echo=0 EXEC:/home/at_server_01,pty,raw,echo=0


Чтобы проверить канал:
    > cat ~/modem_dev
    > echo "AT" > ~/client_dev
Или:
    > cat /dev/pty/X

POSIX TERMIOS
    Интерфейс работы с асинхронными коммуникационными портами
    Высокоуровневый «пульт управления» для программиста.


+-------------------------------------------------------+
|  1. Ваше приложение (код на C/C++, Python и т.д.)     |
+-------------------------------------------------------+
                           |  (использует open, ioctl, tcsetattr)
                           v
+=======================================================+
|  2. Абстракция TERMIOS / Дисциплина линии (Line Disc  | <-- Это уровень ядра ОС
+=======================================================+
                           |
                           v
+-------------------------------------------------------+
|  3. TTY Core (Общий драйвер терминалов ядра)          |
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
|  4. Низкоуровневый драйвер конкретного устройства     | (например, драйвер FTDI или 8250 UART)
+-------------------------------------------------------+
                           |
                           v
+-------------------------------------------------------+
|  5. Физическая шина (USB, PCI, внутренняя шина SoC)   |
+-------------------------------------------------------+
                           |

+=======================================================+


Что конкретно находится между termios и железом?
1). Дисциплина линии (Line Discipline)
     Она обрабатывает поток байт (канонический режим, эхо-режим, обработка спецсимволов Ctrl+C итд)

2) TTY Core (Ядро подсистемы терминалов)
    Принимает поток данных от дисциплины линии и перенаправляет его в нужный драйвер устройства.
    Управляет очередями чтения/записи.

3) Низкоуровневый драйвер устройства (Hardware Driver)
    программный мост, который знает, как общаться со специфическим контроллером.
    - Если чистый COM-порт, то работает стандартный драйвер последовательного порта (например, 8250.c в Linux). 
        Он напрямую пишет байты в регистры ввода-вывода микросхемы UART на материнской плате.
    - Если USB-переходник, здесь работает цепочка из драйвера конкретного чипа (например, ch341.c или ftdi_sio.c) и 
        стека драйверов USB. Драйвер упаковывает байты в USB-пакеты и отправляет их через USB-контроллер.


---
Основные типы асинхр. портов, которые есть в ОС (обычно в Linux и Unix-подобных системах), управляемых через termios:
1. Физические (аппаратные) порты - реальные контроллеры на материнской плате или платах расширения.
    - Стандартные COM-порты (UART 16550 и аналоги): Именуются как /dev/ttyS0, /dev/ttyS1 и т.д. 
        В архитектуре PC они жестко привязаны к прерываниям (IRQ) и базовым адресам (например, COM1 имеет адрес 0x3F8).
    - Встроенные UART-контроллеры (SoC): В одноплатных компьютерах (например, Raspberry Pi) или встроенных системах 
        порты обычно именуются как /dev/ttyAMA0, /dev/ttyAMA1 или /dev/ttyS0 (в зависимости от архитектуры процессора).

2. Виртуальные порты (через шину USB) - Современная замена стандартным COM-портам, подключаемая по USB.
    - Преобразователи USB-to-UART: Мосты на микросхемах FTDI, CH340, CP210x, PL2303. 
        В Linux они определяются как /dev/ttyUSB0, /dev/ttyUSB1
    - Устройства класса CDC-ACM: Виртуальные порты, создаваемые микроконтроллерами (Arduino, STM32, сотовые модемы итд), 
        которые общаются с системой напрямую по USB-протоколу. В системе они видны как /dev/ttyACM0, /dev/ttyACM1.

3. Беспроводные асинхронные порты
    - Bluetooth-порты (Профиль RFCOMM): Эмулируют стандартный последовательный кабель поверх радиоканала Bluetooth. 
        В Unix-системах они создают файлы устройств вида /dev/rfcomm0.

4. Псевдотерминалы (PTY)
    - чисто программные пары устройств («главный» и «подчиненный»), которые используют интерфейс termios для 
        межпроцессного взаимодействия. Они нужны для работы эмуляторов терминала (SSH, Telnet, xterm).
        Файлы устройств обычно находятся в директории /dev/pts/ (например, /dev/pts/0, /dev/pts/1).


Для termios не имеет значения физическая природа порта — будь то старый COM-порт или Bluetooth-соединение. 
    Программа открывает файл устройства через системный вызов open(), а затем настраивает асинхронный обмен с помощью 
    структуры struct termios и функций tcsetattr() / tcgetattr() по следующим ключевым параметрам:
1) Скорость передачи (Baud rate): от B1200 до B115200 (и выше для современных USB-мостов, например, B230400, B921600).
2) Формат кадра (Data bits): 5, 6, 7 или 8 бит данных (CS5, CS6, CS7, CS8).
3) Бит четности (Parity): контроль четности (PARENB), нечетности (PARODD) или его отсутствие.
4) Стоповые биты (Stop bits): 1 или 2 стоповых бита (CSTOPB).
5) Управление потоком (Flow Control): аппаратное (CRTSCTS) или программное (XON/XOFF — IXON/IXOFF).

Inode ("айнод", индексный дескриптор) — структура данных в файловых системах Unix и Linux, которая хранит все метаданные 
    о файле или каталоге, кроме его имени и содержимого.

Хранит:
    - Права доступа (кто может читать, писать или запускать файл).
    - Владелец и группа (ID пользователя и группы).
    - Размер файла в байтах.
    - Временные метки (время создания, изменения файла, изменения самого inode).
    - Количество жестких ссылок на этот файл.
    - Указатели на блоки данных (адреса на диске, где лежит реальное содержимое файла).

Временные метки:
    - ctime (change time) - последнее изменение inode
    - mtime (modification) - изменение содержимого
    - atime (access) - последний доступ (есть заморочь с просмотром файлов - когда каждому меняют atime, можно отключить.)

Айнод не знает, где лежат жесткие ссылки на него! И под какими именами. В этом смысле он слепой.
Поиск всегда идет от каталогов к inode.
Можно найти все остальные ссылки так: > find / -inum 4567 2>/dev/null

---
Жесткая ссылка (hard link):
    - еще одно имя для одного inode
    - данные останутся, пока есть хоть одна hl
    - не могут ссылаться на папки (защита от зацикливания системы)
    - работают в пределах одного диска/раздела (в каждом диске/разделе около 1% размечено под айноды)
    - не занимает место (0 байт) - это просто имя в таблице каталога

        [ Каталог А ] ---> "file_one.txt" ---\
                                              ---> [ Inode №12345 ] ---> [ Блоки данных на диске ]
        [ Каталог Б ] ---> "archive.log"  ---/

---
Мягкая ссылка (soft link):
    - отдельный файл со своим inode, хранящий текстовый путь
    - при удалении оригинала, сломается - хранит путь в никуда
    - можно ссылаться на папки
    - можно ссылаться на другой диск
    - размер равен количеству символов в пути ("/tmp/f" = 6 байт)

        [ Таблица каталога ]
        "ссылка.lnk" ----> [ Inode №99999 ] 
                                 |
                                 v
                            (Хранит текст: "/home/user/оригинал.txt")
                                 |
                                 |  (ОС читает этот путь и ищет его снова в таблице каталога)
                                 v
        "оригинал.txt" --> [ Inode №12345 ] ---> [ Реальные данные на диске ]

---
Создание ссылок:
    ln original.txt hard_link.txt      # Жесткая ссылка
    ln -s original.txt sym_link.txt    # Мягкая (символическая) ссылка

---
Команда просмотра: > ls -li
17631 -rw-r--r-- 3 admin2 admin2    7 Sep 15 13:11  hard2.txt      # три жесткие ссылки на один inode
17631 -rw-r--r-- 3 admin2 admin2    7 Sep 15 13:11  hard3.txt      # (цифра после прав - это кол-во ссылок)
17631 -rw-r--r-- 3 admin2 admin2    7 Sep 15 13:11  hard_link.txt  #
17658 lrwxrwxrwx 2 admin2 admin2   13 Sep 15 13:24  soft1.txt -> hard_link.txt     # три soft link на три хард
17662 lrwxrwxrwx 1 admin2 admin2    9 Sep 15 13:24  soft2.txt -> hard2.txt         # (разные айноды)
17665 lrwxrwxrwx 1 admin2 admin2   13 Sep 15 13:24  soft3.txt -> hard_link.txt     # ("l" - значит "soft Link")
17658 lrwxrwxrwx 2 admin2 admin2   13 Sep 15 13:24  soft_hard.txt -> hard_link.txt # хард-ссылка на софт-ссылку

Для директорий количество ссылок считается по-другому - при создании внутри нее сразу создается 2 hardlink:
    "." (точка) - ссылка на этот же каталог
    ".." (две точки) - ссылка на parent каталог

/home/user/
   │
   └── parent/  [ Счетчик ссылок = 3 ] <──────────────────────────┐
          │                                                       │
          ├── .  (указывает на саму себя: parent)                 │
          │                                                       │
          └── child/  [ Счетчик ссылок = 2 ]                      │
                 │                                                │
                 ├── .  (указывает на саму себя: child)           │
                 └── .. (указывает на родителя: parent) ──────────┘

Архитектура данных (немного про flock):

 [Процесс (task_struct)]
          │
          ▼
   [File Descriptor (fd)] ──► [File Description (struct file)] ──► [struct inode]
                                    │                                    │
                                    ▼                                    ▼
                             (Хранит флаги                    (Хранит список локов
                              чтения/записи)                  fl_block -> lock_1 -> lock_2)
где:
- struct file (описание открытого файла): Создается каждый раз при вызове open(). 
    Если один процесс сделал open() дважды, у него будет две разные struct file.
- struct inode (индексный дескриптор в памяти): Существует в ядре в единственном экземпляре для конкретного файла 
    на диске, сколько бы раз его ни открывали.
- struct file_lock: Это структура, которую ядро создает специально, когда вы вызываете flock().

#DIGDEEP - есть заморочь: блокировки физически лежат в struct inode, но логически принадлежат struct file.
    Дойду до работы с папками/файлами - поковыряю.

unlink()
    удаляет имя файла (ссылку) из конкретной директории.
    Сам inode остается. К файлу больше обратиться нельзя.
    Уменьшает колич.ссылок на inode на 1. 
    Если count=0, то ядро проверяет ОТКРЫТ ЛИ ЭТОТ ФАЙЛ КАКИМ-ТО ПРОЦЕССОМ (счетчик open file descriptors)???
    Если НЕТ, то удаляет окончательно.
    Хитрая схемка - поэтому даже если файл удален во время работы программы, в самой app к нему доступ есть.


//--------------------------------------
Утилита find()

1) Базовый синтаксис: 
    find [где_искать] [критерии_поиска] [что_сделать]
    - где_искать — путь к директории (например, . — текущая, / — весь диск, /var/log). 
        Можно указать несколько путей через пробел. Если не указать, поиск пойдет в текущей директории.
    - критерии (тесты) — фильтры, по которым отбираются файлы.
    - что_сделать (действия) — что выполнить с найденным. По умолчанию файлы просто выводятся на экран (-print).

Ограничение глубины поиска: -maxdepth
    # Искать файлы .sh ТОЛЬКО в /usr/bin, не заходя в подпапки
    > find /usr/bin -maxdepth 1 -type f -name "*.sh"


2) Главные критерии поиска (Фильтры)
    - по имени файла С учетом регистра: <-name "шаблон">. Шаблон пишется в кавычках.
    - по имени файла БЕЗ учета регистра: <-iname "шаблон"> (инвариантно).
    - по типу объекта: <-type тип>. Типы: f — обычный файл, d — директория, l — символическая ссылка
    - По размеру: <-size SIZE> (size: +100M - строго больше 100Мб, -10k - строго меньше 10кб)
    - По времени изменений: Время измеряется либо в днях (mtime, atime, ctime), либо в минутах (mmin, amin, cmin)
        - mtime / mmin — изменение содержимого файла (modification). Пример: -mtime -2 - измененные за посл.2 дня
        - atime / amin — последнее чтение/открытие файла (access). Пример: -amin +30 - доступ более 30 мин назад
        - ctime / cmin — изменение метаданных или статуса (change, например, смена прав или владельца).
    - По правам и владельцам:
        - -user имя_или_id — файлы, принадлежащие конкретному пользователю.
        - -group группа — файлы конкретной группы.
        - -perm 644 — файлы с точными правами доступа 644 (rw-r--r--).
        - -perm /a+x или -perm /111 — файлы, у которых есть хоть какой-то флаг исполняемости (executable).

3) Логические операторы (Комбинирование)
    - И (AND): Выполняется по умолчанию, если условия написаны подряд. Также можно указать явно через -a
    - ИЛИ (OR): Указывается как -o.
    - НЕ (NOT): Указывается как ! или -not.
    - Группировка: Используются кругл скобки \( ... \). Экранирование косой чертой обязательно (шелл перехватит скобки)

4) Действия над найденным (Что сделать)
    - -print — просто вывести пути на экран (действие по умолчанию).
    - -delete — автоматически удалить все найденные файлы (использовать с осторожностью!).
    - -ls — вывести подробную информацию о файлах (аналог команды ls -dils).
    - -exec команда {} \; — выполнить внешнюю команду для каждого файла.
        {} — это подстановка пути найденного файла.
        \; — обязательный признак окончания команды.
    - -exec команда {} + — более быстрая вариация. 
        Собирает много найденных файлов в одну строчку аргументов и вызывает команду один раз (работает как xargs).

5) Практические примеры на все случаи жизни
Поиск документов и медиа:
    # Найти все файлы .log в папке /var/log
    > find /var/log -type f -name "*.log"

    # Найти картинки .jpg или .png в текущей папке (использование OR)
    > find . -type f \( -name "*.jpg" -o -name "*.png" \)

Очистка места и поиск «тяжелых» файлов
    # Найти на всем диске файлы крупнее 1 Гигабайта
    > find / -type f -size +1G 2>/dev/null

    # Найти пустые папки в домашней директории и удалить их
    > find ~/ -type d -empty -delete

Безопасность и аудит
    # Найти в /var/www файлы, у которых права доступа 777 (опасно!)
    > find /var/www -type f -perm 777

    # Найти файлы, принадлежащие удаленному пользователю (без владельца)
    > find / -nouser

Массовая работа с файлами (-exec)
    # Найти все файлы .txt в домашней папке и изменить им права на 644
    > find ~ -type f -name "*.txt" -exec chmod 644 {} \;

    # Найти логи старше 30 дней и удалить их
    > find /var/log -type f -name "*.log" -mtime +30 -exec rm {} \;

    # Быстрый поиск текста "error" внутри всех .conf файлов в /etc
    > find /etc -type f -name "*.conf" -exec grep -H "error" {} +

Поиск по всей WSL (начиная от корня /), исключая Windows-диски:
    > find / -path "/mnt" -prune -o -type f -name "ваш_шаблон" -print
        (-path "/mnt" -prune — главная магия. find натыкается на путь /mnt, обрезает его (prune) и не спускается внутрь)

ANSI-коды (последовательности, управляющие коды, ANSI code)

Шаблон: [Маркер начала] + [Что именно делать / Параметры] + [Конечный флаг]

Шаблон: \e[ + [Числовые параметры через точку с запятой] + [Буква-команда]
    Вместо \e может быть: \033, ESC
    
CSI — Control Sequence Introducer - это последовательность: \033[
    Знак того, что следом идут параметры команды

Основные команды:
1. Управление курсором (Перемещение по экрану)
    \e[Y;XH — Переместить курсор в строку Y и столбец X
    \e[A, \e[B, \e[C, \e[D — Сдвинуть курсор на одну позицию Вверх, Вниз, Вправо, Влево соответственно.
    
2. Очистка экрана и строк
    \e[2J — Очистить весь экран (буква J отвечает за стирание экрана).
    \e[K — Очистить строку от текущего положения курсора и до самого конца (буква K отвечает за стирание строки).

3. Раскраска и стили текста (Команда m)
    Буква m в конце означает SGR (Select Graphic Rendition — выбор графического оформления). Параметры - коды цветов.
    \e[0m — Сбросить всё. Возвращает стандартный цвет терминала, убирает жирность и подчеркивание. 
        Программисты называют это «Reset». Всегда отправлять этот код в конце строки!
    \e[1m — Жирный текст (Bold) или повышенная яркость.
    \e[4m — Подчеркнутый текст.

    Базовые цвета (16 цветов) - Палитра делится на цвет текста (диапазон 30–37) и цвет фона (диапазон 40–47):
        31 — Красный текст, 41 — Красный фон
        32 — Зеленый текст, 42 — Зеленый фон
        34 — Синий текст, 44 — Синий фон
    
    Расширенная палитра (256 цветов — тот самый xterm-256color):
        \e[38;5;[НОМЕР]m — Цвет текста (от 0 до 255)
        \e[48;5;[НОМЕР]m — Цвет фона (от 0 до 255)

    Пример: printf "\e[38;5;208mОранжевый текст\e[0m" (208 — это чистый оранжевый цвет в таблице xterm)

Пример: \e[31m
Что делает терминал:
    \e — «Внимание, терминал, это секретный приказ!» (Символ Escape)
    [ — «Сейчас передам параметры» (Квадратная скобка)
    31 — «Параметр номер 31» (В стандарте ANSI число 31 означает красный цвет текста)
    m — «Конец приказа. Примени настройки стиля!» (Финальный флаг)
Получив эту команду, терминал ничего не выводит на экран, а переключает текст на красный и ждет вывод дальше.

Очень наглядный пример: > printf '\e[2J\e[5;10H\e[1;31mВНИМАНИЕ!\e[0m\e[5;21H\e[4;32mСистема работает исправно!\e[0m\n\n'
    \e[2J — Терминал полностью очистился.
    \e[5;10H — Курсор прыгнул на 5-ю строку, 10-й столбец.
    \e[1;31m — Включился жирный красный цвет.
    Напечаталось слово ВНИМАНИЕ:.
    \e[0m — Цвета сбросились в стандартные.
    \e[5;21H — Курсор прыгнул чуть правее в той же строке (на 21-й столбец).
    \e[4;32m — Включился подчеркнутый зеленый цвет.
    Напечаталась фраза Система работает исправно!.
    \e[0m — Финальный сброс стилей.

============================== ПРОСТРАНСТВО WINDOWS ==============================

  +-----------------------+
  |  Физическая клавиша   |
  |      [Page Down]      |
  +-----------+-----------+
              | (Нажатие генерирует Windows-код: VK_NEXT / 0x22)
              v

  |   3. Конвертирует 0x22 -> в ANSI-последовательность: "\e[6~"                |
  +-----------------------------------+-----------------------------------------+
                                      | (Передает строку "\e[6~" дальше)
                                      v
  +-----------------------------------------------------------------------------+
  | ConPTY (Windows Pseudo Console)                                             |
  |   Секретный мост-транслятор. Берет байты из Windows и прокидывает их        |
  |   через границу виртуализации прямиком в ядро WSL.                          |
  +-----------------------------------+-----------------------------------------+
                                      |
============================== ПРОСТРАНСТВО LINUX (WSL) ==========================
                                      |
                                      | (Байты влетают в виртуальный порт)
                                      v
  +-----------------------------------------------------------------------------+
  | Виртуальный файл устройства ввода (/dev/pts/0)                              |
  |                                                                             |
  |   Поток байтов [ \e ] [ [ ] [ 6 ] [ ~ ] становится доступен для чтения      |
  |   внутри Linux в Raw-режиме (без фильтрации ядром).                         |
  +-----------------------------------+-----------------------------------------+
                                      |
                                      | (Программа считывает поток байт)
                                      v
  +-----------------------------------------------------------------------------+
  | ПРОГРАММА НА NCURSES (например, htop)                                       |
  |                                                                             |
  |   1. Считывает из /dev/pts/0 байты: "\e[6~"                                 |
  |   2. Смотрит на переменную среды: TERM = "xterm-256color"                   |
  |   3. Идет в базу TERMINFO -> открывает файл "/usr/share/terminfo/x/..."     |
  |   4. Находит совпадение: строка "\e[6~" == клавиша "След. страница"         |
  |   5. Выполняет действие: прокручивает интерфейс вниз!                       |
  +-----------------------------------------------------------------------------+

NCURSES (библиотека работы с терминалом в режиме альтернативного экрана)

Берет терминал из TERM.

Базовые принципы:
1) ИНИЦИАЛИЗАЦИЯ - при вызове функции initscr(), делает системный вызов ядра для переключения терминала в raw mode 
    (или cbreak) и отправляет ANSI-код альтернативного экрана \e[?1049h
2) ВВОД - при вызове getch(), библиотека делает парсинг ANSI-последовательностей. Прилетевшая сырая строка \e[6~, 
    будет сверена со справочником terminfo и ncurses вернет понятное число-константу KEY_NPAGE (Page Down).
3) ВЫВОД - высокоуровневые команды на отрисовку окон, рамок или текста (например, printw()), превращаются 
    в "бутерброды" ANSI-кодов (цвета, координаты, стили). И появляются на экране.

---
Установка:
    sudo apt update
    sudo apt install libncurses5-dev libncursesw5-dev

При компиляции необходимо передавать флаг -lncurses (или -lncursesw для поддержки UTF-8)

Использует библиотеки:
- libtinfo — выясняет правила перевода (тот самый terminfo, для xterm-256color итд)
- libncursesw — собсно ядро, собирает всё вместе, оформляет в широкие символы UTF-8 и рисует интерфейс на экране.

Анатомия базового UI в ncurses

1) Окна - основа. Стандартный экран уже имеет переменную stdscr (условно это наш "черновик").
    Также есть - curscr - текущий экран ("чистовик").
    Чтобы использовать эти переменные нужно вызвать: initscr(). А в конце обязательно - endwin().
        Между ними нельзя юзать stdout, либо ДО, либо ПОСЛЕ. Сломает вывод.

2) Обновление экрана: refresh, wrefresh
    Структура WINDOW хранит: высоту, ширину, позицию и контекст. При записи в Окно, контекст меняется.
    Но чтобы это отобразилось нужно вызвать: refresh() или wrefresh().
    При вызове refresh, черновик сравнивается с чистовиком и отправляются только те ansi-коды, которые изменились!
    Под капотом делается 2 шага: 
        - wnoutrefresh() - сравнение stdscr с curscr.
        - doupdate() - физическая отправка анси-кодов в терминал.
    wrefresh(WINDOW*) - черновик►чистовик, но для созданного юзером окна (принимает указатель).
    Собсно, refresh - это эквивалент wrefresh(stdscr).

    --- если у нас 3 окна и надо обновить их все, то только так:
        // 1. Обсчитываем черновики
        wnoutrefresh(header_win);
        wnoutrefresh(process_win);
        wnoutrefresh(footer_win);

        // 2. И только ОДИН раз физически выплевываем все ANSI-коды в терминал
        doupdate(); 

3) Создание новых окон (subwin, newwin) и удаление (delwin)
    WINDOW* win2 = subwin(WINDOW*, height, width, start_y, start_x); // высота, ширина, левый угол (строка, столбец)
    WINDOW *win1 = newwin(height, width, start_y, start_x);
    delwin(WINDOW* win); 

    Subwin - это подокно. Наследует свойства родителя (но можно позже менять независимо).
        Общий симв.массив с parent - экономит память. Но parent может записать туда свой контекст (как это выглядит??)
    newwin - новое окно. Полностью свой симв.массив.
    delwin - обязательно удаляем окно при выходе из контекста (либа на Сях, это malloc, иначе получим утечку).
        Можно не удалять только если прям перед exit().

4) Запись в окно и чтение из окна (printw, scanw, addch, getch, их аналоги: wprintw, wscanw, waddch, wgetch)
    4.1) Магия префиксов w, m и mv
        





Экран представляет собой координатную сетку, где (0,0) — это левый верхний угол. вначале строка Y, потом столбец X.

Управление координатами и вывод
    - move(y, x); — переместить курсор в позицию.
    - printw("текст"); — аналог printf, выводит текст в текущей позиции курсора.
    - mvprintw(y, x, "формат", ...); — объединяет перемещение и вывод (самая частая функция).
    - refresh(); — отправляет буфер на отрисовку. Делайте это после изменений.

Работа с цветом
    Чтобы включить цвета, нужно вызвать функцию start_color(). Цвета работают через «пары» (цвет текста + цвет фона).
        start_color();
        // Создаем пару №1: зеленый текст на черном фоне
        init_pair(1, COLOR_GREEN, COLOR_BLACK); 

        // Включаем пару №1 для последующего вывода
        attron(COLOR_PAIR(1)); 
        mvprintw(2, 5, "Этот текст будет зеленым!");
        attroff(COLOR_PAIR(1)); // Выключаем пару

Создание базовых UI-элементов (Окна и Рамки)
    приложение делят на окна (WINDOW). У каждого окна своя независимая система координат.
