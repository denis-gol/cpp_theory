## ⚠️ Недостающие ключевые темы для 100% освоения CMake + Ninja

### 1. Глубокий экспорт таргетов (Магия `find_package`)
* **Суть**: Недостаточно просто собрать «полуфабрикат» (SDK), нужно заставить CMake автоматически генерировать конфигурационные файлы, которые сторонний разработчик сможет подключить одной строчкой.
* **Ключевые команды**: `install(EXPORT ...)` и `export(EXPORT ...)`.
* **Что происходит**: CMake берет информацию о вашем таргете, включая его `$<INSTALL_INTERFACE:include>` и бинарники, и упаковывает в служебный файл `MyLibConfig.cmake`. Без этого чужой `find_package(MyLib)` просто выдаст ошибку.

### 2. Рантайм-зависимости и проблема «Ада DLL» (RPATH vs DLL Copying)
* **Суть**: Если скомпилировать приложение с динамической библиотекой (`SHARED`), оно успешно соберется в Ninja, но упадет при старте с ошибкой *«DLL/со-файл не найден»*, так как операционная система не знает, где искать бинарник библиотеки.
* **Решение в Linux (RPATH)**: Использование свойств таргета `BUILD_RPATH` (путь к `.so` во время разработки) и `INSTALL_RPATH` (путь к `.so` в системных папках после установки). Жестко зашивает пути поиска прямо в заголовок эльф-файла (`ELF`).
* **Решение в Windows (Копирование)**: Автоматизация переноса `.dll` в папку к `.exe` файлу через кастомные команды сборщика `add_custom_command(TARGET ... POST_BUILD)` или современный механизм CMake `file(GET_RUNTIME_DEPENDENCIES)`.

### 3. Автоматизация тестирования через CTest
* **Суть**: Встроенный в CMake кроссплатформенный фреймворк для управления юнит-тестами. Он связывает сборщик Ninja с вашим кодом тестирования (GTest, Catch2, Doctest).
* **Ключевые команды**: `enable_testing()` в корневом файле и `add_test(NAME ... COMMAND ...)` для каждого тестового бинарника.
* **Интеграция с Ninja**: После настройки в консоли достаточно написать `ninja test` или запустить утилиту `ctest` из папки сборки. Ninja сам проверит актуальность кода, пересоберет изменившиеся тесты и выведет красивый лог прохождения (Passed/Failed).

### 4. Генерация заголовочных файлов конфигурации (`configure_file`)
* **Суть**: Передача метаданных и настроек из CMake (переменных сборки) напрямую внутрь исходного кода C++ перед началом компиляции.
* **Ключевая команда**: `configure_file(config.h.in config.h)`.
* **Принцип работы**: Вы создаете шаблон `config.h.in`, где пишете, например: `#define VERSION "@PROJECT_VERSION@"`. На этапе конфигурации CMake считывает этот файл, подставляет реальную версию и записывает готовый `config.h` в папку `${CMAKE_CURRENT_BINARY_DIR}`. Только после этого Ninja начинает сборку.

### 5. Архитектурный компромисс: `FetchContent` против `find_package`
* **Суть**: Понимание, когда какую стратегию управления зависимостями применять в реальном продакшене.
* **`FetchContent` (Сборка из сырцов)**: Скачивает код зависимости из Git на этапе конфигурации. 
    * *Плюсы*: Стопроцентная переносимость. Проект соберется на любой машине, так как все исходники прилетят сами.
    * *Минусы*: Тотальный удар по инкрементальности. Каждый раз при очистке папки `build` тяжелые сторонние либы будут перекомпилироваться заново, увеличивая время работы Ninja.
* **`find_package` (Поиск готового полуфабриката)**: Ищет уже скомпилированную библиотеку на диске или в системе.
    * *Плюсы*: Мгновенная сборка. Ninja просто линкует готовый бинарник за доли секунды.
    * *Минусы*: Проект не запустится на машине другого разработчика, пока он вручную не установит эту зависимость через систему или пакетный менеджер (vcpkg / Conan).

### 6. Тонкая защита стандартов через `target_compile_features`
* **Суть**: Более гибкая замена глобальным флагам `set(CMAKE_CXX_STANDARD 20)`. Защита проекта на основе конкретных возможностей компилятора, а не абстрактной цифры стандарта.
* **Ключевая команда**: `target_compile_features(my_target PRIVATE cxx_std_20)`.
* **Почему это важно**: Позволяет затребовать у компилятора поддержку конкретной фичи (например, `cxx_constexpr` или `cxx_auto_type`). CMake сам проанализирует базу данных компилятора, поймет, какой флаг ему скормить (`-std=c++20` для GCC или `/std:c++20` для MSVC), и уронит конфигурацию, если компилятор физически не обучен этой фиче.

### 7. Справочник легаси-команд (Для чтения чужого старого кода)
* **Суть**: Способность читать и рефакторить старый CMake-код (до версии 3.0), где правила Modern CMake полностью нарушались в пользу глобальных переменных.
* **Таблица соответствия старых команд новым**:

    | Устаревшая глобальная команда (Легаси) | Современный аналог (Modern CMake Таргеты) |
    | :--- | :--- |
    | `include_directories(/path)` | `target_include_directories(target PRIVATE /path)` |
    | `add_definitions(-DDEBUG)` | `target_compile_definitions(target PRIVATE DEBUG)` |
    | `link_libraries(lib_name)` | `target_link_libraries(target PRIVATE lib_name)` |
    | `link_directories(/path)` | *Запрещено.* Пути передаются напрямую через таргеты-зависимости. |

Исторически единый стандартный сборщик отсутствует.

1. Архитектурные уровни: Системы сборки vs Генераторы проектов
    - Низкий уровень: Системы сборки (Build Systems / Build Tools)
        - Напрямую вызывают компилятор (g++, clang, msvc), передают ему флаги оптимизации, пути к инклудам,
            следят за тем, какие файлы изменились, чтобы пересобирать только их (инкрементальная сборка).
        - Читают конфигурационные файлы с жестко прописанными командами для конкретной ОС и терминала.
    - Высокий уровень: Генераторы проектов (Meta-Build Systems)
        - Сами код не компилируют. Они выступают надстройкой, которая анализирует кроссплатформенный манифест проекта 
            и генерирует конфигурационные файлы для низкоуровневых систем сборки под конкретную ОС.

2. Сравнительный анализ основных систем сборки (Низкий уровень)
    - Make (GNU Make)
        - Файл конфигурации: Makefile
        - Старейший индустриальный стандарт. Конфигурация состоит из цепочек целей (targets), 
            зависимостей (dependencies) и прямых bash-команд для вызова компилятора.
        - Минусы: Синтаксис жестко привязан к утилитам конкретной ОС (команды mkdir или rm в Windows и Linux разные). 
            Парсинг зависимостей на больших проектах работает медленно.
    - Ninja
        - Файл конфигурации: build.ninja
        - Современная ультрабыстрая система сборки, созданная в Google специально для минимизации времени компиляции 
            огромных проектов (изначально для браузера Chromium).
        - Плюсы: Работает на порядок быстрее Make благодаря агрессивному распараллеливанию задач на все ядра CPU 
            и оптимизированному графу зависимостей.
        - Минусы: Конфигурационные файлы не предназначены для написания человеком вручную, они генерируются 
            исключительно мета-сборщиками (CMake, Meson).
    - MSBuild
        - Файл конфигурации: .vcxproj (XML-формат)
        - Родная система сборки от Microsoft, жестко интегрированная в Visual Studio. Оперирует тяжелыми XML-манифестами. 
            Почти не применяется за пределами Windows-экосистемы.

3. Сравнительный анализ генераторов проектов (Высокий уровень)
    - CMake (Промышленный стандарт №1)
        - Файл конфигурации: CMakeLists.txt
        - Де-факто главный инструмент автоматизации сборки в современном мире C++. Поддерживается абсолютно всеми 
            профессиональными IDE (CLion, Visual Studio, VS Code).
        - Программист описывает проект абстрактно: «создать исполняемый файл из таких-то cpp-файлов». CMake сканирует 
            систему и генерирует Makefile (для Make), build.ninja (для Ninja) или решение .sln (для Visual Studio).
        - Тотальная кроссплатформенность, огромная экосистема, встроенная подсистема тестирования CTest
    - Meson
        - Файл конфигурации: meson.build
        - Современный генератор, созданный как быстрая и дружелюбная альтернатива CMake. Написан на Python.
        - Плюсы: Высокая скорость конфигурации, чистый синтаксис. Жестко ориентирован на работу в связке с Ninja.
        - Минусы: Доля на рынке значительно меньше, чем у CMake; многие старые коммерческие библиотеки не поддерживают.
    - QMake — устаревший генератор от компании Qt, в современных версиях Qt6 полностью вытеснен в пользу Modern CMake.
    - XMake — новый генератор на языке Lua, набирающий популярность в геймдеве, но пока редкий гость энтерпрайзе.

Инкрементальная сборка — механизм оптимизации, при котором компилятор повторно собирает только те файлы кода, 
    которые были изменены, вместо полной перекомпиляции всего проекта с нуля.
Сборщик определяет необходимость компиляции файла по признаку - время изменения файла (Timestamp) в файловой системе.

    Вся адовая сложность сборки завернута под капотом несколькими простыми командами.

Out-of-source Build (сборка вне источника)
    Подход к компиляции проекта, при котором все временные файлы (.o, .obj, файлы сборки .ninja, Makefile) и финальный 
    исполняемый файл (.exe) создаются в отдельной изолированной папке, за пределами папки с исходным кодом (.cpp, .h).
In-source Build (сборка внутри источника), 
    когда весь мусор компиляции забивает папки с чистым кодом. В итоге: Мусор в Git, сложно clean, 
    невозможно одновременно собрать отладочную версию (Debug) и оптимизированную (Release).

---
Идеальная структура Out-of-source Build:
Мой_Проект/               (Корневая папка)
├── MyProject_Source/     (Папка С ИСХОДНИКАМИ. Сюда компилятор НЕ пишет)
│   ├── CMakeLists.txt
│   ├── main.cpp
│   └── mainwindow.cpp
│
├── build-debug/          (Папка СБОРКИ 1: Только файлы для отладки)
│   ├── CMakeFiles/
│   ├── build.ninja
│   └── MyProgram.exe     (Отладочный бинарник)
│
└── build-release/        (Папка СБОРКИ 2: Только готовый быстрый релиз)
    ├── CMakeFiles/
    └── MyProgram.exe     (Финальный чистый бинарник)


---
Для связки CMake+Ninja дерево выглядит так:
my_project/                # 1. Корневая папка проекта (Исходный код)
├── CMakeLists.txt         # Манифест CMake
├── main.cpp               # Исходный код
├── src/
│   ├── logic.cpp          # Исходный код
│   └── logic.h
│
└── build/                 # 2. Папка сборки (Тут хозяйничает Ninja)
    ├── build.ninja        # Сгенерированный манифест для Ninja
    ├── .ninja_log         # Лог хэшей команд Ninja
    ├── .ninja_deps        # Бинарная база заголовочных файлов
    │
    ├── main.exe           # КОНЕЧНЫЙ ИТОГ (Исполняемый файл)
    │
    └── CMakeFiles/        # СЛУЖЕБНАЯ ПАПКА ДЛЯ ПРОМЕЖУТОЧНЫХ ФАЙЛОВ
        └── my_project.dir/
            ├── main.cpp.o # ПРОМЕЖУТОЧНЫЙ ФАЙЛ (Объектный код main)
            └── src/
                └── logic.cpp.o # ПРОМЕЖУТОЧНЫЙ ФАЙЛ (Объектный код logic)


Разделение промежуточных файлов дает:
    - Чистота репозитория (.gitignore): Папка build/ целиком заносится в .gitignore
    - Изоляция объектных файлов: Для каждого .cpp файла компилятор генерирует ровно один объектный файл .o.
        Структура папок внутри CMakeFiles/... в точности повторяет структуру исходников в проекте. 
        Это предотвращает конфликты имен, если есть два файла utils.cpp в разных подкаталогах.
    - Мгновенная очистка проекта: Если надо удалить билд, достаточно полностью удалить папку build/

MAKE (https://www.gnu.org/software/make/manual/html_node/)

Файл конфигурации: makefile

---
Синтаксис любого правила:
    цель: зависимости
    <--TAB-->команда_сборки

---
make сначала полностью считывает весь файл, строит в памяти дерево зависимостей (граф) и только потом начинает 
    выполнять команды. Ей всё равно, в каком порядке правила объявлены в тексте.

Главное правило: Цель по умолчанию (Default Goal) - самая первая в файле (make без аргументов выполнит ее).

Правило: одна и та же цель с командой сборки должна быть СТРОГО одна.
    Может быть сколько угодно таких же целей с зависимостями. Могут даже стоять после цели со сборкой.

полная карта структуры Makefile:
1. Конфигурация (Переменные и Функции): Настройки компилятора, флагов и автоматический поиск исходников через wildcard.
2. Условные блоки (ifeq): Подстройка путей и утилит под текущую ОС или режим сборки.
3. Высокоуровневые цели (all, trace, clean): Интерфейс для разработчика (что пишем в консоли).
4. Шаблонные правила сборки (%.o: %.cpp с использованием $< и $@): Инструкция, как компилировать любой файл.
5. Подключение авто-зависимостей (-include): Слежка за изменениями в заголовочных файлах .h.



ВАЖНО!
Когда в зависимостях стоит список файлов, будет выполняться инкрементальная сборка

---
Функция замены суффиксов (suffix substitution):
    https://www.gnu.org/software/make/manual/html_node/Text-Functions.html
    $(VARIABLE:old_suffix=new_suffix)
    Разделитель: символ пустого пространства (whitespace): пробел, табуляция (\t), перевод строки (\n, newline).
    Понимает перенос строк через финальный \
    Пример:
        SRCS = main.c functions.c codewars.c
        OBJS = $(SRCS:.c=.o) // result: "main.o functions.o codewars.o"

---
ОТЛАДКА

1) функция $(info ...) или $(warning ...) - напечатает еще и номер строки
    Пример:
        $(info Список исходников: $(SRCS))
        $(info Список объектников: $(OBJS))
        $(info Текущие флаги:     $(CXXFLAGS))

2) Флаг --print-data-base (-p)
    Выгружает всю свою внутреннюю базу данных переменных и правил, которую он построил в памяти.
    Простыня, только грепать.

3) Флаг --dry-run (-n)
    Напечатает цепочку команд (переменные будут раскрыты).

NINJA

История: Гугл писали Chromium. Использовали мета-сборщик GYP. Любое изменение в коде, занимало 10-20 секунд только 
    на анализ (инкрем.сборка) и часы на перебилд проекта.
Эван Мартин (Evan Martin) - занимался сборкой. Его это заманало, и он решил ускорить процесс. И придумал Ninja.
Первые публичные упоминания и коммиты в репозиторий появились в районе 2011 года.

В папке сборки, CMake создает два основных текстовых манифеста:
1. Архитектура файлов и структура конфигурации
    - build.ninja - Главный манифест проекта. Это плоский граф зависимостей. Три базовых концепта:
        - rule: Объявление шаблона команды (например, правило для компиляции .cpp в .o или правило для линковки).
        - build: Конкретный шаг сборки, привязанный к правилу. Прописаны входные файлы, выходные файлы и переменные.
        - default: Цель, которая будет собираться, если запустить ninja без аргументов.
    - rules.ninja: Вспомогательный файл (генерируется CMake), куда выносятся описания всех системных правил компиляции 
        и линковки, чтобы не захламлять главный файл build.ninja.
    Файлы логов будут созданы Ninja после своей работы.

2. Скрытый механизм отслеживания инкрементальности
    - .ninja_deps (Бинарный файл, создается Ninja): База данных внутренних зависимостей. 
        Граф включения всех .h, упакованных в один файл. Новые зависимости дописываются в конец файла (Append), что
        раздувает со временем файл. Лечится удалением билда, либо Ninja сам иногда включает сжатие (Recompact).
    - .ninja_log (Текстовый файл, создается Ninja): Журнал всех успешно выполненных команд. Три сущности: время начала 
        команды, время окончания команды и хэш командной строки (при смене команды, файлы пересоберутся заново).

3. Инструменты командной строки и флаги оптимизации
    Автоматический параллелизм: кол-во потоков компиляции = количество логических ядер +2 
    - Флаг -j (Ограничение потоков) - Если проект огромный, лучше принудительно зажать сборку в 4 потока (ninja -j4)
    - Флаг -t (Встроенные инструменты диагностики / Tools) - 
        - ninja -t graph > project.dot — Генерирует файл графа всего проекта. Скормить утилите Graphviz.
        - ninja -t targets — Выводит список всех доступных целей
        - ninja -t deps — Показывает список всех заголовочных файлов (чтение из базы .ninja_deps).
        - ninja -t commands main.o — Покажет точную, «голую» команду компилятора, для сборкиmain.o, со всеми env и path.

4. Совместимость и версионирование
    Версии: Минимальный стандарт в индустрии на сегодня — Ninja 1.10–1.12+.
    Ninja поставляется в виде одного-единственного исполняемого файла (ninja.exe на Windows или ninja на Linux). 
        Не требует установки рантаймов, реестра или переменных окружения. Только прописать путь в PATH.


Конечным итогом работы Ninja будет готовый исполняемый файл (exe в Windows или бинарник без расширения в Linux), 
    либо собранная статическая/динамическая библиотека (.lib/.dll или .a/.so).
    Сам по себе Ninja финальный файл не создает — он отдает приказ линкеру компилятора (g++ или ld), который 
    склеивает промежуточные файлы в один готовый артефакт.

CMAKE

Концепция мета-билдера звучит так: «Write Once, Configure Anywhere» (Напиши один раз, сконфигурируй где угодно). 
    Описываем логику проекта в терминах «цели, библиотеки, зависимости», CMake переводит эту абстракцию под 
    конкретную операционную систему, конкретный компилятор и конкретный сборщик (Ninja/Make).


1. Две фазы работы CMake: Конфигурация и Генерация
    Строгий раздел на два изолированных этапа, которые выполняются при вызове команды: cmake -B build -G "Ninja"
    Фаза 1: Конфигурация (Configuration) - основная работа (90-99% работы)
    - читает главный файл CMakeLists.txt сверху вниз как скриптовый язык.
    - проверяет наличие компилятора в системе, определяет его версию и архитектуру (x86/x64). 
        Выполняются все условные операторы if(), проверяются системные зависимости, вычисляются переменные и пути. 
        Строится логический граф будущего проекта в оперативной памяти.
    - компилятор (g++) тестируется с помощью небольших файликов (напр. для cpp14 прогоняется файл с лямбдой итд).
        Если компиляция прошла успешно, значит Компр действительно потянет версию 14.
    - если есть команда install, то выполняется этап декларации (см. раздел "ИНСТАЛЛЯЦИЯ")
    Фаза 2: Генерация (Generation) - "тупая" запись на диск (1-10% работы)
    - берет построенный граф из памяти и материализует его на жестком диске в папке build.
    - На основе флага -G (в нашем случае "Ninja") создаются файлы build.ninja и rules.ninja. Если флаг не указан, 
        сгенерирует файлы для дефолтного сборщика текущей ОС (Makefile для Linux или .sln для Windows с Visual Studio).

2. Смена парадигм: Устаревший CMake против Modern CMake. Версионность.
    - Зона легаси (CMake < 3.0)
        Устаревший Си-стиль (Управление глобальными переменными)
        Что: настройки задавались через глобальные переменные, которые неявно влияли на весь проект целиком.
        Где: старые банковские системы, софт для embedded или старые версии робототехнических библиотек (ROS 1).
            # АНТИПАТТЕРН! Такое писать в современном коде запрещено:
            include_directories(${BOOST_INCLUDE_DIRS}) # Глобально добавляет пути для всех файлов
            add_definitions(-DDEBUG_MODE)              # Глобальный флаг компилятора
            add_executable(main main.cpp)
        Если проект разрастался до десятков библиотек, глобальные флаги начинали конфликтовать, вызывая хаос при сборке.
    - Зона перехода (CMake 3.0 — 3.11)
        Что: Идея таргетов уже есть, но синтаксис еще неуклюжий. Приходится писать много костылей для склейки библиотек.
    - Современная зона (CMake 3.12 и выше)
        Оперирует концепцией Таргетов (Targets). Таргет — это объект сборки (исполняемый файл или библиотека), который 
        инкапсулирует в себе и исходный код, и свои собственные настройки (флаги, пути, зависимости).
        Сборка работает предсказуемо, как конструктор LEGO - объявили таргет, прикрутили либы/модули и все работает.
            # ПРОМЫШЛЕННЫЙ СТАНДАРТ (Modern CMake):
            add_executable(main main.cpp)
            # Настройки привязываются строго К КОНКРЕТНОМУ ТАРГЕТУ:
            target_include_directories(main PRIVATE ${BOOST_INCLUDE_DIRS})
            target_compile_definitions(main PRIVATE DEBUG_MODE)

3. Анатомия базового манифеста CMakeLists.txt
    
    # 1. Защита по версии. Задает минимальную версию CMake, которая сможет прочитать этот файл.
    # при несовпадении вывалит: "CMake 3.10 or higher is required.  You are running version 3.9.0"
    # фактически весь "дьявол" спрятан тут - в политиках (см.ниже раздел)
    cmake_minimum_required(VERSION 3.10)

    # 2. Объявление проекта. Регистрирует имя проекта, версию, язык (CXX — это C++).
    # разбор LANGUAGES см.ниже (раздел "языковой контекст")
    project(MyConsoleApp VERSION 1.0 LANGUAGES CXX)

    # 3. Фиксация стандарта языка. Принудительно выставляем C++14.
    set(CMAKE_CXX_STANDARD 14)
    set(CMAKE_CXX_STANDARD_REQUIRED ON) # Защита от деградации компилятора («Тихий откат» (fallback), см. ниже)

    # 4. Создание таргета. Говорим: собрать исполняемый файл с именем "app" из исходника "main.cpp"
    add_executable(app main.cpp)

ТАРГЕТЫ

Конечным результатом работы таргета (цели) является:
    - исполняемый файл (программа/exe), 
    - библиотека (статическая .lib/.a или динамическая .dll/.so).
    - служебные таргеты

1. Основные (Бинарные) таргеты
    - Исполняемый файл:
        add_executable(trainroom main.cpp logic.cpp)
    - Библиотека (Library):
        add_library(my_math STATIC src/math.cpp)  # Статическая библиотека (.lib / .a)
        add_library(my_network SHARED src/net.cpp) # Динамическая библиотека (.dll / .so)

2. Служебные и абстрактные таргеты (Без генерации файлов)
    - Интерфейсный таргет (Interface Library / Header-only):
        add_library(my_header_only INTERFACE)
        target_include_directories(my_header_only INTERFACE include/)
    - Кастомный таргет (Custom Target):
        # Создает таргет, который при сборке просто удалит временные логи
        add_custom_target(clean_logs
            COMMAND ${CMAKE_COMMAND} -E rm -rf ${CMAKE_BINARY_DIR}/logs
        )

3. Автоматические (Глобальные) таргеты CMake
    - all (ALL_BUILD в VS): Главный таргет. По цепочке соберет все исполняемые файлы и библиотеки, описанные в проекте.
    - clean: Удаляет все скомпилированные объектные файлы и бинарники, возвращает папку сборки в чистый вид.
    - install: Запускает чтение файла cmake_install.cmake и копирует файлы в папку DESTINATION.
    - test: Запускает утилиту ctest для проверки тестов.

ИНСТАЛЛЯЦИЯ

Команда install() и вызов cmake --install - это «декларация» и «исполнение».

Этап Конфигурации (команда install в манифесте):
    При выполнении команды cmake создает специальный текстовый файл cmake_install.cmake внутри папки build,
    внутри которой записывает все пожелания (что копировать, куда копировать итд).
Этап Установки (в консоли, команда: > cmake --install build):
    Утилита CMake открывает ранее созданный файл cmake_install.cmake и начинает физически копировать файлы на 
    жестком диске по указанным адресам.

На примерах:
    # ПРАВИЛО 1: Установить скомпилированный exe-файл в папку "bin"
    install(TARGETS my_game DESTINATION bin)

    # ПРАВИЛО 2: Установить файлы ресурсов в папку "data"
    # ВАЖНО! т.к. путь указан со слэшем (assets/), то скопируется содержимое папки assets
    install(DIRECTORY assets/ DESTINATION data)


DESTINATION — это именованная опция (ключевое слово синтаксиса). Оно сообщает функции install: 
    «Всё, что написано сразу после меня, является путем назначения!».
    Сразу за опцией DESTINATION пишется сам путь. В данном случае пути bin и data являются относительными. 
    CMake автоматически подставит начало пути из CMAKE_INSTALL_PREFIX.

Генераторы (Generators)

Генератор — это обязательный внутренний программный модуль CMake, который переводит абстрактное дерево проекта из памяти 
    в конкретные файлы для сборщика. Если не указать генератор вручную (через флаг -G), CMake принудительно выберет 
    дефолтный генератор, зашитый в него для вашей операционной системы: Unix Makefiles (Linux), MSBuild/VS (Win)

Генератор — это мост между CMake и утилитой сборки (билдером), а не мост между CMake и C++.

Генератор Ninja (cmake -G Ninja) - это не сам сборщик Ninja, а внутренний модуль Cmake, который будет переводить
    дерево проекта на язык Ninja (то есть записать файл build.ninja).
    На этапе конфигурации cmake принудительно находит исполняемый файл утилиты Ninja в системе, запрашивает её версию 
    (ninja --version) и адаптирует синтаксис файла build.ninja под возможности этой конкретной версии.

Политики CMake (CMPXXXX)
https://cmake.org/cmake/help/book/mastering-cmake/chapter/Policies.html

механизм управляемой обратной совместимости, который позволяет обновлять сам CMake без риска сломать сборку старых 
    проектов. Фактически - это ВЕРСИИ команд, которые меняются в новых версиях cmake.

Каждая политика имеет уникальный идентификатор (например, CMP0074) и находится в одном из четырех состояний:
OLD: Эмулируется старое (устаревшее) поведение CMake.
NEW: Включается новое (современное) поведение CMake.
WARN: По умолчанию для старых проектов. CMake ведет себя как OLD, но выводит предупреждение (Warning) о том, что 
    проект пора обновить.
REQUIRED_IF_USED / REQUIRED_ALWAYS: Политика обязательна к исполнению. Если её не выставить в NEW, сборка упадет с 
    ошибкой (используется для окончательно удаленного старого поведения).

Механика работы cmake_minimum_required - это переключатель глобального состояния.
На примере: "cmake_minimum_required(VERSION 3.12)"
    Все политики, представленные в версии 3.12 и ранее, установятся в состояние NEW.
    Все политики, появившиеся в версиях после 3.12, автоматически выставляются в состояние WARN или OLD

Разбор (неочевидный момент):
    NEW означает «новое поведение по отношению к истории развития самого CMake», а не по отношению к проекту.
    При создании новой политики (например, запрет относит.путей) ее старое поведение (OLD) будет разрешать пути,
        а новое (NEW) - запрещать пути.
    Если политика была с 3.20, проект собирается под 3.12, а cmake версии 3.30, то политика станет OLD и показан WARN.

3.10 -------- 3.12 (Ваша отметка) -------- 3.20 -------- 3.30 (Текущий CMake)
  |             |                            |            |
[Политика А]  [Политика Б]               [Политика В]  [Политика Г]
                                        old<-|->new

Всё, что СЛЕВА (до 3.12 включительно): 
    Переводится в состояние NEW. Вы обязаны были знать об этих правилах, ваш код должен им соответствовать.
Всё, что СПРАВА (после 3.12): 
    Переводится в состояние OLD (или WARN). Это технологии будущего, ваш код о них ничего не знает, и 
    CMake защищает его, притворяясь старым.


Ручное управление политиками
1. Точечная настройка (cmake_policy) - включить фичу
    if(POLICY CMP0074)
      cmake_policy(SET CMP0074 NEW) # Включает поиск через <PackageName>_ROOT переменных
    endif()

2. Стек политик (Для авторов модулей и библиотек)
cmake_policy(PUSH)             # Сохранить текущее состояние политик
cmake_policy(VERSION 3.20)     # Временно установить правила под версию 3.20
    # ... код вашей библиотеки или подключение зависимости ...
cmake_policy(POP)              # Вернуть исходные политики основного проекта



В общем, подъем версии в cmake_minimum_required - это фактически рефакторинг сборки.

"Простота" команд cmake это обман. Всю сложность запихнули в политики (под капот).

Политики появились в CMake 2.6 (вышедшем в 2008 году). Тогда разработчики поняли, что ломать код пользователей больше 
нельзя, и внедрили эту систему. Самая первая политика в истории — CMP0000 — как раз и требовала обязательно писать 
строчку cmake_minimum_required в начале проекта.

+--------------+---------------------------+-----------------------------------+
| Версия CMake | Что произошло глобально   | Как это отразилось на политиках   |
+--------------+---------------------------+-----------------------------------+
| 2.6          | Изобретение механизма     | Появились первые CMP0000-CMP0011. |
|              |                           | Начат строгий учет совместимости. |
+--------------+---------------------------+-----------------------------------+
| 3.0          | Смена парадигмы           | Появились политики до CMP0050.    |
|              |                           | Старые политики 2.x стали легаси. |
+--------------+---------------------------+-----------------------------------+
| 3.12         | Расцвет "Modern CMake"    | Массовый переход от глобальных    |
|              |                           | переменных к объектным таргетам.  |
+--------------+---------------------------+-----------------------------------+
| 4.0          | Великое очищение          | Полное физическое удаление кода   |
|              |                           | поддержки OLD-режимов до v3.5.    |
+--------------+---------------------------+-----------------------------------+

Более точная работа версий:
+--------------+---------------------------+----------------------------------------------------------------+
| Версия CMake | Что произошло глобально   | Состояние поддержки режимов OLD                                |
+--------------+---------------------------+----------------------------------------------------------------+
| 3.31         | Начало заката эпохи 3.x   | Режим OLD для политик < 3.10 объявлен устаревшим (WARN).       |
+--------------+---------------------------+----------------------------------------------------------------+
| 4.0          | Релиз нового поколения    | Режим OLD для политик < 3.5 ПОЛНОСТЬЮ УДАЛЕН. Вызывает ERROR.  |
+--------------+---------------------------+----------------------------------------------------------------+
| 4.3.3 (Ваш)  | Текущий рабочий стандарт  | Гарантирует работу OLD для всех политик от версии 3.5 до 4.3.  |
+--------------+---------------------------+----------------------------------------------------------------+

Синтаксис "Коридор версий" (<min>...<max>)
    cmake_minimum_required(VERSION 3.9...4.3)
    при сборке на старом cmake (3.12) он использует 3.9 (версию 4.3 просто не увидит)
    при сборке на новом cmake (4.xx), он выставил политики в NEW и соберет проект.

Языковой контекст: LANGUAGES CXX

CMake изначально создавался как универсальный кроссплатформенный инструмент, поэтому он умеет управлять сборкой проектов 
    на самых разных языках.

CXX — общепринятое в мире Unix сокращение для C++.
C — чистый язык Си.
ASM — Ассемблер.
Fortran — Фортран (до сих пор активно применяется в тяжелых математических и научных вычислениях).
CUDA — Расширение Си/C++ от NVIDIA для вычислений на видеокартах.
OBJ/OBJCXX — Objective-C и Objective-C++ для экосистемы Apple.

Если убрать секцию LANGUAGES, CMake по умолчанию включит поддержку C и CXX одновременно.
    На фазе Конфигурации, будет искать в системе компилятор для чистого Си, проверять его флаги и засорять кэш 
    лишними проверками


---
«Тихий откат» (fallback)

В старых версиях C++ (98, 03) развитие стандарта шло не по языку, а по улучшению компиляции. Поэтому если не было
компилятора под новый стандарт, компиляция шла по старый ("Компиляция любой ценой") - дефолтное поведение.
В 2011–2014 годах C++ начал стремительно меняться, но разрабы CMake уже не могли убрать дефолт - сломало бы легаси.
Поэтому ввели флаг CMAKE_CXX_STANDARD_REQUIRED, который жестко запрещает тихий откат. Если что-то пойдет не так,
компиляция сразу упадет, вывалив ошибки в консоль.

Поэтому - всегда пишем set(CMAKE_CXX_STANDARD_REQUIRED ON)

Области видимости в свойствах таргетов
    Когда привязываем настройки к таргету (например, через команду target_include_directories), нужно указать один из 
    трех модификаторов области видимости. Это ключевой инструмент управления зависимостями:
    - PRIVATE: Настройка нужна только для сборки самого этого таргета. Либа A использует внутри себя заголовочные файлы 
        либы B как деталь реализации, но наружу в свои .h их не показывает, это приватная зависимость.
    - INTERFACE: Настройка самому таргету для сборки не нужна, но она жизненно необходима тем, кто будет к этому таргету 
        линковаться. Пример — Header-only библиотеки (состоящие только из .h файлов, без .cpp). Им компилироваться не 
        нужно, но пути к их инклудам должны получить все пользователи.
    - PUBLIC: Комбинация PRIVATE + INTERFACE. Настройка нужна и для сборки самой этой библиотеки, и автоматически 
        пробросится всем, кто её подключит.

+-----------+-----------------------+--------------------------+
|  Режим    | Нужен мне для сборки? | Нужен тому, кто зависит? |
+-----------+-----------------------+--------------------------+
| PRIVATE   |          ДА           |            НЕТ           |
| INTERFACE |          НЕТ          |            ДА            |
| PUBLIC    |          ДА           |            ДА            |
+-----------+-----------------------+--------------------------+

Золотое правило: Думать как создатель библиотеки
Каждый раз при настройке таргета (например, через target_include_directories или target_compile_options), решаем 
    два вопроса:
    - Нужно ли это свойство мне самому, чтобы скомпилировать мою библиотеку?
    - Нужно ли это свойство тому, кто будет мою библиотеку использовать?

Главное правило: Как выбирать между PUBLIC и PRIVATE?
    «Появляются ли типы данных из чужой библиотеки в публичных заголовочных файлах моего модуля?»
    Пишем PRIVATE, если: Код библиотеки используется только внутри файлов .cpp. В заголовочном файле engine.h 
        нет ни единого упоминания функций либы. Либа — это внутренняя деталь реализации.
    Пишем PUBLIC, если в заголовочном файле программы есть функция, которая возвращает или принимает тип из либы 
        (например, void SetVelocity(SuperVector3 vec)). Поскольку внешняя прога, подключая нашу, обязана знать, что 
        такое SuperVector3, зависимость жестко должна быть PUBLIC, иначе код игры не скомпилируется.

ДЕБАГ

message([<Тип_сообщения>] "Текст сообщения с ${Переменной}")

Тип сообщения (необязательный):
- FATAL_ERROR - красным цветом, немедленная остановка сборки!
- WARNING - желтый/красный цвет. Орет, но не останавливает сборку
- STATUS — Информационное сообщение (Стандарт индустрии). Выводит -- в начале строки
- NOTICE / VERBOSE / DEBUG / TRACE — Уровни логирования (видны только если включены через: cmake --log-level=DEBUG)

Работают переносы строк и добавление пробелов через ""

МОДУЛЬНАЯ СТРУКТУРА (дерево манифестов)

Можно построить дерево модулей.
Главная (корневая) папка - тут лежит основной CMakeLists.txt
В подпапках (модулях) будут лежать локальные CMakeLists.txt

В локальных указывается ТОЛЬКО то, что отвечает за модуль - сборка либы, пути
В корневом - уже собирается проект

Локальный:
    # 1. Объявляем, что результатом сборки этой папки будет статическая либа
    add_library(Logger STATIC src/logger.cpp)

    # 2. Привязываем к логгеру его заголовочные файлы (относительный путь ведет в "logger/include")
    target_include_directories(Logger PUBLIC include)

Корневой:
    cmake_minimum_required(VERSION 3.20)
    ....
    # 1. ПОДКЛЮЧАЕМ ПОДПАПКУ С ЛОГГЕРОМ
    # CMake идет в папку "logger", находит там локальный CMakeLists.txt и выполняет его.
    # !!!можно вызывать только тогда, когда внутри указанной папки физически лежит файл с именем CMakeLists.txt
    # После этой строчки в памяти CMake появляется готовый таргет "Logger"
    add_subdirectory(logger)

    # 2. Объявляем наше основное приложение
    add_executable(MyGame main.cpp)

    # 3. ПОДКЛЮЧАЕМ ЛОГГЕР К ИГРЕ (CMake автоматически свяжет бинарники и пробросит пути к инклудам)
    target_link_libraries(MyGame PRIVATE Logger)

Переменные путей:
    В Главном файле - пути равны, так как это корень:
        ${CMAKE_SOURCE_DIR} --> C:/projects/МойПроект
        ${CMAKE_CURRENT_SOURCE_DIR} --> C:/projects/МойПроект
    В Локальном файле (logger/CMakeLists.txt):
        ${CMAKE_SOURCE_DIR} --> C:/projects/МойПроект (корень проекта остался прежним)
        ${CMAKE_CURRENT_SOURCE_DIR} --> C:/projects/МойПроект/logger (текущая папка изменилась!)

поэтому внутри logger/CMakeLists.txt команда target_include_directories(Logger PUBLIC include) сработала идеально -
    include был взят от пути к локальной папке.

РАБОТА С ПУТЯМИ

переменные путей:
- ${CMAKE_CURRENT_SOURCE_DIR} — путь к папке, где лежит текущий CMakeLists.txt (папка с исходным кодом).
- ${CMAKE_SOURCE_DIR} — путь к самой главной, корневой папке всего проекта (где лежит самый первый, 
    главный CMakeLists.txt). Если проект из 20 подмодулей, эта переменная всегда ведет в корень.
- ${CMAKE_CURRENT_BINARY_DIR} — путь к текущей папке внутри директории сборки (например, внутри build/logger). 
    Сюда компилятор складывает временные .o файлы. Сюда нужно копировать файлы настроек проекта, чтобы программа 
    видела их при запуске.


Команды работы с путями делятся на две жесткие категории: 
    - те, которые требуют только абсолютные пути.
    - те, которые умеют правильно интерпретировать относительные (можно абсолютные, но излишне).

1) Понимают относительные
    Команды создания таргетов всегда интерпретируют относительные пути от текущей папки, где лежит CMakeLists.txt.
        add_library(Logger STATIC src/logger.cpp) // папка src лежит в корне проекта
        add_library(Logger STATIC ${CMAKE_CURRENT_SOURCE_DIR}/src/logger.cpp) // можно так, но излишне
2) Только абсолютные
    - Настройка свойств таргета (set_target_properties)
    - Поиск файлов в системе (find_program, find_library)
    - Генерация файлов и копирование (configure_file, file(COPY...))

ВАЖНО!
Любая переменная, которая содержит или может содержать путь к файлу или папке, ВСЕГДА должна оборачиваться в кавычки.

ПРАВИЛА ОБРАБОТКИ КАВЫЧЕК

Парсер обрабатывает файл CMakeLists.txt строго в два последовательных этапа:
Этап 1. Сканирование кавычек (Tokenization)
    Когда CMake видит открывающую кавычку ", он отключает деление аргументов по пробелам и ждет закрывающую кавычку ". 
    Всё, что попало между ними, парсер жестко фиксирует как один единый текстовый аргумент.
Этап 2. Подстановка переменных (Variable Expansion)
    После того, как границы аргумента определены, CMake начинает искать внутри него знаки ${...}. Он берет значение 
    переменной и вклеивает его текст прямо внутрь этой уже изолированной строки. Переменная физически не может 
    «выпрыгнуть» за пределы кавычек, потому что парсер уже определил границы этого аргумента.
    
Где кавычки обязательны:
    - В путях к бинарникам и инклудам: "${CMAKE_CURRENT_SOURCE_DIR}/..."
    - При копировании и поиске файлов: file(COPY "${строка_пути}" ...)
    - При проверке существования: if(EXISTS "${путь}")
Где кавычки НЕ нужны:
    там, где пробелов физически быть не может 

Если вручную обернуть локальный путь в кавычки, то после подстановки переменной ВЕСЬ путь гарантированно окажется 
    внутри этих кавычек.

Пример:
    IMPORTED_LOCATION "external/lib/libSuperMath.a"
    в начале этого пути будет скрыто подставлен абсолютный путь и кавычки защитят от пробела (C:\Program Files...)


---
Генераторные выражения (Generator Expressions)

$<BUILD_INTERFACE:...> — этот путь будет использоваться только внутри текущего проекта, пока пишем и компилируем код.
    Обычно абсолютный, указывающий на include внутри папки с исходным кодом (${CMAKE_CURRENT_SOURCE_DIR}/include).

$<INSTALL_INTERFACE:...> — этот путь (относительный) запишется в бинарный пакет, когда решите установить готовую либу 
    в систему (например, в /usr/local/include или C:/Program Files).
    Почти всегда относительный (например, просто include). Автоматически вычисляется относительно папки установки 
    (CMAKE_INSTALL_PREFIX).
    

Пример:
    target_include_directories(Logger PUBLIC 
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
    )

ГРУППЫ КОМАНД (добрались до ключевого)

Все функции CMakeLists.txt разделяют на четыре четкие архитектурные группы:
1) Команды создания таргетов (Target Creation)
    Эти команды создают физический или логический объект сборки. Именно в этот момент рождается граф зависимостей.
    - add_executable(app main.cpp) - создаёт исполняемый файл (бинарник).
        Каждый указанный .cpp - это указание создать объектный файл. Если не указать, то линкер растеряется.
    - add_library(lib STATIC src.cpp) - создаёт статическую библиотеку (.a / .lib).
    - add_library(lib SHARED src.cpp) - создаёт динамическую библиотеку (.so / .dll).
    - add_library(lib INTERFACE) - создаёт Header-Only либу (состоит только из заголовков .h, компилировать нечего).
    - add_library(<name> ALIAS <target>) - создание алиаса
    - add_custom_target(name ...) — создает «абстрактную» цель. Для выполнения Нинжей кастомной команды 
        (например, запустить linter или скопировать файлы ресурсов после сборки).

2) Команды настройки таргетов (Target Configuration)
    Эти команды настраивают конкретный таргет. Они работают точечно и изолированно, не влияя на соседние библиотеки. 
    Почти все они требуют указания области видимости (PRIVATE, PUBLIC или INTERFACE).
    - target_sources(app PRIVATE extra.cpp) — добавляет новые исходные файлы к уже созданному таргету.

    - target_include_directories(<Имя_Таргета> <Режим_Видимости> <Путь_К_Папке>) — указывает, в каких папках искать 
        заголовочные файлы (.h) для таргета.

    - target_compile_options(app PRIVATE -Wall) - передает специфичные флаги (warnings, оптимизации) Компру для цели.
    - target_compile_definitions(app PRIVATE VERSION=1) — объявляет макросы препроцессора (#define VERSION 1) 
        внутри кода этого таргета.
    - target_link_libraries(app PUBLIC lib) — связывает таргеты между собой ("слинковать app с библиотекой lib").

3) Настройка свойств через свойства таргетов (Target Properties)
    Универсальный низкоуровневый механизм, который настраивает специфичные параметры таргета, для которых нет 
    именных команд типа target_xxx.
    - set_target_properties(app PROPERTIES CXX_STANDARD 20) — задает стандарт C++ для конкретной цели.
    - set_target_properties(app PROPERTIES CXX_STANDARD_REQUIRED ON) — включает защиту от деградации компилятора.
    - set_target_properties(app PROPERTIES CXX_EXTENSIONS OFF) — запрещает использовать кастомные расширения компилятора.
    - set_target_properties(lib PROPERTIES OUTPUT_NAME "super_core") — позволяет изменить имя итогового файла на 
        диске (библиотека назовется libsuper_core.so, хотя в CMake её таргет называется просто lib).
4) Общие настройки и глобальные команды (Global / Directory Scope)
    Настраивают глобальное состояние CMake, управляют логикой скрипта или задают дефолтные значения для всех таргетов, 
    которые будут созданы НИЖЕ по коду.
    - cmake_minimum_required(VERSION 3.12...4.3) — инициализирует политики совместимости и задает коридор версий.
    - project(MyProject LANGUAGES CXX) — объявляет имя проекта и запускает Compiler Detection для указанных языков.
    - set(VARIABLE "value") — создает обычную текстовую переменную внутри CMake.
    - find_package(Qt6 REQUIRED) — ищет стороннюю библиотеку в операционной системе и загружает её правила экспорта.
    - add_subdirectory(src) — заставляет CMake провалиться в подпапку и прочитать находящийся там src/CMakeLists.txt.
    - message(STATUS "Hello") — выводит текст в консоль на этапе конфигурации.
    - file(COPY "${CMAKE_CURRENT_SOURCE_DIR}/assets" DESTINATION "${CMAKE_CURRENT_BINARY_DIR}") - Копируем из исходников в бинарную папку

project()

Важнейший административный и технологический центр любого манифеста CMakeLists.txt. Обязана вызываться в самом 
начале файла, сразу после cmake_minimum_required().

1. Полный синтаксис команды
    project(MySuperEngine
        VERSION 1.4.2.8
        DESCRIPTION "High-performance cross-platform 3D rendering engine"
        HOMEPAGE_URL "https://github.com"
        LANGUAGES CXX CUDA ASM
    )
  
2. Что делает при вызове:
    - Запуск Compiler Detection: CMake смотрит на параметр LANGUAGES (если не указан, по умолчанию включаются C и CXX). 
        Лезет в систему, находит компиляторы (GCC, Clang или MSVC), выполняет ту самую тестовую компиляцию пустых файлов 
        и вычисляет их возможности.
    - Генерация системных переменных: На основе переданных аргументов CMake мгновенно создает в памяти пакет переменных.
    - Подключение языковых модулей: Загружает внутренние скрипты (например, CMakeDetermineCXXCompiler.cmake), которые 
        знают, какие базовые флаги оптимизации нужны именно для этого компилятора под текущую операционную систему.

3. Какие переменные рождаются в этот момент?

Группа А: Именные переменные проекта (привязаны к проекту)
    ${MySuperEngine_SOURCE_DIR} — абсолютный путь к папке, где лежит этот CMakeLists.txt.
    ${MySuperEngine_BINARY_DIR} — абсолютный путь к папке сборки (куда Ninja будет складывать .o файлы) для проекта.
    ${MySuperEngine_VERSION} — строка "1.4.2.8".
    ${MySuperEngine_VERSION_MAJOR} — число 1.
    ${MySuperEngine_VERSION_MINOR} — число 4.
    ${MySuperEngine_VERSION_PATCH} — число 2.
    ${MySuperEngine_VERSION_TWEAK} — число 8.

Группа Б: Глобальные абстрактные переменные (Перечислим самые используемые)
    ${PROJECT_NAME} — содержит строку "MySuperEngine".
    ${PROJECT_SOURCE_DIR} — путь к исходникам текущего проекта.
    ${PROJECT_BINARY_DIR} — путь к папке сборки текущего проекта.
    ${PROJECT_VERSION} — версия проекта.
    ${CMAKE_PROJECT_NAME} — имя самого верхнего (главного) проекта в иерархии.

КЭШ (CMakeCache.txt)

Служебный файл конфигурации, который CMake создает в корне каталога сборки. Он сохраняет результаты поиска компиляторов, 
    пути к библиотекам и пользовательские настройки между запусками, ускоряя повторную генерацию файлов проекта.

Строки в файле имеют вид ИМЯ:ТИП=ЗНАЧЕНИЕ с сопутствующими комментариями-описаниями.

РАБОТА В КОНСОЛИ

Главные консольные команды при работе с CMake делятся на три основных этапа: 
    - конфигурация (создание файлов для сборщика)
    - сборка (компиляция)
    - установка (перенос готовых файлов)

1. Конфигурация (Генерация проекта)
    Команда проверяет систему, компиляторы и создает файлы сборки (например, для Ninja или VS).
    > cmake -B build -G Ninja — создает папку build и генерирует в ней файлы под Ninja.
    > cmake -B build — генерация с дефолтным сборщиком системы
    > cmake -B build -DCMAKE_BUILD_TYPE=Release — задает тип сборки Release (с оптимизацией кода). Для работы set=Debug.
    > cmake -B build -DCMAKE_INSTALL_PREFIX=./dist — указывает куда именно скопируются файлы при установке (install).

2. Сборка (Компиляция)
    Эта команда заменяет собой прямой вызов ninja или make. CMake понимает, какой сборщик был выбран и запускает его.
    > cmake --build build — компилирует проект внутри папки build. По умолчанию задействует все ядра процессора.
    > cmake --build build -j 4 — запускает сборку строго в 4 потока (полезно, если не хватает оперативной памяти).
    > cmake --build build --target my_executable — собирает не весь проект, а только конкретный указанный таргет.
    > cmake --build build --clean-first — полностью очищает старые объектные файлы (пересборка с нуля).

3. Установка (Инсталляция)
    Команда собирает "чистовой" вариант приложения или SDK без мусора и переносит в директорию CMAKE_INSTALL_PREFIX.
    > cmake --install build — выполняет установку проекта, скомпилированного в папке build.
    > cmake --install build --prefix ./my_output — выполняет установку, переопределяя папку назначения в ./my_output


Пример полной команды (все этапы в одной):
    > cmake -B build -G Ninja -DCMAKE_INSTALL_PREFIX=./dist && cmake --build build && cmake --install build

ТИПЫ СБОРОК

1) Debug — для разработки. 
    Отключает оптимизацию кода и добавляет отладочную информацию. Билд быстрый, легко дебажить, работает медленно.
2) Release — для финальных пользователей. 
    Максимальная оптимизация (флаги вроде -O3 или /O2), вырезает отладочные символы. Код максимально быстр.
3) RelWithDebInfo (Release with Debug Info) — компромисс. Код оптимизирован как в Release, но в файлы зашивается 
    отладочная информация. Полезно, чтобы искать баги и падения (краши) на "живом" приложении.
4) MinSizeRel (Minimum Size Release) — код оптимизируется по размеру итогового файла (флаги вроде -Os). 
    Применяется в основном в микроконтроллерах или мобильных устройствах, где жестко ограничен объем памяти.

Кастомный тип - можно написать любой, но будет полностью чистый, без оптимизации (как самый базовый Debug).
    set(CMAKE_CXX_FLAGS_PROFILE "-O2 -pg")  # Прописываем флаги для кастомного типа "Profile"
    set(CMAKE_C_FLAGS_PROFILE "-O2 -pg")

СТАТИЧЕСКАЯ БИБЛИОТЕКА  (про саму стат.либу ВЫНЕСЕНО В ОБЩЕЕ, здесь только специфика cmake)
    Обозначается типом STATIC

Пример со стат.либой:
    # 1. Создаем статическую библиотеку Logger
    add_library(Logger STATIC src/logger.cpp)

    # Привязываем к библиотеке её заголовочные файлы (PUBLIC — значит, их увидят все, кто подключит Logger)
    target_include_directories(Logger PUBLIC include)

Пример2 - подключаем готовую либу:
    # IMPORTED - означает, что либа уже готова, компилилить не надо, только подключить. Пути будут указаны позже
    add_library(ImportedMath STATIC IMPORTED)

    # 3. Жестко прописываем пути к принесенным файлам на диске
    set_target_properties(ImportedMath PROPERTIES
        # Указываем линкеру, где искать физический бинарный архив .a / .lib
        # Эти переменные зависят от того, что за цель мы настраиваем. У STATIC IMPORTED будут именно такие:
        IMPORTED_LOCATION "${CMAKE_CURRENT_SOURCE_DIR}/external/lib/libSuperMath.a"
        # Указываем компилятору, где искать заголовочный файл этой библиотеки
        INTERFACE_INCLUDE_DIRECTORIES "${CMAKE_CURRENT_SOURCE_DIR}/external/include"
    )
    
    # 4. Связываем наше приложение с импортированной библиотекой
    # реальная команда примерно: /usr/bin/g++ -c main.cpp -I C:/projects/MyGameProject/external/include -o main.o
    # Компр глянет в папку C:/projects.../include (которую ему подсунул CMake), найдет там файл super_math.h и 
    # вставит его текстовое содержимое внутрь main.cpp
    target_link_libraries(MyGame PRIVATE ImportedMath)

ПАКЕТЫ, ЗАГРУЗКА ПАКЕТОВ, БИБЛИОТЕК (@DIGDEEP - подробно не разбирал, просто краткий конспект)

Подходы делятся на два лагеря: 
1) FetchContent - скачать исходный код и скомпилировать его прямо внутри проекта.
2) find_package - взять уже готовую, собранную библиотеку из системы/пакетного менеджера.


1. Подход FetchContent: Скачивание исходников «на лету»
    На этапе конфигурации CMake превращается в браузер и Git-клиент. Он идет по указанной ссылке на GitHub, 
    скачивает исходный код библиотеки, кладет его в папку build и внедряет код либы в проект.

        # 1. Подключаем встроенный модуль CMake
        include(FetchContent)

        # 2. Объявляем, ЧТО и ОТКУДА качать
        FetchContent_Declare(
            fmt_lib                              # Логическое имя для CMake
            GIT_REPOSITORY https://github.com
            GIT_TAG        10.2.1                # Фиксированная версия (хэш или тег)
        )

        # 3. Физически скачиваем и делаем ее частью нашего проекта
        FetchContent_MakeAvailable(fmt_lib)

        # 4. Создаем таргет
        add_executable(trainroom main.cpp)

        # 5. Связываем exe с библиотекой fmt (CMake сам свяжет все пути)
        target_link_libraries(trainroom PRIVATE fmt::fmt)


2. Механизм find_package: Поиск готового в системе
    Эта команда ничего не скачивает. Она бегает по диску, ищет файлы конфигурации либы (*.cmake)
        # Ищет конфигурационные файлы библиотеки в системе
        find_package(fmt REQUIRED) 

        add_executable(trainroom main.cpp)
        # Подключаем найденную библиотеку
        target_link_libraries(trainroom PRIVATE fmt::fmt) 

    Два режима работы:
        - Модульный режим (Module mode) — Ищет Find<Name>.cmake
        - Конфигурационный режим (Config mode) — Ищет "<name>Config.cmake" или "<LowerName>-config.cmake"
    Вначале включается Модульный режим, если не нашел, то Конфигурационный.

3. Пакетные менеджеры: Conan и vcpkg
    Скачивают библиотеку из своего облака, компилируют её и складывают в своё глобальное хранилище.
    Используют механизм Toolchain. На этапе Конфигурации нужно просто подкинуть CMake один специальный флаг.

    Для vcpkg: -DCMAKE_TOOLCHAIN_FILE=D:/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake.
        репо: https://github.com/microsoft/vcpkg.git

    Для Conan: файл манифеста conanfile.txt в корне проекта.
        репо: https://github.com/conan-io/conan
    

Что и когда использовать?
Если проект маленький или учебный - используем FetchContent. Это запуск «в один клик» на любом ПК.
Если проект серьезный с тяжелыми зависимостями (например, OpenCV или Boost), компиляция которых займет полчаса 
    - используем vcpkg или Conan в связке с find_package.
