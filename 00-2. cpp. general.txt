Прием данных из порта (режим прослушивания) и обратной отправки (эхо-сервер): > nc -lk 8080
Поиск пакета: > pacman -Ss netcat
Обновление баз данных пакетов: > pacman -Fy

HEX-вывод прилетевшего в консоль: 
    - ставим xxd (через vim)
    - запускаем > nc -lk 8080 | xxd -c 1 -g 1
    - или (в wsl): > xxd -c1 /dev/pts/X

Побайтовая отправка (raw mode):
    > stty -icanon -icrnl && nc 127.0.0.1 8080
Еще вариант rawmode:
    > stty -icanon -icrnl -onlcr

Флаги работы терминала:
    - icanon - управление каноническим режимом ( > "stty -canon" - выключаем режим, без "-" значит включаем)
Автоматическая конвертация переносов строк:
    - icrnl (Map CR to NL on input) - замена в инпуте прилетающего CR на LF.
    - onlcr - замена в выводе LF на CRLF

В терминологии драйвера терминала (TTY) понятия Input и Output всегда определяются относительно запущенного терминала.
    Легко запомнить - tty это ОС. Мы вводим данные в ОС - это input, читаем - output.
        

 ЧЕЛОВЕК          ДРАЙВЕР ТЕРМИНАЛА (TTY)             ПРОЦЕСС (КОД)
(Железо)          [Управляется через stty]             (Ваша программа)
 
 ┌──────┐  Байт    ┌────────────────────────┐  stdin  ┌──────────────┐
 │Клава │ ───────> │  INPUT-фильтры (i...)  │ ──────> │ Читает данные│
 └──────┘  0x0D    │  (Например, icrnl)     │  0x0A   └──────────────┘
           (CR)    └────────────────────────┘  (LF)
 
 ┌──────┐  CRLF    ┌────────────────────────┐  stdout ┌──────────────┐
 │Экран │ <─────── │  OUTPUT-фильтры (o...) │ <────── │ Пишет данные │
 └──────┘ 0x0D0A   │  (Например, onlcr)     │  0x0A   └──────────────┘
                   └────────────────────────┘  (LF)

Выключая icrnl, вы запрещаете TTY трогать данные, которые идут от клавиатуры в программу.
Выключая onlcr, вы запрещаете TTY трогать данные, которые идут из программы на экран.

Пути поиска headers

Можно увидеть командой > echo | g++ -v -E -
Секция:
#include "..." search starts here:
#include <...> search starts here:
 D:/bin/msys64/ucrt64/bin/../lib/gcc/x86_64-w64-mingw32/16.1.0/include
 D:/bin/msys64/ucrt64/bin/../lib/gcc/x86_64-w64-mingw32/16.1.0/../../../../include
 D:/bin/msys64/ucrt64/bin/../lib/gcc/x86_64-w64-mingw32/16.1.0/include-fixed
End of search list.

Расшифровка:
- пустая секция под первой строчкой - компилятор не имеет глобальных встроенных папок для кавычек.
    Поиск будет: в папке проекта, в путях -I, далее как у <...>
- D:/bin/msys64/ucrt64/lib/gcc/x86_64-w64-mingw32/16.1.0/include
    Специфичные для GCC заголовочные файлы и библиотеки расширений (например, mmintrin.h для работы с процессором, 
    omp.h для OpenMP).
- D:/bin/msys64/ucrt64/include (это расшифровка пути с четырьмя ../../../../)
    Самая главная папка. Здесь находятся заголовочные файлы стандартной библиотеки C++ (STL: <vector>, <iostream>, 
    <string>), заголовочные файлы C-библиотеки среды UCRT (<stdio.h>, <stdlib.h>), а также заголовки 
    Win32 API (<windows.h>). У меня в этой папке 8к+ файлов!
- D:/bin/msys64/ucrt64/lib/gcc/x86_64-w64-mingw32/16.1.0/include-fixed
    «Исправленные» компилятором системные заголовки. Сюда GCC автоматически копирует и адаптирует файлы, в которых 
    были найдены ошибки совместимости с синтаксисом C++.

В цикле разработки жизнь программы строго разделена на два фундаментальных этапа:
1) Compile-time (Компиляция)
2) Runtime (Рантайм / Этап выполнения)
    Время, когда кликнул по exe и программа заработала.

Рантайм - имеет и второй смысл - как библиотека поддержки (Runtime Library).
    Пргме нужна невидимая сервисная служба, которая берет на себя выполнение низкоуровневых задач:
    - Запуск программы: стартует от ОС, инициирует глоб.стат.переменные, готовит Стек, наконец вызывает main()
    - Управление Кучей: malloc() и free(), операторы new и delete — это чистый код рантайм-библиотеки, хранит таблицы
    - Обработка исключений (try / catch): при throw раскручивает Стек, вызывает Деструкторы
    - Динамическое определение типов (RTTI). РТ хранит в памяти текстовые имена и структуры классов.
Этот РТ состоит из двух библиотек:
1) Базовый Си-рантайм (UCRT) - ucrtbase.dll
    Встроен в Винду.
    Управляет: памятью в Куче (malloc, free, calloc), базовым ввода-вывода Си (printf, scanf), работает с файловыми 
    дескрипторами 0, 1, 2 на уровне ОС, мат.Фции (sin, cos, sqrt) и строки в стиле Си (strlen, strcpy).
2) Рантайм стандартной библиотеки C++ (C++ Runtime, чисто C++ библиотека рантайма)
    - MinGW (GCC): файл libstdc++-6.dll (или libgcc_s_seh-1.dll).
    - Visual Studio (MSVC): файл msvcp140.dll (буква p в названии как раз означает C Plus Plus).

ВАЖНО!
При работе в MinGW/UCRT, станд.команда "g++ main.cpp -o main.exe" создает не сам код функций malloc, free или std::cout, 
а таблицу импорта (Import Address Table) - такой список-требование к ОС (т.е. КОД В EXE НЕ ВЕСЬ!). На другом компе
этот exe-шник не запустится ("Запуск программы невозможен, так как на компьютере отсутствует libstdc++-6.dll")
Чтобы принудительно зашить код функций нужно компилировать с флагом -static:
$> g++ -static *.cpp -o main.exe
Размер программы сильно вырастет (1-2 МБ, вместо 100кБ)
Эксперимент - сравнил IAT в обоих файлах, разницы особой нет :(

Увидеть таблицу IAT можно так (работает в консоли UCRT): $> objdump -p main.exe | grep "DLL Name" -A 20
В выводе будут видны либы - секции С-рантайма, С++-рантайма, ядра Windows (Win32 API) KERNEL32.dll
Для PShell команда эта: > Get-Content main.exe -Filter * | Select-String "dll" -Context 0,1

СТАНДАРТЫ БЕЗОПАСНОСТИ

---
MISRA C++
    один из самых строгих и авторитетных международных стандартов кодирования 
    на языке C++. Он создан для разработки программного обеспечения 
    в системах с повышенными требованиями к безопасности и надежности 
    (safety-critical systems).
    Цель MISRA — полностью исключить опасные фичи C++, оставить только то,
    что проверяется математически.
    Примеры, что под запретом:
    - Запрет рекурсии (Правило 7-5-4)
    - Запрет динамической памяти (Кучи)
    - Запрет на использование goto
    - Запрет неявного приведения типов
    - Ограничения на циклы

---
AUTOSAR Adaptive (Automated Automotive Open System Architecture)
    передовой международный стандарт архитектуры программного обеспечения, 
    созданный специально для современных «умных» автомобилей.
    Если классический MISRA — это свод правил о том, как правильно писать 
    строчки кода, то AUTOSAR Adaptive — это огромная операционная платформа и
    экосистема, определяющая, как программы внутри машины должны общаться 
    друг с другом.

Общие описания

ЯП С++:
- высокоуровневый
- компилируемый
- статически типизированный
- мультипарадигмальный
- общего назначения

Действующие лица:
- стандарт С++ (98/11/14/17/20/...)
- компилятор (gcc, msvc, clang)
- программист

Стандарт языка определяет:
- синтаксис (как пишется)
- семантику выражений (как вычисляется, что произойдет. Неочевидно, но 2+3=7)
- состав стандартной библиотеки

Стандарт НЕ определяет:
- реализацию языка компилятором
- уровни оптимизации (но есть рекомендации)
- последствия нарушения правил игры (undefined behavior)
- некоторые детали реализации (unspecified behavior)
    Например, порядок вычисления аргументов функции, если они передаются выражениями.


---
undefined behavior (UB):
- некорректные конструкции
- некорректные данные
- нечто, в стандарте не описанное
Примеры: 
- двойной вызов delete (двойное удаление одной и той же области памяти)
- переполнение знакового целого (! сталкивался ☺ вон оно что было )

unspecified behavior (неуточненное поведение):
- несколько возможных вариантов
- все они корректны
- стандарт не говорит, какой предпочесть

ИМЕНОВАННЫЕ ТРЕБОВАНИЯ (Named Requirements)
Чисто текстовые, неформальные технические спецификации в документации стандарта языка, которые описывают требования 
к типам данных.
Как это работает:
1) Контракт на честном слове: Стандартная библиотека объявляет шаблоны функций или классов. В документации пишется: 
    «Параметр шаблона T должен удовлетворять требованию DefaultConstructible».
2) Проверка в момент инстанцирования: Когда компилятор генерирует код для конкретного типа, он пытается применить к нему 
    операции, заложенные внутри шаблона. Если тип не соответствует требованиям, компиляция ломается.
3) Утиная типизация: Если тип ведет себя как требуемый тип (компилируется во всех местах, где используется в шаблоне), 
    компилятор считает его валидным. Ему не важны иерархии наследования.

Примеры популярных именованных требований:
- DefaultConstructible: тип должен иметь конструктор по умолчанию (объект можно создать как T a;).
- CopyAssignable: тип должен поддерживать оператор присваивания копированием (a = b;).
- Allocator: класс должен реализовывать сложный интерфейс управления памятью. Для std::vector или std::list.
- Compare: предикат должен возвращать bool и соответствовать правилам SWO.
- BasicLocable - работа с мьютексами
    m.lock() — метод для захвата эксклюзивного владения.
    m.unlock() — метод для освобождения эксклюзивного владения.
- Lockable - расширенный BasicLocable:
    m.try_lock() - доп.метод для попытки захвата. True - если захватил, false- если не удалось.
    
- ScalarType - не требование, а категория типов, определенная самим языком. Включено в NamReq для согласованности.
    - Arithmetic types
        - Integral types (char, short, int, long, wchar_t, char8/16/32_t, bool)
        - Floating-point types: float, double, long double.
    - Enumeration types (enum, enum class / enum struct)  #DIGDEEP
    - Pointer types (int*, MyClass*, void(*)(int), void*) #DIGDEEP
    - Pointer-to-member types (int MyClass::*, void (MyClass::*)()) #DIGDEEP
    - std::nullptr_t (для nullptr)
    НЕ ВХОДЯТ:  ссылки & &&, массивы, class/struct/union, void
    Проверяется: готовый метафунктор std::is_scalar_v (<type_traits>)

- TriviallyCopyable (since C++11) - это не требование, а просто категория типов. Включено в NamReq для согласованности.
    - Scalar Type
    - тривиально копируемые типы классов (там мрак #DIGDEEP)
    - массивы таких типов
    - версии этих типов, соответствующие требованиям CV

gcc или g++

---
1. Выбор языка и компиляция по умолчанию

GCC - по умолчанию считает, что компилирует код на языке C. 
Если ему передать файл с кодом C++ (например, с расширением .cpp), 
компиляция может завершиться ошибкой из-за отсутствия нужных библиотек.

G++ жестко настроен на язык C++. Он воспринимает любые входящие файлы как код C++, независимо от их расширения.

---
2. Автоматическая линковка

GCC - при компиляции файлов C++ не подключает стандартную библиотеку C++ 
автоматически, так как считает, что код написан на C.

G++ - автоматически связывает программу со стандартной библиотекой C++ 
(аналогично флагу -lstdc++ в GCC).

---
3. Макросы препроцессора

GCC - компилирует файлы C++ с меньшим количеством предопределенных макросов.

G++ - компилирует код C++ с полным набором макросов, специфичных для этого языка.

---
Что использовать?

Для исходного кода на C всегда используйте команду gcc. 
Для кода на C++ используйте g++.
  Это избавит от ручного добавления библиотек и предотвратит ошибки.

C++ - это Жестко транслируемый язык (AOT-компилируемый / Ahead-of-Time).

исходный код полностью переводится компилятором в целевой машинный код 
    (набор бинарных инструкций процессора) до запуска программы.
    После трансляции (компиляции) представляет собой готовый exe.

«жестко» значит - полное отсутствие интерпретатора или виртуальной машины в RT.

Ключевые признаки «жесткой» трансляции:
1) Прямое исполнение.
    Нет никаких промежуточных слоев вроде JVM (java).
2) Отсутствие JIT-компиляции.
    Все, что способно выполнится, уже зашито в байтах exe.
3) Статическая привязка к платформе.

ПРАВИЛО ОДНОГО ОПРЕДЕЛЕНИЯ (ODR — ONE DEFINITION RULE)

это фундаментальное правило в C++, предотвращающее конфликты при компиляции и
 связывании. Оно требует, чтобы каждая сущность (класс, функция или переменная) 
имела ровно одно определение в рамках всей программы.


Ключевые принципы
Для единицы трансляции (файла .cpp): 
    Каждая переменная, функция, класс или перечисление могут быть определены 
    только один раз.
Для всей программы: 
    Если сущность используется, должно существовать ровно одно ее определение 
    во всех скомпилированных файлах. 
    Исключение составляют классы, шаблоны и inline-функции (???????)

Нарушение ODR приводит к ошибке линковки (например, "multiply defined symbol") 
или, что еще опаснее, к неопределенному поведению (undefined behavior).

ЕДИНИЦА КОМПИЛЯЦИИ (ОФИЦИАЛЬНО: "ЕДИНИЦА ТРАНСЛЯЦИИ", TRANSLATION UNIT, "ЕК")

Это один полноценный исходный файл, который компилятор C++ обрабатывает за один 
рабочий цикл.

Это один .cpp файл со всеми заголовочными файлами (.h/.hpp), которые в него 
скопировались через директивы #include.
Это еще текстовый код (после #include и #define).
Файл .obj (или .o в Linux) — это уже результат её компиляции (объектный файл).



---
Как рождается Единица Компиляции (Этапы):
1) Ваш исходник: 
Есть файл main.cpp. В нём написано всего 10 строк кода, но в самом верху 
стоит #include <iostream>

2) Работа Препроцессора (Preprocessing)
Препроц берет всё гигантское содержимое этого системного заголовка 
(а там тысячи строк кода) и физически вставляет (вклеивает) его прямо внутрь 
вашего main.cpp вместо строчки #include.
ДОП: также заменяет #define на указанное значение.

3) Финальный результат:
Огромный «сплошной текстовый пирог», который получился после склейки, 
и называется Единицей компиляции. 
Её размер может легко вырасти с 10 строк до 50 000 строк кода. 
Именно его массив текста компилятор начинает анализировать.

---
увидеть единицу компиляции своими глазами:

> g++ -E main.cpp



//--------------------------------------
INCLUDE GUARD (IG)

---
Классический Include Guard (Через макросы):
(рекомендуется для публичных библиотек - олдовые компиляторы итд)

#ifndef INC_1_3_MODULES_LOG_H
#define INC_1_3_MODULES_LOG_H
...<код заголовка>
#endif //INC_1_3_MODULES_LOG_H

IG защищает файлы в рамках ОДНОЙ единицы компиляции!
При переходе к следующей единице компиляции все эти константы (макросы) 
полностью стираются, и вся магия Include Guard запускается заново.

Напоминалка: каждая единица компиляции живет в абсолютной изоляции.

---
Современная альтернатива: #pragma once
(рекомендуется для обычных своих проектов)

Должен располагаться строго до любого содержательного кода.
Оптимально: Самая первая строчка файла.
Допускается: Если перед ним идут комментарии (например, лицензия или описание 
    файла) или пустые строки.
Категорически нельзя: Ставить его после объявления структур, функций или 
    подключения других библиотек. Если препроцессор успеет скомпилировать 
    хотя бы одну строчку кода до того, как увидит #pragma once, то при 
    повторном включении этого заголовка эта первая строчка продублируется и 
    вызовет ошибку.

Технические "подводные камни".
Прагма_уанс - опирается на имя файла.
- проблема ссылок - компилятор может подумать, что это 2 разных файла
- если заголовок случайно скопирован в другой файл.
- Сетевые файловые системы (NFS / Samba) - комп.может запутаться.
Во всех этих случаях, в ЕК может залететь дубль заголовка.




//--------------------------------------
В целом процесс сборки:

Препроцессор — склеивает текст (создает единицу компиляции).
Компилятор — переводит этот текст в машинный код с «пустышками» (объектный файл).
Линковщик — сшивает «пустышки» с реальными адресами.

---
Что сделает компилятор:

[ Текст на C++ ] 
   │  (Препроцессор: подставил #include, развернул макросы)
   ▼
[ Чистый C++ ]
   │  (Компилятор: перевел язык высокого уровня в команды процессора)
   ▼
[ Ассемблерный код ] ───► Это текстовый файл (.s). Здесь написаны команды вроде 'mov', 'push', 'add'.
   │  (Ассемблер: превратил текст команд в их бинарные шифр-коды)
   ▼
[ Машинный код ]    ───► Это объектный файл (.o). Здесь только байты (нули и единицы).

---
Что сделает линковщик:

Сейчас в объектом файле есть бинарный код всех функций кода из .cpp.
Но если внутри мы вызывали, например, std::cout или функции из std::string, то в объектном файле на их месте стоят 
пустые заглушки (адреса-пустышки). Компр как бы оставил записку: «Здесь нужно вызвать std::cout, но я не знаю, 
где он находится в памяти». Поэтому нужен финальный этап — Линковка (Компоновка).

Линкер возьмет my_code.cpp.o, возьмет бинарный код стандартной библиотеки C++, свяжет их адреса и выдаст .exe/.a/.so


//--------------------------------------
Пути поиска хедеров (.h/.hpp)

Компр ищет заголовочные файлы по строгому алгоритму, разделяя их на две категории в зависимости от того, как написана 
    строка: в кавычках (#include "...") или в угловых скобках (#include <...>).

1) Пользовательские файлы (#include "my_file.h")
    Этот вариант используется для файлов самого проекта. Компр ищет в следующем порядке:
    - Текущая папка - каталог, в котором физически лежит сам .cpp (или .h) файл, содержащий эту строчку #include.
    - Папки проекта, заданные вручную - каталоги, которые переданы компилятору через флаг -I 
        (например, -I../logger/include). Проверяются строго в том порядке, в котором написаны в команде сборки.
    - Системные пути - если файл не найден в первых двух пунктах, Компр ищет там, где лежат станд. библиотеки (ниже)
2) Стандартные и системные библиотеки (#include <vector>)
    Текущая папка не проверяется, поиск идет сразу в системе:
    - Папки проекта, заданные вручную — те самые пути из флагов -I (аналогично пользовательским)
    - Пути из переменных окружения - специальные системные переменные, если заданы в терминале 
        (например, CPATH или C_INCLUDE_PATH / CPLUS_INCLUDE_PATH).
    - Стандартные системные папки (Встроенные пути) — это жестко зашитые внутри самого компилятора пути к 
        заголовочным файлам операционной системы и стандартной библиотеки (STL).

ПОДХОДЫ К ОРГАНИЗАЦИИ КОДА
обычный код (монолит), статические библиотеки и динамические библиотеки.

Монолит (Обычный код)
    - Хранится в виде текстовых файлов (.cpp, .hpp).
    - При создании программы файлы заново компилируются. Код полностью открыт, компилятор может оптимизировать.
Статическая библиотека (Static Library)
    - Расширения: .a (Linux/macOS), .lib (Windows).
    - Это обычный архив (как .zip), внутри которого лежат скомпилированные объектные файлы (.o/.obj). 
        Main отсутствует. Это просто набор классов-функций-переменных, «физически» не связанных между собой (не было 
        линковки), но знающих через Таблицу Релокаций (Relocation Table). Есть риск случайно подменить/забыть файл.
    - Зачем: Чтобы не компилировать миллион строк кода (например, движок или парсер) заново при каждом изменении 
        в программе. Компилируем один раз, пользуемся много раз и быстро.
Динамическая библиотека (Shared/Dynamic Library)
    - Расширения: .so (Linux), .dll (Windows), .dylib (macOS).
    - Суть: Похожа на стат.либ, но файлы полностью прошли полноценный этап линковки (внутренней компоновки) на 
        этапе сборки. Все внутренние связи между файлами .o, из которых она состояла, полностью разрешены.
    - Главное отличие: добавлен особый интерфейсный слой — Таблица Экспорта. Это список бинарных адресов функций, 
        которые библиотека разрешает вызывать снаружи.
    - Может подгружаться сразу при старте или при вызове (уже в рантайме).
    - Одна либа на все программы - после загруки в память, доступна всем
    - Можно заменить версию либы, не трогая основную программу.
HEADER-ONLY БИБЛИОТЕКА (Отдельный тип. Библиотека, состоящая только из заголовочных файлов)
    - весь код пишется в .h, отсутствует полностью .cpp (нечего компилировать)
    - +++Простота интеграции: Пользователю не нужно возиться с линкером, компилировать бинарники под разные ОС, 
        настраивать форматы .a, .lib, .dll. Просто копируете папку с заголовками к себе в проект, делаете #include — 
        и всё сразу работает.
    - +++Агрессивная оптимизация: Компр видит весь код функций прямо в момент сборки main.cpp, он может применять инлайнинг 
        (inline) - физически вшивать код функций вместо их вызова, что убирает накладные расходы.
    - ---Замедление компиляции: Если один и тот же тяжелый заголовок подключен в 50 разных .cpp файлов проекта, 
        компилятор будет вынужден обрабатывать этот код заново 50 раз.
    - ---Никакой скрытности: Весь исходный код открыт пользователю. Спрятать интеллектуальную собственность 
        в скомпилированный бинарник не получится.
    - Пример: легендарные nlohmann/json (для работы с JSON), GLM (математика для 3D-графики), Catch2 (тестирование) итд.
    - Главный технический подвох: Ошибка "Multiple Definition". Т.к. действует правило ODR, 
        весь код обязан использовать inline для функций или constexpr/inline для переменных.

СТАТИЧЕСКАЯ БИБЛИОТЕКА

В большом проекте, компилировать сотни .cpp файлов каждый раз заново — очень долго. И передавать по проекту сотни файлов 
.cpp неудобно. Статическая библиотека решает эту проблему: исходный код компилируется в библиотеку всего один раз. 
Специальная утилита (архиватор ar) берет получившиеся файлы с машинным кодом и упаковывает их в один-единственный файл,
например, libLogger.a.
При линковке готовый код (.o) будет вклеен в исполняемый файл (.exe) - на этапе линковки архив распакуется, из него
возьмутся только нужные файлы .o и будут вставлены в .exe.

Плюс: Приложению для работы больше не нужны никакие внешние файлы. Можно перенести App.exe на другой чистый компьютер, 
    и всё будет работать, потому что библиотека находится внутри него.
Минус: Если эту же библиотеку используют еще 5 программ, код логгера продублируется и запишется внутрь каждой из них. 
    Размер программ на диске будет больше.
Минус2: Стат.либа не уменьшает монолит. Служит только для удобства организации и скорости компиляции.

Функции main в статической библиотеке быть не должно - иначе при подключении либы будет 2 main (ошибка).

Чтобы подключить готовую статическую библиотеку (например, libLogger.a или Logger.lib) к приложению, нужно: 
    - показать коду заголовочные файлы (.h / .hpp) на этапе компиляции.
    - указать линкеру на файл библиотеки на этапе компоновки.

МойПроект/
├── include/
│   └── logger.h          <-- Заголовочный файл библиотеки
├── lib/
│   └── libLogger.a       <-- Сама статическая библиотека
└── main.cpp              <-- Основной код, куда подключаем либу

Само подключение - см. СБОРЩИКИ (cpp.builders.txt)

HEADER-ONLY БИБЛИОТЕКА (библиотека, состоящая только из заголовочных файлов)

1. Структура проекта библиотеки
    SuperFormatter/
    ├── CMakeLists.txt
    └── include/
        └── super_formatter.h

2. Код библиотеки (include/super_formatter.h)
    #pragma once
    #include <string>

    namespace Format {
        inline std::string ToStars(const std::string& text) { // Обязательно inline!
            return "*** " + text + " ***";
        }
    }

3. Манифест для создания
    # Создаем виртуальную библиотеку типа INTERFACE (без бинарного кода)
    add_library(SuperFormatter INTERFACE)

    # Привязываем заголовочные файлы через режим INTERFACE
    # Это значит: "Мне самому компилировать нечего, но передай этот путь всем, кто меня подключит"
    target_include_directories(SuperFormatter INTERFACE 
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    )

4. Подключение в другом проекте
    # Объявляем чужую библиотеку как INTERFACE IMPORTED (бинарника .a/.lib у неё нет)
    add_library(ImportedFormatter INTERFACE IMPORTED)

    # Указываем только путь к заголовочным файлам (IMPORTED_LOCATION указывать НЕ нужно!)
    set_target_properties(ImportedFormatter PROPERTIES
        INTERFACE_INCLUDE_DIRECTORIES "${CMAKE_CURRENT_SOURCE_DIR}/external/SuperFormatter/include"
    )

    # Подключаем к нашему приложению через PRIVATE (так как это заголовочный интерфейс)
    # CMake возьмет путь external/SuperFormatter/include и подставит его компилятору в виде флага -I
    # Компр физически вставит код из .h и вуаля! Код в нашей программе!
    target_link_libraries(MyApp PRIVATE ImportedFormatter)

ВАЖНО!
Помнить, что цепочка подключений INTERFACE должна закончится реальным подключением PUBLIC или PRIVATE.




//--------------------------------------
ПРО ФАЙЛЫ H/HPP И CPP

В заголовочный файл выносятся элементы, которые являются декларациями 
(инструкциями/чертежами) для компилятора. 
Они только описывают интерфейс, но не выделяют память и не генерируют 
    физический код.

Выносить в .h файлы:
---
МОЖНО И НУЖНО:
1) инклуд-гарды (не забываем!)
2) Прототипы, сигнатуры (объявления, declaration) функций.
3) Объявления классов и структур (struct, class) и enum.
4) Объявления глобальных переменных с ключевым словом extern.

МОЖНО (Исключения из правил):
5) Шаблоны (Templates).
6) Константы (const или constexpr).
7) inline-функции

КАТЕГОРИЧЕСКИ НЕЛЬЗЯ(!):
8) Тела обычных функций (ошибка multiple definition).
9) Определения глобальных переменных без extern.
10) Директива using namespace std; - "грязь", конфликты имен, сломает.
11) Инклуды файлов .cpp (УПАСИ БОЖЕ, ТЕХНОЖРЕЦЫ ПРОКЛЯНУТ!)


//--------------------------------------
INLINE-ФУНКЦИИ

Когда компилятор видит inline-функцию, у него есть два пути развития событий:
Путь_1: Идеальный (Встраивание кода)
    компилятор берет её внутренности и встраивает их прямо в место вызова.
    сама функция исчезает, она больше не нужна.
Путь_2: Реальный (Функцию не удалось встроить)
    Компилятор имеет право отказаться встраивать код 
    (функция слишком длинная, содержит сложные циклы или рекурсию).
    Тогда он скопирует определение несколько раз и пометит каждое (weak symbol 
    или COMDAT). Линковщик оставит одну (случайную) копию, остальные выбросит.


Особенности:
- функции со словом inline не видны (НЕДОСТУПНЫ!) из других объектных файлов 
    (они имеют внутреннее связывание) .obj
- тело функции копируется во все единицы компиляции, но компилятор и линкер 
    имеют секретное соглашение, которое официально разрешает это нарушение (ODR)
- в конечном итоге все копии тела должны быть одинаковы!

УСТРОЙСТВО ПАМЯТИ (сложная тема, поэтому только некоторые аспекты)

Теоретически 64-битная архитектура может адресовать 16 Эксбибайт (ЭиБ), 
    что равно 18 446 744 073 709 551 616 байт.
Реально для адресации памяти используется 48 бит (57 бит для новых серверов).
Это - 256 Терабайт (ТБ).
Windows делит доступные 256 ТБ виртуального пространства пополам: 
    128 ТБ выделяется на процессы пользователя и 
    128 ТБ резервируется под нужды ядра ОС.
128 ТБ (0x800000000000, 11 нулей после 8) (0b100..000 - 47 нулей)
Диапазон польз. адресов в Windows x64 находится в границах 
    от 0x0000000000000000 до 0x00007FFFFFFFFFFF (F*11)

Для одного приложения доступно до 8 ТБ, остальное резервируется.
Эта память делится между пользовательскими приложениями и системным ядром.
Это максимальное виртуальное адресное пространство, поддерживаемое для каждого 
    процесса в Windows 10. Это не для каждого пользователя или ядра процессора, 
    это общесистемное архитектурное ограничение. 

Когда программа обращается к адресу 0x7ff643e14000, специальный аппаратный блок 
процессора (MMU — Memory Management Unit) мгновенно подглядывает в секретную 
таблицу страниц, которую ведет Windows. Он «на лету» переводит этот огромный 
виртуальный адрес в реальный физический адрес внутри ваших 32 ГБ 
(например, в условный 0x1A2B3C).
При этом - другая программа может обращаться по этому же адресу, но
физически - это будут РАЗНЫЕ адреса (механизм страниц памяти)

ПРО ЯДРО:
Ядро ОС занимает верхнюю половину всего доступного виртуального пространства 
размером 128 ТБ. Этот диапазон адресов в шестнадцатеричной системе выглядит так:
Начало диапазона: 0xFFFF8000`00000000`
 Конец диапазона: 0xFFFFFFFF`FFFFFFFF`
Sign Extension (Расширение знака): По правилам архитектуры AMD64/Intel 64, 
биты с 48 по 63 должны дублировать 47-й бит. Поскольку у адресов ядра 47-й бит 
равен единице, все старшие биты превращаются в F. Из-за этого адреса ядра 
всегда начинаются с 0xFFFF.
Здесь находятся - драйверы, системный кэш, таблицы страниц, сист.пулы.


---
ПРО СТЕК:

Физически стек находится в оперативной памяти (RAM).
Виртуальный адрес - (Win10) может быть любым в Вирт.памяти (128Гб)
Растет сверху вниз (от больших адресов к меньшим), вершиной вниз.

ВЕРШИНА СТЕКА:
Адрес хранится в регистре ESP/RSP (текущий занятый адрес)
(ESP в 32-битных процах, x86, шаг: 4 байта)
 RSP в 64-битных процах, x64/AMD64, шаг: 8 байт)
Добавление данных (команда PUSH):
    Процессор уменьшает значение RSP на 8 байт (в 64-битной системе).
    Записывает данные по новому адресу, на который указывает RSP.
Извлечение данных (команда POP):
    Процессор считывает данные из адреса, на который указывает RSP.
    Увеличивает RSP на 8 байт, «освобождая» место.

УПРАВЛЕНИЕ КАДРОМ СТЕКА (Stack Frame):
EBP (Extended Base Pointer) - x32, размер: 4 байта
RBP (Register Base Pointer) - x64, размер: 8 байт


Как работает кадр стека (Stack Frame):
1) Создание кадра (Пролог функции):
    - сохраняем rbp текущей функции (чтобы мб вернуться), "sub rsp, 8"
    - добавляем 32 байта rbp - 32 для переменных и аргументов (shadow space)
2) Доступ к переменным:
    Пока функция работает, RSP может хаотично меняться. Но адрес RBP стабилен.
    Выделенные 32 байта как-то там используются под аргументы итд
3) Уничтожение кадра (Эпилог функции):
    Перед выходом из функции старые значения восстанавливаются.

Внутри кадра процессор может перемещаться, от RBP (неподвижный адрес) 
до BSP (двигается) 


---
ПРО ПАМЯТЬ (RAM):

Программе выделяется кусок памяти, состоит из 4 частей:
1) Сегмент кода (Текст)       <- Машинные инструкции программы (Read-Only)
2) Сегмент данных (Data/BSS)  <- Глобальные и статические переменные
    Хранит инициализированные переменные (int x = 42;)
    Хранит неинициализированные переменные (int array[1000];)
3) Куча (Heap)                <- Растет "вверх" (к старшим адресам)
    Область памяти, которой вы управляете вручную (new, malloc)
    Удаляем из нее тоже сами (delete, free).
    Забыли удалить? Получили утечку памяти (memory leak).
4) Стек (Stack)               <- Растет "вниз" (к младшим адресам)
    Автоматическая память
    Хранит аргументы функций и локальные переменные

В Win10 (а может и других), на самом деле все сегменты могут лежать в разных
частях виртуальной памяти.
И даже Куча - под разные ее части могут быть выделены разные диапазоны адресов.

Главный обман: Виртуализация
Программа на C++ никогда не знает, где физически лежат её данные — 
в модуле оперативной памяти DDR5, в кэше процессора L1/L2/L3 или вовсе временно 
    сброшены на жесткий диск в файл подкачки (pagefile.sys).
Процессор (через блок MMU) и Windows прозрачно для C++ переводят каждый 
виртуальный адрес в физический (это хранится в секретной таблице страниц
и специальном кэше процессора (TLB).
Благодаря этому две разные запущенные программы могут использовать один и тот же
виртуальный адрес (например, 0x00400000), но физически они будут писать в 
совершенно разные ячейки памяти компьютера, не мешая друг другу.
Это технология защиты (ASLR), от хакеров, адреса процессов все время разные.

Процессору запрещено хранить физические адреса в регистрах по 2 причинам:
1) Полный хаос при многозадачности.
    при смене потока пришлось бы жонглировать данными в RAM
2) Безопасность.
    Из процессора можно было бы выдернуть реальный адрес и атаковать.

ПРО ИЗОЛЯЦИЮ ПРОЦЕССОВ (RAM продолжение):

Механизм аппаратной виртуализации памяти. В основе этой изоляции лежит 
концепция: один процесс — одна уникальная таблица страниц.
Программа физически не способна дотянуться до памяти другого процесса, 
потому что для неё этой памяти просто не существует в её виртуальном мире.

Главный механизм: Таблицы страниц (Page Tables).
Вся виртуальная память делится на небольшие блоки — страницы (обычно 4кБ).
Хранит связь между виртуальными адресами программы и физическими чипами ОЗУ.
Когда Windows создает процесс (например, chrome.exe или вашу программу на C++), 
она выделяет для него индивидуальный набор таблиц страниц в памяти ядра.
В процессорах x86/x64 есть специальный системный регистр контроля — CR3 
(он же Page Directory Base Register). Он хранит физический адрес таблицы страниц 
текущего запущенного процесса.
При переключении Процесса А на Процесс Б, в регистр CR3 пишется адрес таблицы 
страниц Процесса Б. С этого момента MMU "видит" адреса Процесса А.
(ТУТ НЕ СОВСЕМ РАЗОБРАЛСЯ, НО ПОКА И НЕ НУЖНО)
Регистр CR3 - защищен аппаратно - Ring 0.
Если программа полезет в адреса, которых нет в ее таблице, ядро перехватит это
и вывалит ошибку 0xC0000005 (Access Violation).

ПРО ДЕСКРИПТОРЫ (общее про ОС)

Дескрипторы ввода-вывода (I/O Descriptors / File Descriptors) -
    это идентификаторы (числа), которые ОС выдает программе для работы с 
    потоками данных: файлами, консолью, сокетами или трубами (pipes).
    Они служат мостом между вашей программой и ресурсами ОС. Вместо того чтобы 
    каждый раз передавать операционной системе длинное имя файла или адрес 
    устройства, программа передает короткий идентификатор.

Дескриптор - это индекс в таблице открытых файлов текущего процесса, которую 
    ведет ядро Linux. Это обычное целое число (тип int).
    Любой открытый файл или сокет получит число 3, 4, 5 и так далее. 
    Напрямую передается в системные вызовы вроде read(fd, buf, size).

Стандартные дескрипторы всегда фиксированы:
0 — Стандартный ввод (stdin)
1 — Стандартный вывод (stdout)
2 — Вывод ошибок (stderr)
Они задаются системой отдельно для каждого процесса (программы). При этом Прг
не знает куда они "смотрят" (у каждой программы есть своя маленькая личная
таблица дескрипторов, она просто читает из 0 или пишет в 1.)
У ОС есть Системная таблица открытых файлов (Глобальная), в ней записаны ВСЕ
выделенные ресурсы. Еще есть Таблица v-nodes (виртуальных узлов) или i-nodes,
в которую смотрит глобальная таблица (это для файлов, для сокетов по-другому)
Все сложно, в общем...


Все дескрипторы, начиная с 3 и далее, ОС выделяет динамически под любые новые 
источники/приемники данных, которые запрашивает программа. 
В Linux (glibc) это всегда будут просто нарастающие целые числа (3, 4, 5...). 
В Windows (UCRT) это тоже будут числа, но за ними внутри библиотеки будут 
    скрываться системные хэндлы (HANDLE) Windows.

Основные типы ресурсов, которые занимают дескрипторы:
1) Открытые файлы (Самый частый случай)
    Дескриптор 3 -> config.txt (открыт на чтение)
    Дескриптор 4 -> log.txt (открыт на запись)
  ПРИМ.: У "железа" нет ограничений (HDD/SDD может одновременно и писать, и 
    читать). За статусом файла следит сама ОС (пишем или читаем итд). 
    Также ОС хранит разную служебн.инфу (напр.: File Offset - смещение итд)
2) Сетевые сокеты (Sockets)
3) Каналы и Пайпы (Pipes / Named Pipes).
    В консоли пишем |, создастся 2 дескриптора: на чтение и запись, которые
    будут подпихнуты шеллом нужным программам 
    (например, пишем: > a.exe | log.txt,
    тут труба (pipe): дескриптор №7 (вход), дескриптор №8 (выход).
    Вход 7 шелл подпихнет нашей проге и подменит ей STOUT (1) адресом Вход_7.
    В итоге: программа пишет в STOUT, а данные попадают в пайп. Хитро!
4) Специфичные для Linux ресурсы (glibc): "все есть файл", поэтому:
    Таймеры (timerfd_create), События (eventfd), Устройства (/dev/)


Жизненный цикл дескрипторов
1) Выделение: Программа просит ресурс (open()) -> ОС находит минимальный 
    свободный индекс (например, 3) и резервирует его.
2) Использование: Программа читает/пишет, передавая число 3
3) Освобождение (close()): Программа закрывает файл -> дескриптор 3 снова 
    становится свободным. При открытии другого файла ОС м снова выдать номер 3

               ▼
┌──────────────────────────────────────────────┐

└──────────────┬───────────────────────────────┘
               │  (Аппаратное прерывание IRQ)
               ▼
┌──────────────────────────────────────────────┐
│ 2. Низкоуровневый драйвер (Low-level Driver)  │ -> Читает регистры SoC, очищает FIFO (передает байт в подсистему TTY)
└──────────────┬───────────────────────────────┘
               │  (Интерфейс tty_port)
               ▼
┌──────────────────────────────────────────────┐
│ 3. Дисциплина линии (TTY Line Discipline)    │ -> Обработка спецсимволов (\n, CR/LF). Канонич.режим - копит до \n.
└──────────────┬───────────────────────────────┘        Сырой режим - пробрасывает байт дальше.
               │  (TTY Буфер / Входной кэш)
               ▼
┌──────────────────────────────────────────────┐
│ 4. Подсистема TTY Core & VFS (Ядро Linux)    │ -> Абстракция файла (/dev/ttyS0). Увязывает буфер с нодой, 
└──────────────┬───────────────────────────────┘        хранит fd (который ранее был выдан через open())
               │  (Системный вызов sys_read)
               ▼
┌──────────────────────────────────────────────┐
│ 5. Пространство пользователя (User Space)    │ -> read(fd, &buf, 1) в C++ коде. Syscall по fd, вызывает tty_read(),

Три поколения системных вызовов, работающих по принципу готовности (readiness-based)
    для отслеживания готовности файлов: select() ➔ poll() ➔ epoll().

- select() - O(N). морально очень устарел. Основан на битах и битовых масках. Max 1024 файла. Низкий перфоманс.
- poll() - O(N). старый, но не устарел. Ограничений на кол-во файлов нет, но нужно перебирать.
        Подходит для обычных файлов.
- epoll() - O(1). Вершина эволюции. Перебора нет, возвращает готовый список дескр, в которых что-то произошло.
        НЕ подходит для обычных файлов.

poll
Standard C library (libc, -lc)
<poll.h>

    int poll(struct pollfd *fds, nfds_t nfds, int timeout);

    struct pollfd {
        int   fd;         /* file descriptor */
        short events;     /* requested events */
        short revents;    /* returned events */
    };

Ввод и вывод (можно задавать в events):
    - POLLIN — есть обычные данные для чтения.
    - POLLOUT — можно писать данные (буфер отправки не переполнен).
    - POLLPRI — есть срочные (внеполосные) данные для чтения (OOB data).
Ошибки и события (возвращаются только в revents, задавать их в events не нужно):
    - POLLERR — на дескрипторе произошла аппаратная или системная ошибка (помехи на линии, не совпал Baudrate).
                При этом контроллер генерирует ошибки кадра (Framing Error) или переполнения (Overrun Error).
    - POLLHUP — (Hang Up / Обрыв). удаленная сторона закрыла канал/сокет.
                Выдернули провод, устройство исчезло, и Линукс вешает флаг.
    - POLLNVAL — невалидный дескриптор файла (например, он вообще не открыт или закрыт до вызова poll).
                Протух, например, закрыли в другом потоке.
Обычно базово: events = POLLIN; для чтения и проверяют revents & POLLIN
    
    
    - nfds_t - целочисленный тип, кол-во дескрипторов файлов;
    - timeout - (в мс) время ожидания поступления данных (поток спит), "-1" - ждать бесконечно, 
        "0"-вернуть сразу (вернет 0, если ничего не было).

Эталонная работа с poll()
```
void process_main(Config& config) {
    // Используем буферное чтение, для оптимизации вызовов read()
    uint8_t rx_buffer[255];

    // Подготовка структуры для poll (всего 1 элемент, поэтому без массива)
    struct pollfd fds{};
    fds.fd = config.pty_fd;
    fds.events = POLLIN; // Нас интересует только событие "готово для чтения"

    // Main loop
    while (true) {

        // Безопасность: сбрасываем возвращенные события перед каждым опросом
        fds.revents = 0;

        // Спим-Ждем нажатия максимум 500мс, потом проснемся и пойдем дальше.
        int ret = poll(&fds, 1, 500);

        if (ret > 0) {

            // @debug
            //std::clog << "[DEBUG] poll проснулся по событию. revents = 0x"
            //    << std::hex << fds.revents << std::dec << std::endl;

            // Были ли ошибки?
            if (fds.revents & (POLLERR | POLLHUP | POLLNVAL)) {
                std::cerr << "[ERROR] Аппаратная ошибка UART (tty) закрыт!" << std::endl;

                // выходим из цикла
                close(config.pty_fd);
                break;
            }

            // Если ошибок нет, проверяем, пришли ли данные
            if (fds.revents & POLLIN) {

                // успешный успех, читаем что пришло
                ssize_t readLen = read(config.pty_fd, rx_buffer, sizeof(rx_buffer));
                // обязательно проверяем (ЖЕЛЕЗНОЕ ПРАВИЛО), >0 - это юридический факт (могло убиться на ctrl+C например)
                if (readLen > 0) {
                    for(ssize_t i = 0; i < readLen; ++i) {
                        uint8_t rx_byte = rx_buffer[i];
                        process_byte(rx_byte, config);
                    }
                }
                else if (readLen == 0) {
                    // Конец файла (EOF), провод выдернули?
                    std::cerr << "[CRITICAL]: Устройство отключено (EOF)." << std::endl;
                    close(config.pty_fd);
                    break; // Выходим из цикла опроса, нужно переподключение
                }

                // readLen < 0 (Произошла ошибка!)
                else {

                    // Сигнал ОС прервал чтение. Это не страшно. Возвращаемся к poll()
                    if (errno == EINTR) {
                        continue;
                    }
                    // Ложное срабатывание. Выходим из обработки POLLIN, чтобы poll() снова уснул
                    if (errno == EAGAIN || errno == EWOULDBLOCK) {
                        break;
                    }

                    // Все остальные ошибки (EIO, EBADF, ENXIO) - критические!
                    std::perror("[CRITICAL] Сбой при чтении read()");
                    close(config.pty_fd);

                    break;
                }
            }
            else {
                // Произошли другие события, которые нам сейчас неинтересны (POLLOUT, POLLPRI, POLLRDHUP)
                // @debug
                //std::clog << "[INFO] poll проснулся по иному событию. revents = 0x"
                //          << std::hex << fds.revents << std::dec << std::endl;
            }

        }
        else if (ret < 0) { // ret < 0
            // Ошибка самого системного вызова poll (например, прерван сигналом)
            if (errno == EINTR) continue;
            std::perror("[CRITICAL] Сбой системного вызова poll()");
            break;
        }

        // Если прошло время, а ничего не пришло, то ЭМУЛЯЦИЯ внутренней работы (мигаем лампочками итд)
        std::this_thread::sleep_for(std::chrono::milliseconds(400));

        // Этот таймер нужен, чтобы не перегружать проц, если команды сыплются потоком и poll почти не спит
        std::this_thread::sleep_for(std::chrono::milliseconds(20));
    }
}
```

epoll - как работает?

Это абстракция уведомления, а не доставки. Он лишь сообщает, что в буфере есть данные: "гарантированно дергай read()".



[ Шаг 1: Прилетел байт ]
  Дисциплина линии складывает байт в буфер TTY-порта (в памяти ядра).

[ Шаг 2: Проверка спящих ]
  Ядро видит: "Буфер теперь НЕ пуст". 
  Оно заглядывает в специальный список ожидания (`wait_queue`) этого TTY-порта.

[ Шаг 3: Будильник epoll ]
  Если ваш поток вызвал `epoll_wait()`, ядро находит связанную структуру данных.
  Ядро переводит ваш поток из состояния "Сон" (TASK_INTERRUPTIBLE) в состояние "Готов к работе" (TASK_RUNNING).
  `epoll_wait()` завершается и возвращает вашему коду событие: "Дескриптор /dev/ttyS0 ГОТОВ ДЛЯ ЧТЕНИЯ (EPOLLIN)".

[ Шаг 4: Забор данных ]
  Ваш поток проснулся. Но в руках у него НЕТ байта! У него есть только знание, что файл готов.
  Ваш код обязан вызвать `read(fd, &buf, 1)`.
  Только в этот момент ядро берет байт из буфера TTY и копирует его в ваш `&buf`.





//--------------------------------------
open
    фундаментальный кирпичик Unix-архитектуры.
    Поскольку «всё есть файл», то open() может открыть практически любой ресурс операционной системы.

Через open ядро Linux предоставляет единый интерфейс (дескриптор fd) для работы с совершенно разными сущностями:

1. Обычные файлы и директории
    - Файлы на диске: Текстовые документы, бинарники, картинки, базы данных (.txt, .bin, .db).
    - Директории (папки): Папку тоже можно открыть (обычно с флагом O_DIRECTORY), 
        чтобы, например, читать её содержимое на низком уровне или заблокировать от изменений.

2. Устройства (Файлы в /dev/)
    - Псевдотерминалы (PTY/TTY): /dev/pts/N, /dev/ttyS0 (COM-порты), к которым подключаются модемы.
    - Физические накопители: /dev/sda или /dev/nvme0n1 — можно открыть жесткий диск напрямую в обход файловой системы 
        (так делают утилиты разметки дисков или установщики ОС).
    - Генераторы случайных чисел: /dev/urandom и /dev/random — открываются для чтения криптографически стойких байт.
    - «Черные дыры»: /dev/null (туда пишут, чтобы удалить данные) и /dev/zero (оттуда читаются бесконечные нули).

3. Межпроцессное взаимодействие (IPC)
    - Именованные каналы (FIFO): Специальные файлы на диске, созданные через mkfifo. 
        Если процесс А откроет такой файл на запись, а процесс Б — на чтение, они смогут передавать данные друг другу.
    - Unix Domain Sockets: Файлы сокетов (часто лежат в /tmp/ или /run/), которые используются для быстрой и безопасной 
        связи между двумя программами на одном компьютере (например, так общаются Docker-демон и CLI-клиент).

4. Виртуальные файлы ядра (/proc/ и /sys/)
    Это не настоящие файлы на диске, а «окна» в оперативную память ядра:
    - Через open("/proc/meminfo", O_RDONLY) программа может узнать текущее состояние оперативной памяти системы.
    - Через файлы в /sys/class/gpio/... на одноплатных компьютерах (вроде Raspberry Pi) можно управлять 
        физическими ножками микросхем (подавать ток или считывать напряжение).

Основные флаги

+--------------+----------------------------------------+---------------------------------------------------------+
| Флаг         | Описание                               | Типичное применение                                     |
+--------------+----------------------------------------+---------------------------------------------------------+

1. Флаги режима доступа (Access Modes)
    Обязательные флаги. В вызове open должен присутствовать строго один флаг из этой группы.

| O_RDONLY     | Открытие только на чтение              | Чтение файлов конфигурации, логов или /proc             |
| O_WRONLY     | Открытие только на запись              | Запись в файлы, куда не требуется подглядывать          |
| O_RDWR       | Открытие на чтение и запись            | Работа с TTY/псевдотерминалами, базами данных           |
+--------------+----------------------------------------+---------------------------------------------------------+

2. Флаги создания и управления (Creation Flags)
    Управляют поведением ядра в момент открытия или создания файла.

| O_CREAT      | Создать файл, если он не существует    | Логирование, создание новых выходных документов         |
| O_EXCL       | Ошибка, если файл уже существует       | Защита от перезаписи (работает только вместе с O_CREAT) |
| O_TRUNC      | Очистить файл (усечь до 0 байт)        | Полная перезапись файла новой конфигурацией             |
| O_NOCTTY     | Не делать файл управляющим терминалом  | Безопасное открытие TTY, исключающее перехват Ctrl+C    |
+--------------+----------------------------------------+---------------------------------------------------------+

3. Флаги статуса и ввода-вывода (I/O Status Flags)
    Определяют, как именно будут происходить операции чтения и записи данных после открытия.

| O_APPEND     | Писать строго в конец файла            | Безопасная дозапись в файлы системных логов             |
| O_NONBLOCK   | Неблокирующий режим (O_NDELAY)         | Чтение из TTY/сокетов без зависания при отсутствии байт |
| O_SYNC       | Блокировать запись до сброса на диск   | Гарантия сохранности транзакций СУБД на физическом HDD  |
| O_DSYNC      | Блокировать до сброса данных (без мета)| Оптимизированная синхронизация без обновления дат файла |
+--------------+----------------------------------------+---------------------------------------------------------+

4. Специализированные флаги Linux (Advanced Flags)
    Дополнительные системные оптимизации ядра.

| O_DIRECTORY  | Ошибка, если файл не является папкой   | Безопасный обход дерева каталогов в утилитах типа find  |
| O_CLOEXEC    | Закрыть дескриптор при вызове exec()   | Защита от утечки открытых файлов в дочерние процессы    |
| O_NOFOLLOW   | Не переходить по символическим ссылкам | Защита от уязвимостей подмены путей (Symlink Race)      |
| O_DIRECT     | Ввод-вывод в обход кэша страниц ядра   | Прямая работа с диском для высоконагруженных СУБД       |
+--------------+----------------------------------------+---------------------------------------------------------+

Режим O_NONBLOCK (неблокирующий ввод-вывод) — 
    флаг, который кардинально меняет поведение системных вызовов (read, write, open, connect) при работе с «медленными» 
    файлами: терминалами (TTY/PTY), сокетами, пайпами (pipe) и именованными каналами (FIFO).

1. Как работает read():
Блокирующий режим (По умолчанию):
    - поток засыпает внутри read()
    - программа абсолютно мертва
Неблокирующий режим (O_NONBLOCK):
    - Вызов read() возвращается немедленно в ту же микросекунду, независимо от того, есть данные или нет.
    - Если байт в буфере терминала есть, read() возвращает 1 (кол-во прочитанных байт) и записывает его в переменную.
    - Если данных в буфере нет, read() возвращает -1. 
        Ядро устанавливает errno в значение EAGAIN (или EWOULDBLOCK): «Данных сейчас нет, попробуй заново чуть позже».
        Можно пойти помигать лампочками, проверить регистры и вернуться.
2. Как работает write():
    У TTY или сетевого сокета есть ограниченный буфер отправки в ядре (обычно от нескольких килобайт до мегабайта).
Блокирующий режим (По умолчанию):
    - Если программа попытается выплюнуть в модем огромный файл данных (лог), а клиент на той стороне медленно их читает, 
        буфер отправки переполнится. Вызов write() заблокирует программу и будет ждать, пока там освободится место.
Неблокирующий режим (O_NONBLOCK):
    - Если буфер отправки переполнен, write() не станет ждать. Он:
        -- либо запишет лишь ту часть данных, которая поместилась (и вернет количество записанных байт, например 128), 
        -- либо, если буфер забит полностью, вернет -1 и выставит errno = EAGAIN.

read()


Возвращает ssize_t.

1) Возвращает -1 (Произошла ошибка или буфер пуст)
    Это сигнал о том, что чтение не выполнилось. Что именно пошло не так, нужно сразу смотреть в переменной errno:
    В block mode: Произошел реальный сбой (например, EBADF — передан неверный дескриптор, или EIO — аппаратный сбой).
    В nonblock mode (O_NONBLOCK): Чаще всего -1 возвращается, когда errno == EAGAIN (или EWOULDBLOCK). 
        Это штатная ситуация: ядро говорит, что клиент в эту миллисекунду не нажал ни одной кнопки.

2) Возвращает 0 (Обнаружен конец файла / EOF)
    - Для обычного файла на диске 0 означает, что вы дочитали его до самого конца.
    - Для псевдотерминала (/dev/pts/N) — это критический сигнал: клиент на той стороне закрыл соединение 
        (например, пользователь закрыл окно PuTTY, завершил сессию screen или отключил модем).
        При получении 0, выходим из while и закрываем дескриптор.

3) Возвращает > 0 (Успешно прочитаны байты)
    - Число показывает, сколько байт ядро смогло скопировать из буфера ОС в буфер программы.

Монопольное завладение портом (через flock или fcntl):

flock() - консультативная (advisory) блокировка на уровне ядра.
    Это табличка "Занято", а не эксклюзивное право на дескриптор ("моё, не трожь")

Привязка к Open File Description - Блокировка привязывается к открытому файлу в таблице ядра, а не к дескриптору 
    в процессе. Если сделать dup или fork, новый дескриптор будет ссылаться на ту же блокировку, они не конфликтуют,
    но при закрытии в одном месте, блокировка снимется.

Синтаксис: 
    #include <sys/file.h> // For flock
    int flock(int fd, int operation);

Возвращает:
    0 — в случае успешного установления или снятия блокировки.
    -1 — в случае ошибки. Ошибка детализируется в errno.

Флаги:
    - LOCK_SH (Shared) — Разделяемая блокировка. Несколько процессов могут одновременно держать файл открытым на чтение.
    - LOCK_EX (Exclusive) — Эксклюзивная блокировка. Только один процесс может владеть файлом (обычно для записи).
    - LOCK_UN (Unlock) — Снятие существующей блокировки с этого дескриптора.
Блокировки (LOCK_SH / LOCK_EX) можно объединять с побитовым ИЛИ с флагом блокировки: LOCK_NB (Don't block when locking)
    - Без LOCK_NB - если файл занят, то процесс заснет и будет ждать освобождения.
    - С LOCK_NB - если файл занят, то процесс не заблокируется, вернет -1, в errno запишется EWOULDBLOCK.

Тонкости LOCK_UN - не нужно снимать блокировку, если программа завершается (деструктор). Но нужно в 3 случаях:
    - Досрочное освобождение ресурса (Не дожидаясь закрытия) - демон закончил init, больше блокировать не нужно
    - Понижение или повышение уровня блокировки (Lock Promotion / Demotion) - захват конфига монопольно, поправил
        и освободил для других.
    - Явное управление в сложных архитектурах (Fork и Дублирование FD) 
        #DIGDEEP тут про fork/dup, покопать.

В errno:
    - EWOULDBLOCK (EAGAIN) - Самый частый сценарий. Файл уже заблокирован, flock вызывался с флагом LOCK_NB.
    - EBADF - невалидный fd (файл закрыт или дескриптор не существует).
    - EINTR - вызов был в блокирующем режиме (ждал освобождения файла), но был прерван сигналом.
    - EINVAL - в operation передан несуществующий флаг или недопустимая комбинация флагов.
    - ENOLCK - закончилась память для выделения записей о блокировках (редко).


#include <sys/file.h>  // For flock()

if (flock(fd, LOCK_EX | LOCK_NB) == -1) {
    std::cerr << "[Ошибка] Порт уже занят другим процессом!" << std::endl;
    return 1;
}

ERRNO
    Переменная errno (error number) - глобальный системный идентификатор ошибок в POSIX-системах (Linux / macOS). 
    Это фундаментальный механизм, через который ядро ОС сообщает C++ коду, почему именно системный вызов 
    (например, open, read или write) завершился неудачно.Когда системный вызов возвращает ошибку (обычно это -1), 
    ядро Linux записывает числовой код проблемы в errno.

Является потокобезопасной (Thread-local) - у каждого потока свой errno.

Главное правило - системные вызовы никогда не очищают errno, если они завершились успешно.
    Поэтому проверять errno можно только в том случае, если системный вызов вернул признак ошибки 
    (например, read или open вернули значение < 0).

Способы вывести ошибку текстом:
1)  // выведет наш текст, потом докинет ": " и текст ошибки, будет четко
    if (fd < 0) {
        std::perror("Не удалось открыть устройство");
    }

2)  if (read_len < 0) {
        std::cerr << "Критический сбой чтения: " << std::strerror(errno) << " (код: " << errno << ")\n";
    }

EINTR (Interrupted System Call) - системный вызов был прерван отправкой сигнала процессу до того, как успел завершиться.
    Это не признак критического сбоя или бага. Его смысл: процесс спал ожидая ввода (по read), пришел сигнал,
    процесс пришлось разбудить для обработки сигнала. После обработки вызов read не продолжается. 
    Возвращается -1 и устанавливается EINTR.
EBADF - (Bad file descriptor) - неверный дескриптор.
EIO (I/O error) - ошибка ввода-вывода.
EFAULT (Bad address) - залезли в чужую память.









//--------------------------------------
ПРОЦЕССЫ И ПОТОКИ

Базовая формула: Процесс — это контейнер ресурсов, а Поток — это единица исполнения (код в действии).

Процесс - предоставляет потокам изолированную инфраструктуру (ресурсы):
- Виртуальное адресное пространство - (.text) где лежит программа, (.data/.bss) переменные, (Heap) кучу.
- Системные дескрипторы (Handles) - Открытые файлы, сетевые сокеты, окна гуя.
- Токены безопасности и права доступа: Информация о том, от чьего имени (какого пользователя) запущена программа.
- Процессы аппаратно изолированы друг от друга на уровне таблиц страниц и системного регистра CR3.
- Обязательно имеет минимум 1 поток. Не может быть 0 потоков!

Поток - "рабочий" внутри процесса:
- имеет собственный изолированный стек (примерно 1 или 8 МБ) и собственный набор регистров процессора: RSP/ESP, RBP/EBP.
    Все local vars, аргументы функций и адреса возврата создаются в этом стеке и принадлежат только этому потоку.
    При этом есть способы добраться до стека другого потока! Их изоляция не идеальна.
- имеет доступ ко ВСЕМ ресурсам процесса (кроме личных стеков других потоков, с оговорками).
- имеет приоритет выполнения (вычисляется на уровне ОС).
- все потоки внутри одного процесса РАВНОПРАВНЫ (хотя есть нюансы, можно создать привилегированный итд).
- при этом "логически" считаем, что main() - это главный поток.
- если "главный" поток main выйдет через return 0; ОС уничтожит весь процесс целиком, все потоки погибнут.
- поток не знает кто его породил. Любой другой поток может его заджойнить (при наличии доступа к объекту T).

Планировщик ОС (Thread Scheduler) мыслит не процессами, а именно потоками.
Глобально для него все потоки всех процессов абсолютно равноправны (конечно с учетом приоритетов каждого потока).
В современных ОС общего назначения (Windows, Linux, macOS) используется так называемая потоковая модель планирования 
    (Thread-level scheduling). Процесс — это лишь юридический владелец памяти, а планировщик распределяет процессорное 
    время напрямую между потоками.
Шедулер раскидывает потоки на ядра. При этом он знает, что переключение между разными процессами - это дорого, и
    старается группировать потоки одного процесса на одном ядре (или соседних), попутно загружая кэши смежными данными.

Зомби - это процесс, все потоки которого умерли. Обозначается буквой z. Представляет собой запись в таблице процессов,
    хранит только PID и код возврата. Не занимает оперативную память (его адресное пространство очищено), 
    не использует процессор (CPU).
    Не может ожить ни при каких обстоятельствах. Контекст уничтожен, память освобождена. Кода нет, нечего оживлять.

Код возврата потока и процесса - это разные вещи. Когда в main() мы пишем return 0; - это код возврата потока, но при
    штатной работе (когда main умирает последним) это значение пробрасывается рантаймом в ОС как код возврата процесса.
        // То, что скрыто от глаз разработчика внутри стандартной библиотеки (glibc)
        void _start() {
            // ... инициализация ...
            int result = main(); // Вызывается ваш main(), который возвращает 15
            exit(result);        // Вызывается системный вызов exit(15)
        }


Умирающий штатно поток (return) вернет потоку-родителю NULL (или 0-success на уровне ядра).

МНОПОТОЧНОСТЬ.

Во всех ОС (Винда, Линух, Мак) используется ВЫТЕСНЯЮЩАЯ МНОГОЗАДАЧНОСТЬ (Preemptive Multitasking) 
  - это режим работы ОС, при котором ядро полностью контролирует процессорное время и может в любой момент 
    принудительно прервать (вытеснить) выполняющийся поток, чтобы передать процессор другому потоку.
    Главный принцип здесь: «Ни один поток не имеет права занимать процессор вечно, решение принимает только ОС».

Как это устроено изнутри (Пошаговый алгоритм):
1) Выделение кванта (Quantum / Time Slice). Квант - от несколько мсек до десятков мсек
2) Аппаратное прерывание (Таймер) - каждую мсек посылает аппаратное прерывание (hardware interrupt)
3) Перехват управления - Проц физически прерывает текущий поток и передает управление планировщику (разный в каждой ОС).
4) Проверка кванта - уменьшает счетчик времени текущего потока:
    - если квант не закончился, поток продолжает работу.
    - если квант истек, планировщик принимает решение о вытеснении.
5) Смена контекста (Context Switch) - сохраняет текущее состояние Проца (регистры, стек, адрес след.инструкции).
    Загружает контекст следующего потока в очереди и начинает его выполнять.
6) Вытесненный поток (Running►Ready) возвращается в очередь готовых к выполнению потоков (Ready Queue / Run Queue):
    - Винда - падает в конец очереди своего уровня приоритета (одного из 32).
    - Линух - заново вставляется в Red-Black Tree, "правее", подальше от немедленного выполнения.
    Поток получит свою очередь в зависимости от кол-ва ядер, приоритета, кол-ва других поток, поведения самого потока.

Преимущества вытесняющей многозадачности:
- Стабильность системы (Изоляция сбоев) - Зависшее прила будет продолжать вытесняться, не завешивая остальную систему.
- Отзывчивость интерфейса (Плавность) - Мышка ездит даже во время "тяжелой" обработки видео.
- Честность - процессорное время делится по приоритетам, а не как каждая прога пожелает.

СОСТОЯНИЯ ПОТОКОВ на уровне операционной системы (Ядра ОС)
Жизненный цикл потока описывается классическим конечным автоматом. Основных состояний пять:
1) New / Народившийся (Создание): 
    Поток только что создан (выделен изолированный стек, инициализированы структуры данных TIB/TEB в ОС), но планировщик 
    еще не включил его в общую очередь. На этом этапе он не исполняется.
2) Ready / Runable (Готов к выполнению): Поток полностью готов к работе, у него есть все ресурсы, и он стоит в очереди 
    готовых задач (Ready Queue). Ждет, когда планировщик выделит ему ядро процессора и квант времени.
3) Running / Executing (Выполнение): Поток прямо сейчас занимает ядро процессора и физически выполняет инструкции кода. 
    Из этого состояния его может вывести только вытеснение по таймеру (переход обратно в Ready), добровольный уход в 
    ожидание (переход в Waiting) или завершение.
4) Waiting / Blocked / Suspended (Ожидание / Блокировка): Поток не может выполняться, потому что ждет внешнего события. 
    Планировщик полностью игнорирует его и не дает процессорного времени (поток «спит» и потребляет 0% CPU).
    Причины: 
    - Ожидание ввода-вывода (чтение файла, сети), 
    - блокировка на мьютексе (std::mutex), 
    - вызов std::this_thread::sleep_for
    - явная приостановка (Suspend). 
    Когда событие происходит, ОС переводит поток в состояние Ready.
5) Terminated / Dead (Завершен): Поток закончил выполнение своей функции или был принудительно завершен. Его стек 
    освобождается, но системный объект потока может еще недолго находиться в памяти, пока процесс-родитель не заберет 
    код возврата.

СОСТОЯНИЯ ПОТОКОВ на уровне C++ (std::thread / std::jthread)

Понятия и обозначения:
    - объект - имеется в виду объект класса thread: std::thread t();)
    - МПк (основной, главный, вызывающий, main) поток - тот, который создал новый поток (типа "родитель")
    - ДПк (дочерний, вызванный) - поток, который был создан вызывающим (типа "ребенок" - но это плохая аналогия).
Стандарт языка C++ абстрагируется от сложных системных очередей. Поэтому всего два состояния:
1) Joinable (Присоединяемый / Активный) - Означает, что объект в данный момент жестко связан с реальным, живым потоком 
    в операционной системе.
    ВАЖНО! Поток считается Joinable независимо от того, что он делает на уровне ОС (работает на процессоре, стоит в 
    очереди Ready или спит в Waiting).
    ВАЖНО! Если объект Joinable, программист обязан явно вызвать для него .join() (подождать завершения) 
    или .detach() (отпустить в "свободное плавание") до того, как деструктор объекта std::thread выйдет из области 
    видимости. Иначе программа аварийно завершится через std::terminate.
2) Not Joinable (Неприсоединяемый) - Объект представляет собой пустую оболочку и не связан ни с каким потоком в ОС:
    - Поток был создан по умолчанию без указания функции: std::thread t;
    - Для потока уже был вызван метод .join().
    - Для потока уже был вызван метод .detach().
    - Данные объекта были перемещены в другой объект через std::move().

ОСНОВНЫЕ АСПЕКТЫ РАБОТЫ:
- Новый поток создается через создание объекта: std::thread t(Func); Теперь объект t - владелец нового потока.
    Он хранит SystemID нового потока и его дескриптор (Handle). И соответственно: память, стек, регистры итд.
    Т.е. для программиста - это "ручка" управления этим потоком.
- Как только конструктор объекта успешно завершил работу, ОС сразу же получает команду запустить поток.
    Поток регистрируется в планировщике ОС и начинает выполняться параллельно МПк, как только ОС выделит ему 
    квант времени. Он полностью автономен. Мы никак управляем моментом старта.
- Поток изначально является joinable. Пока связь с ним не разорвана (см. ниже) считается, что t им владеет.
- «Разорвать связь» (или передать ответственность) — это значит сообщить объекту std::thread, что ему больше не нужно 
    контролировать и опекать этот поток в ОС.

- Неизвестно чем занят поток в каждый конкретный момент времени - он просто молотит код, который мы ему передали.
    Для координации нужно настраивать каналы связи - атомики, переменные итд

- Есть ровно 2 пути управления объектом: join или detach
    1) join() — приостанавливает выполнение МПк (Waiting) и ожидает завершения работы ДПк. 
       После выполнения join объект потока становится неактивным (joinable() == false).
       Гарантирует, что МПк дождется завершения работы ДПк, прежде чем продолжит выполнение. Можно создать кучу ДПк.
       Опасность повесить весь процесс, если ДПк зависнет (например, бесконечный цикл).
    2) detach() — отсоединяет ДПк от управляющего объекта std::thread. Поток ДПк продолжает работать в фоне под 
       управлением ОС (демон), а объект std::thread теряет с ним связь (joinable() == false).
       При этом можно продолжать работу с потоком через различные механизмы: atomic, mutex, semaphore etc.
       Можем отправлять/получать данные, ставить на паузу итд.

- После завершения потока (Terminated) системный объект потока будет висеть в памяти ровно до тех пор, пока на неё 
    существует хотя бы одна ссылка (открытый Handle). Это зависит от того, что мы вызвали:
    - join - вызывающий поток забирает данные (код возврата) и очищает handle. Системный объект уничтожается мгновенно.
    - detach - Сист.объект уничтожится сразу после завершения своей работы, т.к. main его судьба не интересна вообще.
            (у него нет своего Handle - через который он был привязан к процессу).
    - native_handle (обошли механизм join/detach) - объект будет висеть до конца жизни процесса (потом Проц снесет всё).

- Если поток завершится раньше, чем код дойдет про вызова join/detach, то он перейдет в статус Terminated (Завершен).
    Его изолированный стек уничтожается, память освобождается, поток превращается в зомби (Zombie).
    Системный дескриптор (Handle) и код возврата потока хранится while ДПк не заберет эти данные.

- Отсоединенный поток (detach) привязан не к тому потоку, который его создал, а к процессу в целом. Он будет жить до тех 
    пор, пока жив сам процесс (не завершится самая первая функция main(), или наступит краш, или std::exit()).

- Создавать ДПк может как поток main() (90% всех программ, создают в основном потоке), так и отдельный поток (бригадир), 
    который уже управляет созданием и работой с другими потоками-рабочими. При этом надо помнить про передачу 
    данных по ссылкам - переменные, полученные по ссылке от "бригадира" будут уничтожены при уничтожении бригадира, 
    а сам поток-рабочий продолжится (пока не наступит main-return0). Возникнет UB.

- ВАЖНО! Если объект std::thread выходит из области видимости (уничтожается в деструкторе), оставаясь в состоянии 
    joinable() == true (т.е. для него не были вызваны ни join(), ни detach()), то рантайм автоматически 
    вызывает функцию std::terminate(), что приводит к аварийной остановке всего приложения.

- Повторный вызов join/detach для потока (т.е. joinable==false) вызовет эксепшн std::system_error. Его выбрасывает либа.
    Поэтому всегда проверяем: if (t.joinable())...

- Механизмы join/detach придуманы для управления системными ресурсами и предотвращения утечек памяти («зомби-потоков»).
    Это защищает ОС от ситуации, когда программа наплодила тысячи уже мертвых потоков (Zombie Thread), чьи системные 
    дескрипторы забили всю память ядра.
    Если же рабочий завис в цикле, а бригадир его тупо ждет (join), то ОС считает, что всё нормально - на уровне системы
    программа не сломана, а работает норм. Предотвратить такое залипание механизм join/detach не может, он не для этого.
    Он для банальной гигиены памяти внутри самой ОС.

- ВАЖНО! Порядок выполнения созданных потоков недетерминирован (созданный в коде позже может выполниться раньше!):
    - Они могут быть раскиданы по очередям на разных ядрах (ниже) 
    - они могут протупить при создании - тяжелая операция, пока сходит в ring0, пока выделит память, то-се.
    - также играют роль: Динамические приоритеты (Priority Boost) и Аффинитивность к кэшу (Cache Affinity).

- У потока есть некий платформозависимый ID, который можно использовать (==, <, >). Везде будет разный, но будет.

- Рантайм запускает поток в обертке типа:
    void __thread_proxy(void* args) {
        try {
            my_function(); // Запуск функции потока
        } 
        catch (...) { // Сюда долетает любое непойманное исключение!
            std::terminate(); // Рантайм сам жестко вызывает эту функцию. Если не зареган обработчик, то вызывается
                              // std::abort(); А это уже команда ОС: SIGABRT - «процесс, убей себя»
        }}

ОСОБЕННОСТИ МНОГОЯДЕРНОЙ СИСТЕМЫ

Основной поток (Ядро 0) -> Создает потоки последовательно 0, 1, 2... 9
                                |
       +------------------------+------------------------+
       |                        |                        |
       v                        v                        v
Ядро 1 (Очередь)         Ядро 2 (Очередь)         Ядро 3 (Очередь)
[Поток 0] -> Ждет        [Поток 2] -> Ждет        [Поток 9] -> СРАЗУ ИСПОЛНЯЕТСЯ!
[Поток 3] -> Ждет        [Поток 5] -> Ждет

- Планировщик распределяет (балансирует) создаваемые потоки по разным ядрам CPU.
- Поток i=3 попадает на Ядро 1, где в этот момент очередь уже занята тяжелым системным процессом или потоком i=0. Он ждет.
- Поток i=9 распределяется на Ядро 3, которое в данный момент полностью свободно. Ядро 3 мгновенно забирает 9-й поток 
    из его локальной очереди и выполняет, пока 3-й поток все еще ждет освобождения Ядра 1.

ЗАМЕЧАТЕЛЬНАЯ АНАЛОГИЯ РАБОТЫ ПРОЦЕССОРА-ПРОЦЕССА-ПОТОКОВ НА ПРИМЕРЕ ЗАВОДА

1) Архитектурная модель: «Завод и Бригады»:
- Завод (Компьютер): Предоставляет общую инфраструктуру: энергоснабжение, вентиляцию, физическое пространство.
- Бытовка со шкафами и чертежами (Процесс): Изолированный контейнер ресурсов. Хранит общую кучу (Heap), глобальные 
    переменные и открытые файлы. Бригады полностью изолированы друг от друга операционной системой.
- Рабочий (Поток / Unit of Execution): Живая единица, выполняющая инструкции. У каждого рабочего на поясе есть свой личный 
    блокнот (изолированный стек) для быстрых промежуточных расчетов, куда никто другой не заглядывает.
- Станок (Ядро процессора): Физическая вычислительная мощность. Станков обычно меньше, чем рабочих.
- Ящики у станка (Кэш процессора L1/L2/L3): Столы прямо под рукой у станка для временного хранения чертежей.
    - Внутрипроцессное переключение (дешевое): За станок встает рабочий из той же бригады; чертежи в ящиках +- совпадают
    - Межпроцессное переключение (дорогое): За станок встает рабочий из чужой бригады; ящики приходится полностью 
      опустошать и забивать новыми чертежами из чужой бытовки (смена адресного пространства / сброс TLB).
2) Как ОС управляет заводом (Планировщик и Многозадачность):
- Вытесняющая многозадачность: Начальник цеха (Планировщик ОС) жестко контролирует станки. Каждые несколько миллисекунд 
    (квант времени) он принудительно прерывает рабочего по сигналу аппаратного таймера и отправляет его обратно в 
    очередь готовых задач (Ready Queue).
- Приоритеты: Определяют, как часто рабочий получает доступ к станку. Зависят от класса приоритета всей бригады 
    (процесса) и индивидуальной роли рабочего внутри нее. ОС может временно «премировать» рабочих (Priority Boosting) 
    за работу с интерфейсом или ввод-вывод.
- Ликвидаторы (OOM Killer): Если рабочие забивают все склады завода хламом (выделяют слишком много памяти в Heap), 
    приходит ОМОН (OOM Killer) и цинично расстреливает всю прожорливую бригаду (процесс) целиком, чтобы спасти 
    завод от коллапса.
- Катастрофы (Неотловленные исключения): Если рабочий совершает критическую ошибку, которую никто не обработал, 
    срабатывает система SOS. ОС мгновенно сносит здание бытовки (уничтожает процесс) со всеми рабочими внутри, 
    так как память может быть повреждена («отравлена») - заблочена мьютексами итд.

ПРОБЛЕМЫ И СИНХРОНИЗАЦИЯ ПОТОКОВ

Data Race (Гонка данных) — это чисто аппаратная/памятийная проблема некорректного доступа к одной ячейке памяти. 
    - возникает на самом низком уровне — уровне оперативной памяти и кэша процессора.
    - Два или более потоков одновременно обращаются к одной и той же ячейке памяти.
    - Хотя бы один из этих потоков выполняет запись.
    - Потоки не используют синхронизацию (нет мьютексов или атомиков).
    - В стандарте C++ DR автоматически означает Undefined Behavior (Неопределенное поведение)
        (при хорошей оптимизации в ячейку памяти могут попасть даже биты от разных потоков).
Race Condition (Состояние гонки) — это логическая/архитектурная ошибка в порядке выполнения операций.
    - возникает, когда корректность работы Прг зависит от недетерминированного порядка или времени выполнения потоков 
        планировщиком ОС. Даже защищенный мьютексами код, всё равно может сломаться "логически" - если один поток
        окажется быстрее - из-за плохо продуманной предметной области.

Критическая секция (Critical section) - участок кода, выполняющий операции над разделяемым ресурсом.

КАК РАБОТАЕТ МЬЮТЕКС

ВАЖНО! Мьютекс сам по себе - не запрещает доступ к определенной ячейке памяти (переменной, объекту итд).
    Это всегда "джентельменское" соглашение в коде, что раз мьютекс занят, то мы эту переменную не трогаем.
    Всегда можно написать поток-хулиган, который изменит данные, невзирая ни на какие мьютексы.
    Железо+ядро+рантайм - предоставляют нам механизм эксклюзивного захвата мьютекса, а что с ним делать, решаем сами.

ЛЛ: На уровне железа. Два сигнала не могут слиться в один — мешает физика полупроводников.
Подробно: поток делает несколько последовательных операций:
1) Попытка «с разбегу» (Fast Path):
    Поток выполняет атомарную инструкцию процессора LOCK CMPXCHG (см.ниже). Если потоков > 1, и они выполняют ее
    одновременно (с разных ядер), то только один сможет это сделать. "Везунчик" меняет состояние мьютекса с 0 на 1 и 
    сразу уходит выполнять полезный код, остальные получают 0 (fail).
2) Стадия Спин-лока (Spinning / Адаптивное ожидание):
    Опоздавшие потоки начинают крутиться (в своем ядре) в очень коротком цикле, проверяя не освободился ли мьютекс?
    Покрутиться дешевле, чем сразу укладывать всех спать (Context Switch - очень дорогая операция, см.ниже).
    Загружает ядро на 100% - жрет энергию. Есть способы управлять им в ручном режиме (включать только когда хотим).
3) Стадия Сна (Slow Path / Блокировка):
    После несколько сотен пустых циклов (примерно), понимает, что мьютекса не дождаться, и делает системный вызов.
    ОС забирает его квант и отправляет поток спать (Waiting).
4) Когда первый поток закончит работу и вызовет unlock(), это сбросит мьютекс в 0 и 
    пошлет сигнал ОС: «Разбуди первого из очереди». Ядро лезет в таблицу этого мьютекса, где записано, какие потоки
    ждут освобождения этого мьютекса. Будит следующего и тот продолжает работу.

«Нечестные» мьютексы (Barging): Во время пробуждения потока (долго) может прибежать третий поток и нахально захватить 
    мьютекс себе (Fast Path). Проснувшийся поток покрутится в спин-локе и опять заснет.
    Это нечестно, но считается эффективным.

Под капотом представляет собой обычный указатель, по которому хранится его внутр.состояние. А также: счетчик ожидания, 
    флаги. Суммарным размером около 40 байт (Linux/pthread) или 8 байт (вWindows SRWLock).
При его активации внутри ядра создается таблица, в которую записываются потоки, которые спят и ждут его освобождения.
Кол-во мьютексов в системе почти не ограничено, активные будут лежать в кэшах, неактивные (со ждунами) вытеснятся
в RAM.

В кэшах (Cache-lines) есть проблема Ложного разделения (False Sharing). #DIGDEEP

НИЗКОУРОВНЕВАЯ РАБОТА БЛОКИРОВКИ

Инструкция CMPXCHG (Compare and Exchange, сравнение с обменом), для мьютекса всегда выполняется вместе с префиксом LOCK.
LOCK обеспечивает:
- Эксклюзивный доступ: Гарантирует, что текущее ядро будет единственным, кто имеет доступ к этой области памяти 
    на время выполнения всей операции «чтение-модификация-запись».
- Блокировка кэша (одной линии кэша): В L3 находится арбитр, в L1/L2 данные о занятости мьютекса. Именно арбитр решает,
    кто из потоков, пришедших с разных ядер, получит мьютекс (1), остальные получают 0.
    На одноядерных системах
- Атомарность: гарантия, что в процесс обмена никто не влезет.

На одноядерных и многоядерных процессорах, процесс блокировки отличается:
- на 1-ядр: 
    - Нет спин-лока (не имеет смысла, нет другого ядра, которое могло бы отпустить мьютекс). Обычно вместо него yield.
    - Поток сразу уходит в глубокий сон (Wait State)
    - Поток, захвативший мьютекс, будет работать пока не освободит мьютекс. Есть риски утечки блокировки (lock leak).
    - Префикс LOCK блокирует таймер (гарантия, что пока выполняется CMPXCHG, таймер не придет переключать потоки и
        не сломает запись данных в цикле «чтение-модификация-запись»).
- на Многоядерных:
    - Этап спин-лока есть (существует надежда, что другое ядро освободит мьютекс).
    - Префикс LOCK блокирует линию кэша и ждет решения арбитра в L3.

Прим.: CMPXCHG очень быстрая, т.к. обрабатывается преимущественно чистым железом (контроллером кэша и шины) (Ring 3).

ПЕРЕКЛЮЧЕНИЕ КОНТЕКСТА (Context Switch)

Состоит из двух принципиально разных частей: «чистой» работы ОС и тянущегося «шлейфа» аппаратных задержек процессора.
Итоговая стоимость сильно зависит от того, переключается ли контекст между потоками одного процесса или между разными 
    процессами, а также от сопутствующих аппаратных задержек.
1) Чистое переключение (Direct Cost) - время, которое тратит сама ОС (код ядра), чтобы сохранить регистры одного прцесса 
    и загрузить регистры другого. В конце переключения будет считаться, что переключение "юридически" произошло:
    - Сохранение и восстановление регистров (~500 тактов)
    - Очистка конвейера инструкций (~50–500 тактов)
    - Обработка системного вызова / прерывания (~1000 тактов)
2) Косвенные издержки (Indirect Cost) - суммарные потери, которые несет процессор с момента начала переключения 
    до того момента, когда новый процесс начнет работать на полную мощность (прогрев кэшей итд).

ТАЙМИНГИ:

Цифры зависят от процессора и ОС, но для современного x86/ARM процессора десктопного уровня средний порядок величин:

- Создание потока (std::thread t(Func)): ~10–50 МИКРОСЕКУНД (то есть 10 000 – 50 000 наносекунд!).
    Это тяжелый системный вызов ядра ОС. Ядру нужно выделить физический 1-8 МБ блок памяти под изолированный стек, 
    прописать структуры данных в планировщике, выделить хэндл и настроить контекст регистров процессора. 
    По меркам процессора создание потока — это целая вечность.
- Метод detach() потока: ~10–50 наносекунд. Это чисто внутрипрограммная операция C++. Объект std::thread просто обнуляет 
    свой внутренний идентификатор (ID) и делает пару проверок в памяти. Он не ходит в ядро ОС.

Чуть потыкал во внутреннее устройство процессора, это чума вообще!

Например, предсказатели ветвлений и предвыборка данных - работают на чистом железе.
А спекулятивное выполнение (заранее, по ветке) работает прямо во время выполнения нашего кода, в паузах.
И если ветку угадали, то код уже выполнен на 100-200 инструкций вперёд, а если не угадали, что выкидывается.
Также внутри есть микрокод (пишется на VHDL/Verilog), который можно даже перепрошить.

Виртуализация - это вообще шедевр! Инженеры добавили 2 глоб.уровня (VMX Root / VMX Non-Root).
Основная ОС (хозяин) работает в Root и отдает управление в гостевую (Non-Root). Если гость хочет выполнить нечто
запрещенное, просыпается хозяин, замораживает гостя, проверяет и исполняет команду, и возвращает ее гостю.
Память также работает на 2 уровнях. Гость стучится в MMU №1, который возвращает "физический" адрес, который тут же
MMU №2 преобразуется в настоящий физический.

И кэш! L3 - общий для всех ядер, умеет "подсматривать", что одно из ядер себе там потащило и ставит "протухание" данных.
    Именно оно отвечает за флажок мьютекса итд

Сноски и важные напоминания:
- ам. - Амортизированное время (иногда случается перевыделение памяти за O(N)).
- *   - Операция нарушит текущую сортировку контейнера.
- **  - Операция сохраняет сортировку, если элемент вставляется строго в свою позицию (например, найденную через 
        std::lower_bound).
- O(1)* для std::list — Сама вставка/удаление занимает O(1), но сначала нужно дойти до середины списка за O(N). Если итератор уже указывает на узел, то операция займет чистые O(1).

АЛГОРИТМЫ
(здесь про сами алгоритмы, не про функции C++)

--------------------
КРАСНО-ЧЕРНОЕ ДЕРЕВО (Red-Black Tree) #RBT

Процедура обхода дерева - In-order traversal / симметричный обход бинарного дерева
Сложная процедура, т.к. "соседние" узлы не лежат в памяти последовательно, а могут принадлежать другому родителю итд.
Проблема: Процессорный кэш страдает (Cache Misses)
Выигрыш: Для любого пути обхода дерева, сложность будет О(1) , хехе


--------------------
ДВОИЧНАЯ МАКСИМАЛЬНАЯ КУЧА (binary heap / max-heap)
    Полное бинарное дерево, где значение каждого родительского узла больше или равно значениям его дочерних узлов.

Базовые операции и их сложность:
1) Добавление элемента: Новый элемент добавляется в конец массива, после чего «всплывает» наверх, меняясь местами 
    с предком, пока не восстановится свойство кучи. Сложность — O(log n).
2) Извлечение максимального элемента: Корень (максимум) удаляется, а его место занимает последний элемент массива. 
    Затем этот элемент «просеивается» вниз, меняясь местами с наибольшим из своих потомков. Сложность — O(log n).
3) Просмотр максимума: Возвращается значение корня. Сложность — O(1).
4) Построение кучи: Массив преобразуется в кучу за O(n) путем вызова операции просеивания вниз для всех элементов, 
    начиная с последнего родительского узла.

Условие - «сложность по памяти должна быть O(1)»
(пространственная сложность / space complexity).
Это значит, что программа должна расходовать константный (фиксированный) объем дополнительной памяти, который не 
зависит от размера входных данных. Сколько бы элементов ни пришло на вход алгоритму (10, 1000 или 10 миллионов), 
количество используемой оперативной памяти должно оставаться практически неизменным.
Если пришел вектор, нельзя создавать еще один вектор, чтобы копировать данные туда.
Можно создавать только счетчики, индексы или временные буферы для обмена элементов, размер которых всегда одинаков.

Важные ловушки для джуниора при оценке O(1):
- Память под входные данные не считается дополнительной. Сам массив accum размера N, который вам передали в функцию, 
    уже существует. Если вы просто читаете из него или лезете по индексу через accum.at(j), вы не выделяете новую 
    память. Главное — не копировать его.
- Опасность рекурсии. Если глубина рекурсии зависит от N, то каждый вызов создает фрейм. Это уже O(N).
- Вызовы скрытых функций. Использование некоторых стандартных функций (f.e.перевод числа в строку std::to_string(num)) 
    неявно выделяет динамическую память под эту самую строку. Если это происходит в цикле N раз, то O(1) станет O(N).

Требование O(1) по памяти заставляет модифицировать данные in-place (прямо внутри исходного контейнера, если разрешено) 
или вычислять значения «на лету» в один проход, используя лишь базовые переменные-счетчики.

Ассоциация, агрегация, композиция

- Ассоциация - означает связь «использует» (uses-a) или «взаимодействует с».
    Использует объект, но не хранит его внутри себя. В аргументах фунций - указатели
    void attendClass(Teacher* teacher) {...}
- Композиция (Жесткое владение) - связь «содержит в себе» (has-a), один объект физически хранит внутри своих полей другой объект.
    Часть не может существовать без целого. Если уничтожается главный объект, автоматически намертво уничтожаются все вложенные.
    Это жесткая связь - при уничтожении внешнего уничтожится и внутренний (стены в доме, Человек и Сердце). 
    Объект создается и хранится внутри класса (при удалении внешнего, нужно удалить внутренний).
- Агрегация (Слабое владение) - связь «содержит в себе» (has-a).
    Объекты могут существовать независимо. Если уничтожить целое, части выживут.
    Пример: Университетская группа и Студент. Если расформировать группу, студент не перестанет существовать
    Объект создается снаружи, класс хранит указатель на объект.
    При удалении класса нельзя вызывать delete для хранящихся объектов!

ПРО КРОССПЛАТФОРМЕННОСТЬ

Кроссплть - там, где чистый язык - конструкции, контейнеры 

Кроссплть заканчивается там, где коду нужно выйти наружу — обратиться к возможностям операционной системы.
Т.к. устройство операционных систем у Windows и Unix (Linux/macOS) принципиально разное, то и либы начинают отличаться:
    - Сеть (Сокеты): В Linux сокеты — это часть файловой системы (POSIX-стандарт). В Windows сеть сделана иначе 
        (через подсистему Winsock), у неё своя инициализация (WSAStartup) и свои типы данных.
    - Работа с консолью (termios.h): В Linux управление терминалом (Raw Mode) встроено в ядро через драйвер TTY. 
        В Windows консоль — отдельная подсистема Win32 API со своими функциями вроде GetConsoleMode и SetConsoleMode.
    - Комитет C++ просто не может стандартизировать сокеты или управление терминалом так, чтобы это устроило обе 
        ОС, поэтому в стдлиб до сих пор нет встроенной работы с сетями 
        (разговоры об этом идут годами, но к C++26 сеть так и не добавили).

Как это решают профессиональные разработчики?
1) Сторонние кроссплатформенные библиотеки (Фреймворки):
    - Для сетей берут Boost.Asio или Asio. Они прячут внутри себя весь этот ужас с Windows- и Linux-сокетами, 
        предоставляя красивый, чистый C++ код, который одинаково компилируется везде.
    - Для графики и окон берут Qt, SFML или SDL.
2) Пишут строго под одну целевую платформу:
    - Если сервер будет крутиться только в облаке на Linux (а это 90% современных серверов), разработчики 
        настраивают WSL, Docker или ставят Linux второй системой и пишут чистый POSIX-код.
3) Современный C++ (C++20/C++23 и новее):
    - Стандарт потихоньку развивается. Например, в C++20 добавили <filesystem> для кроссплатформенной работы 
        с путями файлов (раньше разделители / и \ тоже приходилось разруливать руками).
